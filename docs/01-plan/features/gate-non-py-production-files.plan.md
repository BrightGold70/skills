# Plan: gate-non-py-production-files

## Executive Summary
During Phase 5, make all three write gates (Claude, codex, agy) TDD-judge a non-`.py` file **if and only if** it is code-like (not one of the nine doc/data suffixes), not exempt, and listed on an active impl-plan Task's **Production file** line, using one shared listing matcher in the judge and one shared doc/data definition. Doc/data files stay allowed even when listed (operator ruling R-A). Retire wire-pin 5b's `ungated:` report, and update the h-mad prose that states which files the gates judge (FR-10).

## Overview
h-mad's largest production code is shell (`h-mad/scripts/hmad-dispatch.sh`, `h-mad/bin/hmad-dispatch`), and today no host's gate judges it: the parser drops non-`.py` production tokens into `ungated`, the judge inherits that drop, the Claude gate early-allows every non-`.py` suffix, and the codex and agy gates judge only `_is_production_python` names. Wire-pin 5b reports the hole but cannot close it. This plan closes row 2856's gate half by gating code-like files on Task membership rather than suffix, so a listed `.sh` needs a failing test first, an unlisted `.sh` stays free, and every `.md`/`.json`/other doc/data write stays free whether listed or not.

## Scope
In scope, all under `h-mad/` in this worktree:
- The impl-plan Task parser `h_mad_wire_pin_gate._parse_tasks` and wire-pin 5b's report (`check()` result and `main` output).
- The judge `h-mad/scripts/h_mad_tdd_judge.py`: the listing decision inside `resolve`, its exposure to the Claude gate as a CLI verb or flag, and `target_module_names` for a non-`.py` target.
- One code-level doc/data definition (the nine suffixes and the ASCII case-insensitive end-of-basename predicate, spec Terms), imported by the codex and agy gates and used or pinned-copied by the Claude gate (FR-11).
- The three write gates: `h-mad/hooks/h-mad-tdd-gate.sh`, `h-mad/hooks/h-mad-codex-tdd-gate.py`, `h-mad/hooks/h-mad-agy-tdd-gate.py`.
- Their tests and mutation specs under `h-mad/tests/`.
- The h-mad prose surfaces that state which files the gates judge, and the doc-derived test that pins them (FR-10; Deliverables D9).

User-visible behaviour: during an active Phase 5, a write to a listed, code-like, non-exempt file is DENY until its Task's pytest test fails for an assertion; a doc/data write is ALLOW in every state, listed or not; the `ungated:` line is gone from wire-pin 5b output; an undecidable listing for a code-like target fails closed with `kind=judge-error`. Everything else is as today.

## Goals
- Every backticked production path reaches the judge's Task map, not only `.py` ones — FR-1.
- Wire-pin 5b stops making a claim ("no TDD judge covers it") that is no longer true for code-like files, and its retired guarantees are re-pinned — FR-2.
- Exactly one implementation decides "listed", alias-closed on the target side, reachable from all three hosts, and asked only for code-like non-exempt targets — FR-3.
- A listed non-`.py` target is judged by its Task's own tests, with the two Python-only shortcuts switched off — FR-4.
- The Claude gate allows doc/data before any state read and judges a listed code-like target instead of early-allowing it — FR-5.
- The codex gate does the same in its per-target selection — FR-6.
- The agy gate does the same in its write-class loop — FR-7.
- A listing that cannot be decided for a code-like target denies, in exactly the stated states — FR-8.
- Each host is proven end to end on its own, following the `verify-hmad-gates` method against the worktree's hooks by explicit path, with a paired unlisted control and a recorded hook identity — FR-9.
- The prose that states which files the gates judge states the shipped rule — FR-10.
- Doc/data files are allowed on every host, listed or not, by one shared definition — FR-11.

## Requirements

- FR-4: `judge` resolves a listed non-`.py` target via `impl-plan` to its Task's `tests`; never reaches the name map; `target_module_names` returns `frozenset()` for non-`.py`. The judge does not apply the doc/data rule.

- FR-7: agy gate applies FR-6's rule, doc/data skip included, in its write-class loop after unchanged T1–T5.
- FR-8: for a code-like non-exempt target, unreadable chain or unreadable/undecodable impl-plan → `kind=judge-error` on every host; absent impl-plan → not listed; a doc/data target is ALLOW in every one of these states.

- FR-10: the two floor surfaces (`codex-implementer-prompt.md` Hook bullets; `codex-runtime.md` §"Trust boundary") and any the design's widened sweep adds state the four-part rule; AC-10.1 phrase sweep empty; AC-10.2 doc-test tokens.
- FR-11: one code-level doc/data definition; the gates apply it identically, before any listing decision, over every canonical name; a mixed-name target is judged. Stated residual: a listed doc/data file is never judged.

## Implementation Strategy
- **Widen, do not fork.** FR-1 widens the existing `production` field (operator call 1) rather than adding a sibling. The consumer census (M1) shows the judge's `resolve` is the only script reading `production`, so widening reaches the one reader that needs it and moves no other.
- **One matcher, three transports.** The listing decision is extracted from (or exposed by) `resolve`; codex and agy reach it in-process through the existing `h_mad_target_identity._load_judge()` path, and the Claude gate reaches it through a judge CLI verb or flag. No gate re-implements matching. The CLI form and its exact value set are a Phase-4 decision (operator call 5).
- **One doc/data definition, applied by the gates only.** FR-11's constant and predicate live in one Python module both Python gates already import (both import `h_mad_target_identity` today, M10; the design names the home). The Claude gate either calls it or keeps its bash `case` arm as a copy pinned equal to it by a test, following the existing precedent `test_h_mad_target_identity.py::test_py_suffixes_match_bash_fold`, which pins the bash `_fold_py` suffixes equal to `PY_SUFFIXES`. The parser and the judge never consult it (FR-1, FR-4), so the judge stays suffix-agnostic and FR-4's fixtures can still drive it with any target.
- **Insert, do not reorder.** In each gate the doc/data allow sits where the non-`.py` allow happens today (Claude: after the path exemptions, before the state read; codex/agy: before per-name qualification and `read_chain`), and the new listed branch follows it, before the existing refusals it must still pass through. The `.py` path is not edited.
- **Fail closed only where undecidable.** FR-8 is the sole place an existing ALLOW becomes DENY for an unlisted file, and only for code-like targets; it is enumerated in the spec and gets its own fixtures, including the AC-8.4 doc/data controls in both states.
- **Retire with a re-pin.** FR-2 deletes the `ungated` surface and its tests/mutants only alongside a replacement test that pins the guarantee on `production`.
- **Prose with its pin.** FR-10's prose edit and the AC-10.2 test extension land in the same Task, RED first (the test fails on the current bullets, M9).
- **Test-first throughout**, in this worktree: each Task's RED is measured before its GREEN, on the full suite.
- **Deliberately not touched:** the Task grammar (`_TASK_RE`, `_PATHS_FIELD_RE`, `_NON_PY_PATH_RE`, `_NONE_VALUE_RE`, `_FIELD_RE`); the path exemption rules (`tests`/`fixtures`, root `docs/`, out-of-root, scratch); `h_mad_derive_test_path.sh`; `h_mad_wire_registry` (still `.py`-only by `changed_files`); the shell-allowance and safe-command routes; `WIREPIN:` / `TDD-JUDGE:` / `TDD-STATE:` shapes; the `verify-hmad-gates` skill (read-only method reference, outside this tree).

## Architecture Considerations
- **The judge is the trust anchor for "listed"; the shared definition is the trust anchor for "doc/data".** After this change, the "is this production" question for code-like non-`.py` lives only in the judge, and the "is this doc/data" question lives in one definition. A defect in either is a defect on every host, which is why AC-3.1 and AC-11.6 are scored per host, each host's test run alone.
- **Claude gate process budget.** The Claude gate is bash under macOS `/bin/bash` 3.2 and stays so (M8). A doc/data write starts no new process in any state (its allow precedes the state read). An unlisted code-like write in a tree with no state file starts no new process (`_chain_may_hold_state` keeps its early allow); with state present it may add at most two short Python processes (state, listing), which the design may merge (NFR Performance). If the Claude gate calls the shared Python predicate instead of a pinned copy, that call must not break the zero-process doc/data rule; this is the main pressure toward the pinned-copy option, and the design states which it chose and why.
- **Case-insensitive matching in bash 3.2.** `${var,,}` is bash 4 and unavailable; `shopt nocasematch` exists in 3.2.57 (spec Terms, measured by the spec author). `nocasematch` is a shell-global option: left set, it would also change every later `case`/`[[ == ]]` in the gate, including the `.py` fold and test-name matching the spec requires byte-identical. The design names the construct and how its effect is confined to the doc/data arm (R12).
- **An existing pin sits on the arm being changed.** `test_py_suffixes_match_bash_fold` requires the literal marker `*.md|*.yaml` to be present in the Claude gate and preceded by `_fold_py` within 300 characters (M10). Narrowing or rewriting the first arm must keep that marker or update the test in the same Task, deliberately.
- **Enumerated CLI contract.** The Claude gate must parse exactly one line with exactly one of the design-named values and refuse `kind=judge-error` on anything else, matching how it treats the `state` and `judge` verbs today. A new value set is a new contract other tooling may read; it must be named once in the design and pinned.
- **Canonical names, not spellings.** Listing and the doc/data predicate are both evaluated over `h_mad_target_identity.canonicalise` names (symlink referent, on-disk case, same-directory hard links). A target is doc/data only when every name is (AC-11.5). The three spellings in AC-3.5 remain residuals and are pinned as ALLOW so a later change is visible.
- **Hook identity under test (settled by R-B).** `~/.claude/skills/h-mad`, `~/.agents/skills/h-mad` and `~/.gemini/config/skills/h-mad` all resolve to `/Users/kimhawk/orca/skills/h-mad`, not this worktree (M7). Every test and every FR-9 drive executes the worktree's hook files by explicit path. FR-9 adopts the `verify-hmad-gates` method, not its helper, whose gate paths are the installed ones with no override and which has no Claude drive (M7).
- **Reach after merge (consequence, not a change).** Once merged, every listed, non-exempt, code-like file in a future impl-plan is judged; listed doc/data files are not (FR-11). M5 counts both halves over existing impl-plans; R5 states the residual.
