# Plan: gate-non-py-production-files

## Executive Summary
During Phase 5, make all three write gates (Claude, codex, agy) TDD-judge a non-`.py` file **if and only if** it is code-like (not one of the nine doc/data suffixes), not exempt, and listed on an active impl-plan Task's **Production file** line, using one shared listing matcher in the judge and one shared doc/data definition. Doc/data files stay allowed even when listed (operator ruling R-A). Retire wire-pin 5b's `ungated:` report, update the h-mad prose that states which files the gates judge (FR-10), and replay the real motivating Task against the base and the shipped hooks (FR-9 incident replay).

## Overview
h-mad's largest production code is shell (`h-mad/scripts/hmad-dispatch.sh`, `h-mad/bin/hmad-dispatch`), and today no host's gate judges it: the parser drops non-`.py` production tokens into `ungated`, the judge inherits that drop, the Claude gate early-allows every non-`.py` suffix, and the codex and agy gates judge only `_is_production_python` names. Wire-pin 5b reports the hole but cannot close it. This plan closes row 2856's gate half by gating code-like files on Task membership rather than suffix, so a listed `.sh` needs a failing test first, an unlisted `.sh` stays free, and every `.md`/`.json`/other doc/data write stays free whether listed or not.

## Scope
In scope, all under `h-mad/` in this worktree:
- The impl-plan Task parser `h_mad_wire_pin_gate._parse_tasks` and wire-pin 5b's report (`check()` result and `main` output).
- The judge `h-mad/scripts/h_mad_tdd_judge.py`: the listing decision inside `resolve`, its exposure to the Claude gate as a CLI verb or flag, and `target_module_names` for a non-`.py` target.
- One code-level doc/data definition (the nine suffixes and the ASCII case-insensitive end-of-basename predicate, spec Terms), imported by the codex and agy gates and used by the Claude gate (FR-11).
- The three write gates: `h-mad/hooks/h-mad-tdd-gate.sh`, `h-mad/hooks/h-mad-codex-tdd-gate.py`, `h-mad/hooks/h-mad-agy-tdd-gate.py`, including a **new listing call site** on the code-like path of the codex and agy gates (FR-3).
- Their tests and mutation specs under `h-mad/tests/`.
- The h-mad prose surfaces that state which files the gates judge, and the two doc-derived tests that pin them (FR-10; Deliverables D9).
- The incident replay of a real tracked Task against the base-commit hooks and the worktree hooks (FR-9, AC-9.4, AC-9.5; Deliverables D14).

User-visible behaviour: during an active Phase 5, a write to a listed, code-like, non-exempt file is DENY until its Task's pytest test fails for an assertion; a doc/data write is ALLOW in every state, listed or not; the `ungated:` line is gone from wire-pin 5b output; an undecidable listing for a code-like target fails closed with `kind=judge-error`. Everything else is as today.

## Goals
- Every backticked production path reaches the judge's Task map, not only `.py` ones — FR-1.
- Wire-pin 5b stops making a claim ("no TDD judge covers it") that is no longer true for code-like files, and its retired guarantees are re-pinned — FR-2.
- Exactly one implementation decides "listed", alias-closed on the target side, reachable from all three hosts through a call site on the code-like path, and asked only for code-like non-exempt targets — FR-3.
- A listed non-`.py` target is judged by its Task's own tests, with the two Python-only shortcuts switched off — FR-4.
- The Claude gate allows doc/data before any state read and judges a listed code-like target instead of early-allowing it — FR-5.
- The codex gate does the same in its per-target selection, in the spec's five-step order and with its Selection rule — FR-6.
- The agy gate does the same in its write-class loop — FR-7.
- A listing that cannot be decided for a code-like target denies, in exactly the stated states — FR-8.
- Each host is proven end to end on its own, following the `verify-hmad-gates` method against the worktree's hooks by explicit path, with a paired unlisted control and a recorded hook identity, and the real motivating Task is replayed before and after — FR-9.
- The prose that states which files the gates judge, or whose writes the Claude-side authorship refusals cover, states the shipped rule — FR-10.
- Doc/data files are allowed on every host, listed or not, by one shared definition — FR-11.

## Implementation Strategy
- **Widen, do not fork.** FR-1 widens the existing `production` field (operator call 1) rather than adding a sibling. The consumer census (M1) shows the judge's `resolve` is the only script reading `production`, so widening reaches the one reader that needs it and moves no other.
- **One matcher, three transports, two new call sites.** The listing decision is extracted from (or exposed by) `resolve`. No gate re-implements matching. Neither Python gate has a judge call on a code-like target's path today (M11): codex calls `_load_judge()` only after `if not production: continue`, and agy, which never calls `_load_judge`, binds `import h_mad_tdd_judge as judge` in `main` and uses it only after its own `if not production: continue`. So codex and agy each get a **new call site** on the code-like path, placed after that guard's `.py` branch per FR-6 steps 2–5, which reads the chain first and then decides listing; it uses the host's existing binding or a new `_load_judge()` call, and the design names both call sites and the binding each uses. The Claude gate reaches the matcher through a judge CLI verb or flag; its form and exact value set are a Phase-4 decision (operator call 5).
- **One selection rule.** Where several canonical names qualify, every host judges the least basename in Python `str` order, and a production-`.py` name, when present, takes the existing `min(production)` path first (FR-6). The Claude gate's `--target` and agy's judged name follow the same rule. AC-5.8, AC-6.5 and AC-7.4 share one selection fixture whose two states each fail a different wrong rule.
- **One doc/data definition, applied by the gates only.** FR-11's constant and predicate live in one Python module both Python gates already import (both import `h_mad_target_identity` today, M10; the design names the home). The Claude gate uses it and holds no bash copy (spec FR-11). The parser and the judge never consult it (FR-1, FR-4), so the judge stays suffix-agnostic and FR-4's fixtures can still drive it with any target.
- **Insert, do not reorder.** In each gate the doc/data allow sits where the non-`.py` allow happens today (Claude: after the path exemptions, before the state read; codex/agy: before per-name qualification and `read_chain`), and the new listed branch follows it, before the existing refusals it must still pass through. The `.py` path is not edited.
- **Fail closed only where undecidable.** FR-8 is the sole place an existing ALLOW becomes DENY for an unlisted file, and only for code-like targets; it is enumerated in the spec and gets its own fixtures, including the AC-8.4 doc/data controls in both states (D10).
- **Retire with a re-pin.** FR-2 deletes the `ungated` surface and its tests/mutants only alongside a replacement test that pins the guarantee on `production`.
- **Prose with its pins.** FR-10's prose edit lands in the same Task as both doc-test changes, RED first: the AC-10.2 extension of `test_hook_bullets_state_the_shipped_rule` (RED on today's bullets, M9) and the AC-10.3 update of `test_skill_states_the_docs_first_component_rule`. Regression provenance for the latter, adopted from spec v1.5, which says the test asserts three different things: its anchor "asserts the rule this feature changes … the change updates the anchor to the new gate-scope sentence in the same Task that rewrites surface 3"; its first four tokens (`FIRST component`, `relative to the project root`, `` `docs` ``, `` `src/docs/foo.py` ``) assert the root-`docs/` first-component exemption, which is current behaviour, and are kept unchanged; and, verbatim from spec v1.5: "The **fifth token**, `Both gates`, is a stale contract, not current behaviour. Three gates apply the docs-first rule today: the codex gate and the agy gate both import `_is_production_python` from `h_mad_target_identity` (whose `docs` first-component check carries the marker `# M:G-DOCS`), and the Claude gate holds its bash copy (`# M:H-DOCS`). The test asserted a two-gate statement as correct. The change replaces this token with `All three gates`, both in the test and in surface 3's sentence that carries it, in the same Task that rewrites surface 3." The updated test asserts five tokens (the four, plus `All three gates`), no longer asserts `Both gates`, and is RED on today's text (new-anchor count 0).
- **Replay the real Task, not a retyping.** The incident replay (D14) copies the impl-plan blob tracked at the base commit byte-for-byte and observes the before verdicts at the base commit rather than assuming them; a before reading other than ALLOW is a finding against the spec's premise, never a pass.
- **Test-first throughout**, in this worktree: each Task's RED is measured before its GREEN, on the full suite.
- **Deliberately not touched:** the Task grammar (`_TASK_RE`, `_PATHS_FIELD_RE`, `_NON_PY_PATH_RE`, `_NONE_VALUE_RE`, `_FIELD_RE`); the path exemption rules (`tests`/`fixtures`, root `docs/`, out-of-root, scratch); `h_mad_derive_test_path.sh`; `h_mad_wire_registry` (still `.py`-only by `changed_files`); the shell-allowance and safe-command routes; `WIREPIN:` / `TDD-JUDGE:` / `TDD-STATE:` shapes; the `verify-hmad-gates` skill (read-only method reference, outside this tree); the replayed impl-plan (read, never edited).

## Architecture Considerations
- **The judge is the trust anchor for "listed"; the shared definition is the trust anchor for "doc/data".** After this change, the "is this production" question for code-like non-`.py` lives only in the judge, and the "is this doc/data" question lives in one definition. A defect in either is a defect on every host, which is why AC-3.1 and AC-11.6 are scored per host, each host's test run alone.
- **Two bindings, one module.** codex's `_load_judge()` and agy's `import h_mad_tdd_judge as judge` both load `h_mad_tdd_judge` from `h-mad/scripts/` beside the hook (spec FR-3), so either binding reaches the same matcher. What is new is the call site, not the module: a code-like target exits both loops at `if not production: continue` today (M11), so a matcher wired only where the judge is called today would leave both Python hosts ungated while the Claude host's tests pass. AC-3.1's callee-scoped mutation of the matcher, each host run alone, is one control for that; the other is the connection mutation, adopted verbatim from spec v1.5 AC-3.1: "That mutation is callee-scoped. Each host's **connection** to the matcher is also mutated alone, in both directions (base invariant §"Connection enforcement" in `h-mad/invariants.base.md`), with the matcher left intact. These are six mutants, two per host (Claude, codex, agy), each run with that host alone: (a) *Remove.* The host's new listing call is removed, so the host treats the target as not listed without calling the matcher. The host's listed-DENY test fails: AC-5.1 (Claude), AC-6.1 (codex), AC-7.1 (agy) turns from DENY to ALLOW. (b) *Force.* The host's connection reports "listed" unconditionally, without consulting the matcher's result. The host's unlisted control fails: the `scripts/other.sh` write of AC-5.4 (Claude), AC-6.3 (codex), AC-7.3 (agy) turns from ALLOW to a DENY. Before a mutant's result counts, the run verifies the mutation landed (base invariant §"Mutation verification"): the mutated file differs from the unmutated one at the connection site. A mutant whose landing is not verified scores neither killed nor survived. These six mutants are the connection entries AC-9.3 requires for FR-3."
- **Chain before listing on codex and agy.** The listing decision needs the active records, so the new call site reads the chain first (FR-6 step 3) and only then decides listing (step 4). This is why FR-8's unreadable-chain case is a `judge-error` on the code-like path although the `.py` path's chain read is unchanged.
- **Claude gate process budget.** The Claude gate is bash under macOS `/bin/bash` 3.2 and stays so (M8). A doc/data write starts no new process in any state (its allow precedes the state read). An unlisted code-like write in a tree with no state file starts no new process (`_chain_may_hold_state` keeps its early allow). With state present, adopted verbatim from spec v1.5 NFR Performance: "Where state exists, the Claude gate starts at most three extra short Python processes for an unlisted code-like write: the judge-path derivation (`_find_judge`'s `python3 -c` launch, marker `# M:W6`, which every state-reading path in `h-mad/hooks/h-mad-tdd-gate.sh` runs before `_read_state`), the state read, and the listing decision. The design may reduce this count, for example by deriving the judge path without Python or by merging the state read and the listing decision into one process, and names the count it ships." The Claude gate's use of the shared definition must not break the zero-process doc/data rule; the design states how it holds.
- **Case-insensitive matching in bash 3.2.** `${var,,}` is bash 4 and unavailable; `shopt nocasematch` exists in 3.2.57 (spec Terms, measured by the spec author). `nocasematch` is a shell-global option: left set, it would also change every later `case`/`[[ == ]]` in the gate, including the `.py` fold and test-name matching the spec requires byte-identical. Design D13 uses neither: no bash case-insensitive construct is used, and the case fold is in Python (R12).
- **Existing pins sit on the code being changed.** `test_py_suffixes_match_bash_fold` requires three literal markers in the Claude gate — `# M:H6`, `*.md|*.yaml` and `!= *.py` — each preceded by `_fold_py` within 300 characters (M10). Per design D13, `# M:H6` and `!= *.py` are kept (the `ALL_NON_PY` loop stays byte-identical; only the allow that follows it is replaced), and `*.md|*.yaml` is removed with the arm it marked, so the Task that removes it updates the test's marker tuple in the same Task, deliberately, and says so (R13).
- **Enumerated CLI contract.** The Claude gate must parse exactly one line with exactly one of the design-named values and refuse `kind=judge-error` on anything else, matching how it treats the `state` and `judge` verbs today. A new value set is a new contract other tooling may read; it must be named once in the design and pinned.
- **Canonical names, not spellings.** Listing and the doc/data predicate are both evaluated over `h_mad_target_identity.canonicalise` names (symlink referent, on-disk case, same-directory hard links). A target is doc/data only when every name is (AC-11.5). The selected name is the least qualifying basename (FR-6 Selection rule); because same-directory hard links can be listed by different Tasks, the choice can change the verdict, which is why it is observed rather than assumed. The three spellings in AC-3.5 remain residuals and are pinned as ALLOW so a later change is visible.
- **Hook identity under test (settled by R-B).** `~/.claude/skills/h-mad`, `~/.agents/skills/h-mad` and `~/.gemini/config/skills/h-mad` all resolve to `/Users/kimhawk/orca/skills/h-mad`, not this worktree (M7). Every test and every FR-9 drive executes the worktree's hook files by explicit path. FR-9 adopts the `verify-hmad-gates` method, not its helper, whose gate paths are the installed ones with no override and which has no Claude drive (M7).
- **The replay's "before" side is a second tree.** Each hook loads its siblings from `h-mad/scripts/`, so the before side takes every file under `h-mad/` from the base commit, not just the hook files (spec FR-9). The base is this branch's merge-base with `origin/main` (M12). The evidence is taken before the Phase 7 push: afterwards that merge-base returns HEAD and the before tree equals the after tree, so the driver refuses the replay when the base equals HEAD (spec FR-9). The design names how the before tree is materialised without touching this worktree.
- **Reach after merge (consequence, not a change).** Once merged, every listed, non-exempt, code-like file in a future impl-plan is judged; listed doc/data files are not (FR-11). M5 counts both halves over existing impl-plans; R5 states the residual.
