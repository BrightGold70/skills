## Summary
The plan's task graph, exact paths, 25-mutation JSON, and 38-node RED accounting are coherent, and the v18 timeout mutants now have distinct observables. It is still not dispatch-ready: the timeout AC contradicts itself, the source plan retains an incompatible blanket-RED instruction, and several new guards or mutation procedures do not meet the repository's mandatory discrimination and verification rules.

## Must-fix
- AC-2.6 says there is **no lower bound** because a correct timeout was measured at 0.376 s, but its final paragraph still instructs that “0.5 still rejects an instant return” and calls that “the only thing the lower bound is for” — these are mutually exclusive implementation instructions, and following the later paragraph reinstates the exact `>= 0.5 s` assertion that the same AC proves can reject correct code. Delete the stale 0.5-lower-bound paragraph (the argv capture is already the replacement), or the RED/GREEN contract remains ambiguous and can halt a correct T2.
- The source plan's Convention Prerequisites still says to “confirm each new test fails against the unfixed wrapper,” while its own Success Criteria and the design/impl-plan require 27 failing and 11 legitimately passing RED nodes — an implementer following the prerequisite will demand an impossible blanket RED and trigger `step5d:red_not_all_failing`. The source plan's v1.7 history claims this rule was back-propagated out, so the live body must be swept to the per-node fail/pass contract.
- AC-2.8, AC-5.4, and AC-6.11 prescribe manual tracked-file mutations followed by restoration, but none requires a separate re-read proving either the mutation or the restore landed — observing a test result is not state verification, and a no-op replacement or failed restore can look successful. Add explicit source/JSON re-reads after each change and after each restoration, or route these procedures through the mutation harness; otherwise they violate the base Mutation verification invariant.
- `test_skill_md_frontmatter_unchanged` accepts any line beginning `description:`, including an empty `description:` or wholly changed contract text, while Task 5 says the frontmatter is untouched and uses this test to pin Skill manifest integrity; Task 6 mutates only `name`. Add an exact/non-empty description assertion and a discriminating description mutation (or snapshot the complete existing frontmatter), because the current green-at-RED guard does not enforce half of the contract it claims to preserve.
- `_orca_tail_sig` treats process rc 0 plus a present `.result.terminal.tail` as success without rejecting a top-level `"ok":false`, although this repository explicitly documents and tests that Orca error envelopes can exit 0 and must never pass as data. An error envelope carrying partial/stale tail text can therefore become identity evidence and cause the unsafe wrong-resolution direction; check the envelope verdict before extraction and add a targeted AC/mutation for exit-0 `ok:false`, rather than testing only non-zero exits and missing keys.

## Should-fix
- AC-2.6 still uses a `< 1.5 s` wall-clock threshold to prove the `1`-second override rather than directly asserting the value passed to `_cmd_run` — the measured gap is useful, but scheduler delay can make a correct build fail. Keep a loose upper bound to kill the unbounded-call mutant and use a capture/function seam or source assertion to kill `timeout-override-ignored` deterministically.
