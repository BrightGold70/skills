# Spec: phase5-gate-feature-scope

## Executive Summary
A `step5` record names the checkout its code is written in; every Phase-5 gate applies the record only to that checkout, through one shared rule that fails closed, and a gated codex or agy session cannot change what arms or scopes its gate.

## Goal
A session working on another feature in another checkout runs without Phase-5 allow lines, while an implementer in the named checkout stays gated exactly as strictly as before.

## Definitions

- **Record**: one value of `orchestrator_state` in a state file. A record is *live* when its `phase` is `"step5"`.
- **State file**: a `docs/.bkit-memory.json`.
- **Root**: the project root a hook already determines. codex: `CODEX_PROJECT_DIR`, else the git top level of the payload's project or current directory. agy: the git top level of the parent of the hook's working directory. Claude: `CLAUDE_PROJECT_DIR`. This feature changes exactly one thing here (D7): the codex and agy git lookups ignore the four git environment variables named under *Checkout of a path*. `CODEX_PROJECT_DIR` and `CLAUDE_PROJECT_DIR` are used as given, with no git lookup, and are unchanged.
- **Checkout of a path**: the canonical git top level of the deepest existing directory at or above that path, as `git rev-parse --show-toplevel` reports it, passed through `canonical_directory` (`h-mad/scripts/h_mad_target_identity.py`). Inherited `GIT_DIR`, `GIT_WORK_TREE`, `GIT_COMMON_DIR` and `GIT_CEILING_DIRECTORIES` are not used. When git is missing, fails, times out, or reports no work tree, or `canonical_directory` refuses the top level it reports, the checkout is *unknown*. Git *cannot answer* for a path in each of these cases but one, a path *in no work tree*. A path is in no work tree only when both of these hold for that deepest existing directory: git's report is that neither it nor any parent directory is a repository, and no `.git` entry of any type exists in it or in a directory above it on its resolved path; an entry whose presence cannot be decided counts as one. Every other report is one git cannot answer for. That includes the report that git is inside a repository that gives the directory no work tree, as in a bare repository (operator ruling, 2026-11-25), the report that a repository found there cannot be used, and a report that stops at a filesystem boundary and so is not about every parent. With the second condition, a damaged or dangling repository that git passes over is not read as an absence of one. For a path with a `.git` component the rule of FR-6 comes first, and git cannot answer for it only when that rule gives no checkout. Where git reports a top level, that is its answer, whatever entries lie below that top level. Residual: a git directory that is not named `.git`, has no `.git` entry at or above it, and is too damaged for git to recognise cannot be told from an ordinary directory, and is in no work tree; and on a separate filesystem an ordinary directory in no repository is one git cannot answer for, so more records apply there, unless git itself is set to look across the boundary.
- **Session checkout**: the checkout of the root. When the root itself cannot be opened for reading as a directory, so that `canonical_directory` refuses it, the session checkout is *unknown* in every hook and judge verb, whatever git would answer for that directory (operator ruling, 2026-11-24), and the stage (FR-9) is not consulted. A different case is a root that can be so opened, in a checkout whose reported top level `canonical_directory` refuses: its session checkout is unknown as well, so every live record applies, but the stage is consulted there.
- **Arming fields**: `phase`, `implementation_checkout` and `phase5_stage` (FR-9). No other record field arms or scopes a gate.
- **Gated session**: a codex or agy session to which at least one live record applies (FR-3). A Claude session has a write gate only. A grok session has no shell gate; the Claude `Write|Edit` hook may run in it, and its refusal there is unverified until a live smoke (`h-mad/references/grok-runtime.md` §"The TDD gate").
- **Ungated session**: any other session, and a person at a terminal. The word is about the shell: a Claude or grok session is ungated and may still meet the write hook.
- **Surfaces**: codex shell, codex write tools (`apply_patch`, `Write`, `Edit`), agy `run_command`, agy write tools, and the Claude `Write|Edit` hook.

## Functional Requirements

### FR-1: The record names its implementation checkout
- **Description**: The strict state schema (`h-mad/scripts/h_mad_state_schema.json`) declares an optional field, `implementation_checkout`: a string, or null. It holds the canonical top level of the checkout where the feature's code is written. It is an identity by path, not by git directory, so a moved checkout is covered by FR-4 rather than followed. `h_mad_state_write.py` is its only documented writer, and its rules bind the CLI and the library function (`merge_fields`) alike. A refusal exits 2, prints `ERROR: <reason>` on stderr, and leaves the store byte-identical; success exits 0 and prints `STATE-WRITE: OK`. Callers read that token, never `$?`. A null given for this field or for `phase5_stage` names nothing: it removes the key, or leaves it absent, and is refused where it would clear a value on a record that stays live. Clearing the field removes its key, and the writer stores no null in it, so a writer that predates the field can write the record again (FR-10).
- **The field is written with `phase = "step5"`, at 5a.** If the code will be written in a worktree, the worktree is created before 5a. 5c then creates the branch inside the named checkout and never changes the field. Moving a live feature to another checkout means leaving `step5` (FR-7) and arming again.
- **Acceptance Criteria**:
  - AC-1.1: A record that is not live, given `phase=step5` and a valid checkout in one write, stores both, with the checkout in canonical spelling even when the caller spelled it through a symlink or, on a case-insensitive filesystem, in another case.
  - AC-1.2: The same write is refused, with the store byte-identical, for each of: neither a string nor null; empty; relative; a missing path; a file; a directory that is not a checkout top level; a path git cannot judge. Each is its own test case.
  - AC-1.3: The same write is refused when the state file being written is not among the files FR-2 discovers from the named checkout, compared as real paths. A worktree whose state file is a symlink to the written file passes; a worktree with no state file, or with its own copy, is refused.
  - AC-1.4: A write that takes a record from not live to live without naming a checkout clears any stored checkout. The record then applies everywhere (FR-4), so a value left by an earlier run never scopes a new one.
  - AC-1.5: While a record is live, a write that would change its checkout is refused. Repeating the stored value, as stored or in a spelling with the same canonical form, is accepted without the checks of AC-1.2 and AC-1.3, so the 5a command can be re-run even when the stored checkout is now missing. Naming a checkout on a record that is not live, without `phase=step5` in the same write, is refused.
  - AC-1.6: Any write that takes a record from live to not live clears the checkout in the same write.
  - AC-1.7: A write given a symlinked state file updates the link's target and leaves the link a link. Two checkouts that share a state file by symlink still share it after either one writes, and both writers take the same lock. bkit's target (`seed` in `h-mad/scripts/h_mad_bkit_guard.py`) is seeded for the path as given and for the resolved path.
  - AC-1.8: `h_mad_state_validate.py` reports a record with the field, and a record without it, as strict v2.2. `required` does not change.
  - AC-1.9: A null for either field is accepted on a record that is not live, with or without `phase=step5` in the same write, and on a live record that lacks the field; the key is absent afterwards, and arming with a null checkout is arming without one (AC-1.4). On a record that carries the field and stays live it is refused, with the store byte-identical.

### FR-2: State-file discovery
- **Description**: One shared function decides which state files under a root count. A state file counts when either:
  1. it is `<root>/docs/.bkit-memory.json`, whether or not git tracks or ignores it; or
  2. it is `<root>/<P>/docs/.bkit-memory.json` for a real sub-project `P`: reached without following a directory symlink (the rule is about the path to `P`; `P/docs` itself may be a symlink); no directory from below the root down to `P/docs` is a nested checkout (holds a `.git` entry of any type); no component of `P` is `tests` or `fixtures`; and `P` is not in a git-excluded tree.

  `P` is in a git-excluded tree only when git ignores `P` or a directory above it **and** git has no content under `P` in either the index or `HEAD`. The state file's own ignored status is never consulted. If git cannot answer, the file counts. Presence is decided by `lstat` on the candidate path, on every supported Python: whatever `lstat` finds there is present, so a dangling or looping link is present and unreadable, and a spelling that the filesystem resolves to the candidate path is present. Where `lstat` cannot decide, each path keeps its present decision, the residual of FR-10 apart.

  For a write target, the files that count are those on the target's directory chain up to the root, filtered by the same rule, with one addition: when the target is in a nested checkout `N` under the root, `N` is treated as a root for the part of the chain inside it, and the outer root's chain still counts. A target outside the root uses the root file, as `read_chain` does now.
- **Acceptance Criteria**:
  - AC-2.1: The root file arms its session when git ignores it and when git tracks it.
  - AC-2.2: A sub-project file arms when git tracks content in the sub-project, including when the state file itself is ignored, and when the sub-project is new, untracked and not ignored.
  - AC-2.3: A live copy in a git-excluded directory does not arm any surface; nor does an unparsable copy there.
  - AC-2.4: A live file under a `tests` or `fixtures` component does not arm the root's shell.
  - AC-2.5: A live file in a nested clone, nested linked worktree or submodule does not arm the outer root's shell. It does arm a session rooted in the nested checkout, and a write from the outer session to a target in the nested checkout is judged with it.
  - AC-2.6: Adding an ignore rule for a sub-project that has tracked content does not remove its state file from discovery.
  - AC-2.7: When git cannot answer for a sub-project candidate, the file counts.
  - AC-2.8: With each of the four named git environment variables set, each to a value that changes what git answers, every decision is unchanged, the choice of root included: on codex with and without `CODEX_PROJECT_DIR`, on agy, and on Claude. Each variable has its own case on each of these, and its value names another checkout where that has an effect. A case fails unless git, asked directly a question the hook asks in that case, answers differently with the variable set and unset; where the root comes from git, that question is the root lookup.
  - AC-2.9: A scratch repository holds 20,000 files in 2,000 directories (the directory count is fixed with the operator ruling under Performance) and, beside them, one git-excluded tree with 100 copies of a live state file, each in its own directory. Measured twice, with no live record in the root file and with one live record there naming the root's checkout, on all five surfaces: the decision is the one given with the tree absent, no file in the tree is opened, the git processes started number no more than with one copy in the tree, and the median time over 20 runs is at most 300 ms per hook call above the `7a3cca48` hook in the same repository. The same process count holds with the 100 copies spread over 100 separate git-excluded trees, with 100 further sub-projects that are not excluded and hold a state file with no live record, with the 2,000 directories nested 20 levels deep, and with one file in each of 10 directories in place of the 20,000. At a root outside any git work tree with the same layout, each discovery of that root starts at most one git process.
  - AC-2.10: A sub-project whose `docs` is a symlink to a directory holding a live state file arms. A sub-project reached only through a directory symlink does not.
  - AC-2.11: Each presence case gives one result on every supported Python, in the session's discovery and on a target's chain: a regular file, a file link, a dangling link, a looping link, a directory in the file's place, `docs` as a symlink, and, on a case-insensitive filesystem, a case variant of `docs` and of the file name. In each the file counts. On a case-sensitive filesystem a case variant is another name and does not count.
- **Residual**: a sub-project below a directory named `tests` or `fixtures` is not discovered. A sub-project with no content in the index or `HEAD` leaves discovery if an ignore rule for it appears. A session is gated only by state files discovered from its own root; AC-1.3 keeps a new record from naming a checkout that cannot discover it. For AC-2.8: the judge starts a judged test with the environment it was given, and this feature does not change that; AC-2.8's fixture therefore uses judged tests that run no git, and what a judged test does with those variables is outside it.

### FR-3: One applicability rule for every gate
- **Description**: One shared function takes the discovered records, the session checkout, and the checkout of what is being judged, and returns the records that apply. The codex and agy shell gates, the write-target checks in both, the write judge (`read_chain` and its `state`, `judge` and `listing` verbs) and the Claude hook all use it. A live record applies when any of these holds:
  1. its `implementation_checkout` is not usable (FR-4);
  2. the session checkout is unknown;
  3. its checkout is the session checkout (`checkout-match`);
  4. for a write target, its checkout contains the target, or the target's checkout is unknown (`target-match`);
  5. for a shell command, its checkout contains the directory the command runs in (`directory-match`), or that directory is unknown (`directory-unknown`): its field (codex `workdir`, agy `Cwd`) is present and is not a non-empty string, null and the empty string included (operator ruling, 2026-11-25); or it is not an existing directory; or it exists and git cannot answer for it (Definitions). An absent field is not itself unknown: it selects a directory, with its present meaning, and the clauses on the directory then judge the one selected. On agy that is the root. On codex it is the payload's `cwd`, or the root when the payload gives none; a `cwd` that is null or empty counts as none, and one that is not a string, or is a relative path, is not an existing directory. A directory in no work tree (Definitions) is known, and is contained in no checkout (operator ruling, 2026-11-24); rules 1 to 3 decide there. All this is the value rule 5 uses and nothing else: the directory the safe list is judged in is the one it is judged in now, and what a record with none of the new fields decides does not change (AC-10.1).

  Rules 4 and 5 keep a write that lands in the named checkout gated when it is issued from another one. Containment is by the checkout of the path, so a nested checkout is not part of the outer one. A write with no identifiable or resolvable target, an agy workspace mismatch and an agy tool outside the admitted classes are judged on rules 1 to 3, except that on `run_command` a workspace mismatch is judged as the shell is: rules 1 to 3 and 5, and FR-9. A Claude write with no target, or with one that cannot be resolved, consults the root file alone, as now, and is judged on rules 1 to 3 over its records. The `scope` verb asked with neither a target nor a command directory answers for the session with its whole discovery (FR-8). The decision reads nothing the session says about itself: no feature name, owner id, heartbeat or claim.
- **Acceptance Criteria**:
  - AC-3.1: With two checkouts sharing one state file by symlink and a record naming the first, every surface in the first is gated and every surface in the second is not. This reproduces the two-checkout rows of the brainstorm's evidence table.
  - AC-3.2: With feature A not live and feature B live and naming another checkout, a session for A is not gated on any surface.
  - AC-3.3: With B live and naming this same checkout, a session for A is still gated.
  - AC-3.4: A session in the first checkout writing production code into the second, when a record in its state file names the second, is refused on codex, agy and Claude. On Claude that includes a target that is not Python and that the impl-plan of that record lists, the plan being looked for beside the state file and in the named checkout.
  - AC-3.5: A codex `workdir` or agy `Cwd` inside the named checkout, from a session elsewhere, is gated; one that is present and null, empty or not a string, one naming no directory, or one naming a directory for which git cannot answer (Definitions; a bare repository and a damaged one included), makes every live record apply. One naming a directory in no work tree (Definitions) is judged on rules 1 to 3. An absent one selects the directory rule 5 gives, which is judged in the same way: on codex a payload `cwd` that is not a string, is relative, names no directory, or names one for which git cannot answer makes every live record apply, and one that is absent, null or empty selects the root. The directory each command's safe-list judgement uses is unchanged in all of these.
  - AC-3.6: For one corpus of records, sessions and targets, the codex gate, the agy gate, the judge verbs and the Claude hook agree on which records apply. Removing the call to the shared function from any one of them makes at least one test fail.
  - AC-3.7: Changing `owner_session_id`, `owner_heartbeat_ts`, or the feature key of the record changes no arming decision.
- **Residual**: a shell command issued in an ungated session that names a path in another checkout is not judged by its arguments.

### FR-4: Fail closed, case by case
- **Description**: A live record whose checkout cannot be used applies to every session whose discovery finds it. Each case below is tested from a session in a checkout the record does not name, on all five surfaces, with a valid record naming another checkout as the not-gated control.
- **Acceptance Criteria**:
  - AC-4.1 (absent): no field, or null: applies.
  - AC-4.2 (not a string): number, boolean, list and object: applies.
  - AC-4.3 (empty): applies.
  - AC-4.4 (relative): including `.` and a spelling starting `~`: applies.
  - AC-4.5 (missing path): applies. It is not treated as stale.
  - AC-4.6 (names a file): applies.
  - AC-4.7 (names a directory that is not a checkout top level, including a sub-project directory): applies.
  - AC-4.8 (checkout unreadable, or git cannot judge it): applies.
  - AC-4.9 (unreadable state): an unreadable, unparsable, non-regular or wrongly shaped discovered file gives the same refusal as before this feature on every surface that consults it. On a target's chain it decides whatever any other file on the chain says. Among the files the session discovers, a record that applies and gates the shell decides the shell first, as now, and the unreadable file decides otherwise. A live record that does not apply, or that is at stage `"planning"` (FR-9), never hides an unreadable file. A file whose top level is not an object keeps its present refusal in every case.
  - AC-4.10 (symlinked state file): a link to a valid file is read, and each record is judged by its own checkout; a record with no checkout applies; a dangling or looping link is unreadable and refused, with the same result on every supported Python.
  - AC-4.11 (symlinked checkout): a record spelled through a symlink, and a session entered through one, match the real checkout and no other.
  - AC-4.12 (case variant): on a case-insensitive filesystem a case-variant spelling matches its checkout and no other; on a case-sensitive one it is AC-4.5.
  - AC-4.13 (linked worktree): a record naming the main checkout does not apply in its linked worktree, and the reverse.
  - AC-4.14 (nested checkout): a record naming the outer checkout does not apply in the nested one, and the reverse.
  - AC-4.15 (moved checkout): after the named checkout moves, the record applies in the moved checkout and everywhere else that finds it.
  - AC-4.16 (session unknown): a root whose checkout is unknown because git reports no work tree for it, whether or not that report is an answer (Definitions; a bare repository and a damaged one included), or because git is missing, fails or times out, makes every live record apply. So does a root that cannot be opened for reading as a directory (Definitions), whether it is the top level of a checkout or a directory below one, wherever a hook consults records for such a root: codex and Claude, when the root can be entered. Where a hook refuses before it consults records (agy for any such root; codex and Claude for one that cannot be entered), the refusal is unchanged. At a root that cannot be so opened, a record at `"planning"` gates the shell too. A readable root whose reported top level is refused (Definitions) also makes every live record apply, on codex with `CODEX_PROJECT_DIR`, on Claude and in the judge verbs; there a record at `"planning"` does not gate the shell. In each case the not-gated control is, in place of FR-4's, the same case with the root, or the refused top level, made readable and inside a checkout the record does not name, and git available.
- **Residual**: if the named checkout moves and a different checkout is then created at the old path, the record applies to the new occupant and not to the moved one, until it is re-armed. The operator accepted this for v1 on 2026-11-24.

### FR-5: A gated shell cannot change the arming fields
- **Description**: A gated codex or agy shell may run the state writer only for an invocation that changes no arming field. This requirement adds a refusal and admits nothing: an invocation it does not refuse still takes one of the routes of FR-7. The check covers every field assignment in the invocation, in each spelling the writer accepts, and parses field names with the same rule the writer uses. A line in `.h-mad/phase5-shell-allow` does not lift this refusal, directly or through `hmad-dispatch run`. The refusal names the field, the feature, the state file and the exit route of FR-7. codex reports it as a `permissionDecision` of `deny`; agy as `decision` `deny` with `kind=arming-input`.
- **A command the safe list admits** is judged by the position that runs the state writer. The commands the safe list admits take none of their operands as a command to run, apart from the one inner command of `hmad-dispatch run`, which is judged in the same way in every shape of that verb that the safe list admits. Text in any other operand is data: a search, a `git log` or a test run that holds an arming write, or a state write that holds one in the value of another field, keeps its present decision. This is about what `_safe_shell_command` admits, not about a program's name.
- **Any other command** is one that only an operator allow line can admit, and what it runs cannot be known. It is *refused on mention* (operator ruling, 2026-11-25, "Refuse on mention"): when its text holds the state writer's name and an arming field name followed by `=`, anywhere in it, in either order, in one word or in several. No position is sought, so a direct state write that the safe list does not admit is judged this way too, and a line that matches does not lift the refusal, plain or under `hmad-dispatch run`. Without a matching line the command is refused as now, and the reason given is this one. A command that the gate's lexical rule does not carry, or that cannot be split, is admitted by no route and keeps its present refusal.
  - *The text* is the words that the gate's shell splitting gives, joined by single spaces and case-folded, without the quote characters that remain in them (a program may split a word again).
  - *The name* is in the text when the text holds `h_mad_state_write`, as part of a longer word or not. A word, or a part of a word that white space sets off, that leads to the writer's file counts as its name too, its quote characters removed: by resolved identity, as in FR-6, and a relative one from the directory the safe list is judged in.
  - *The field* is in the text when the text holds the name of an arming field, not directly preceded by a letter, a digit or an underscore, and then `=`, with nothing but white space between them, because the writer strips the field name. So `phase =` is a mention, and `current_phase=` and `last_completed_phase=`, which name other fields, are not.
  - *The refusal* names each field found and, in place of the feature and state file of a write, the record that FR-8 (a) names.
  - *Cost*: a command under an operator line that only reads, carries or describes such text is refused, a commit message for example, and so is a state write under a line that holds a field mention in any argument (FR-7, route 2). Such a command counts as a state write that names those fields; AC-5.6 sets only what must be treated as changing an arming field, and this may be more. A command that holds one of the two and not the other keeps its present decision.
- **Acceptance Criteria**:
  - AC-5.1: From a gated codex shell and a gated agy shell, a state write naming any arming field is refused, for a value that arms, disarms or repeats the stored one, on the session's own record and on another.
  - AC-5.2: The same holds when the arming field is one of several assignments in one invocation, in any position.
  - AC-5.3: The same holds with a matching allowance line, plain and wrapped by `hmad-dispatch run`. With such a line, plain and wrapped, a command that the safe list does not admit and that meets the mention rule is refused whatever its program: one the safe list does not know, and one it knows in a form it does not admit. Each clause of *the text*, *the name* and *the field* has its own case. With the name alone, the field alone, or the field's name only as the end of a longer name, the line admits the command as now.
  - AC-5.4: A state write that names no arming field keeps its present decision: creating a record (whose `phase` starts null), claim, release, beat, dropping undeclared keys, and setting any other declared field. One that the safe list admits keeps it whatever text its other values hold; one that it does not admit keeps it when its text does not meet the mention rule.
  - AC-5.5: An ungated session's state write is not affected.
  - AC-5.6: For a corpus of state-writer invocations, which holds ones the safe list admits, ones in every shape of `hmad-dispatch run` it admits, and ones that only an operator line can admit, the set that the gate treats as changing an arming field includes every invocation that, run by the real writer on a scratch store, changes one.
- **Residual**: the gate is a workflow guard, not an operating-system sandbox, as its docstring says. Code that an admitted test run or another operator-declared command executes is outside this requirement, apart from what the mention rule reads in the command's own text.

### FR-6: A gated write tool cannot change the arming files
- **Description**: When a record applies to the session or to the target (FR-3), codex and agy write tools and the Claude `Write|Edit` hook refuse a target that is a state file FR-2 would count, whether or not it exists yet, or that has a path component `.git`. Both are judged from two places, the session root and the target's own checkout: a state file discovered from either, and a `.git` component inside either, is protected. When the target's own checkout is unknown, the session root alone is used. When a path with a `.git` component has an unknown checkout, its checkout, here and in FR-3, is that of the nearest directory above holding such a component whose checkout is known; when there is none, its checkout stays unknown. Targets are judged by resolved identity, so symlink, hard-link-in-directory and case-variant spellings are the same target; a target named through a symlink is also judged under the path as named, and either is enough. Claude and agy use `kind=arming-input`, and agy's closed set `GATE_KINDS` gains exactly that name. Any session that may not use a write tool here uses the state writer, under FR-5 and the routes of FR-7.
- **Acceptance Criteria**:
  - AC-6.1: Creating, editing, moving or deleting the root state file by each codex write operation, each admitted agy write tool and the Claude hook is refused while a record applies.
  - AC-6.2: The same for a sub-project state file and for a target with a `.git` component.
  - AC-6.3: The same for each alternative spelling named above.
  - AC-6.4: With no record applying, those targets keep their present decision.
  - AC-6.5: With discovered state unreadable, those targets are refused on all three hooks.
  - AC-6.6: Other documents and data files keep their present decision while a record applies.
  - AC-6.7: With a record naming checkout A, and checkout B sharing A's state file by symlink, a Claude, a codex and an agy session in B are each refused: A's own state file; the same real file named through B's link; and a target with a `.git` component in A. A target with a `.git` component in B keeps its present decision.
  - AC-6.8: With a record naming checkout A, and A's state file a symlink to the real file in checkout M, a Claude, a codex and an agy session in A are each refused both the link and the real file; a session in M is refused the target named as A's link, and M's own file keeps its present decision there.

### FR-7: Every legitimate writer has an outcome
- **Description**: The callers below were enumerated from `git grep -n h_mad_state_write -- h-mad handoff` and from the phase-field statements in `SKILL.md`, `references/phase5-substeps.md`, `references/failure-recovery.md`, `references/state-schema.md` and the three host runtime references, at `7a3cca48`. "Gated" means gated in the record's own checkout at that moment. Exit means leaving `step5`. *By route* means that the write is accepted from an ungated session, and from a gated one is made by the routes set out below the table; it names no arming field, so FR-5 refuses it only where route 2 says so.

| Caller | Fields | Host and step | Gated then? | Required outcome |
|---|---|---|---|---|
| Phase 0 create and claim; takeover create | new record with `phase` null; claim | any; before Phase 1 | only by another record | by route |

## Non-Functional Requirements
- Performance: *Discovery.* Inside a git work tree every hook (codex, agy, Claude) may start its discovery's git processes at once: before any candidate is found, and with nothing live. This relaxes the earlier rule, which allowed a git process with nothing live only to classify a sub-project state file already found; the operator ruled it on 2026-11-24. At a root outside any git work tree, or with git missing, a discovery may start one git process, the one whose result shows that; it then starts no other, the walk goes on unpruned, and each candidate counts. *Checkouts.* The checkout questions of FR-3 and FR-6 are not discovery. When every file that counts was read and no live record was found, none of them is asked, so a hook then starts no git process beyond those it starts now and its discovery's. A git-excluded tree is pruned as a tree: it is judged once, at its highest excluded directory, and that one answer covers everything below it, so no state file in it is opened or classified on its own. The number of git processes one discovery of one root starts is a constant, at most four, that does not grow with the number of files, state files, sub-projects, excluded trees or directory levels (AC-2.9). *Time.* With one live record in the scratch repository of AC-2.9, the median added time over 20 runs is at most 300 ms per hook call. The same bound, against the `7a3cca48` hook, holds in this repository with its own state files, measured read-only. These two repositories are where the bound is stated; outside a git work tree, and in a tree with more directories, no time bound is set, as before. Every git call this feature adds is bounded (2 s, the bound agy's root lookup already uses), and a timeout of one is handled as "git cannot answer". For the one process of a discovery that answers many paths, the 2 s bounds the time spent waiting for it, summed over its life; its lifetime is not bounded by that. When the process that holds its input exits, nothing ends it but the closing of that input, at which git leaves. A launch that is not git and ignores that closing is outside this requirement (operator rulings, 2026-11-25). The codex and agy root lookups change only as D7 says.
- Security: FR-4, FR-5 and FR-6. No public artifact of this feature contains a reproduction of a gate weakness. Every loosening (D1 to D3, D7 where it admits, FR-3, FR-9) is accounted for by the AC-10.1 differential, which does not hold the case of the FR-10 residual, and each guard has a mutation that a test catches.
- Compatibility: FR-10. Python standard library only; macOS and Linux; each supported Python gives the same decision. The supported Pythons are the distinct interpreters among `/usr/bin/python3`, the `python3` on PATH, and each `python3.N` on PATH from 3.11 up; on the operator's machine at `7a3cca48` those are 3.9, 3.11, 3.12, 3.13, 3.14 and 3.15.
