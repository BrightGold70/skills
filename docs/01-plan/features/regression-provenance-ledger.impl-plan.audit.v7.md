## Summary
The implementation plan is structurally robust, with comprehensive test strategies (including mutation testing of guards) and precise typing across most boundaries. However, it explicitly defers updating the paired Design document to a future phase, creating a severe cross-doc consistency violation across grammar, halt reasons, and git commands that must be resolved now.

## Must-fix
- Cross-doc consistency gap — The Impl-plan specifies mechanics that actively contradict the paired Design document, explicitly acknowledging this by deferring Design updates to "Phase 6a-prime" (noted in v1.1 and v1.4 history). Cross-doc consistency requires synchronized contracts. The Design must be updated now to match the Impl-plan's finalized grammar (5 halt reasons; `undeclared_removals=U`, `dangling=D`, `ambiguous=A` counts; `NOT_COMPARED` token) and git commands (`--name-status --diff-filter=d`).

## Should-fix
- Task 2 `partition` type hints — The return type is defined as `tuple[list, list, list]`. This should specify the element types (e.g., `tuple[list[dict], list[dict], list[dict]]`) to enforce strict type consistency, particularly since the downstream `run_pins` explicitly expects `resolving: list[dict]`.
- Task 6 `changed_files` and `git_show` type mismatch — `changed_files` yields `None` for the `base_path` of an Added file, but `git_show` (Task 3) strictly expects `path: str`. The plan should explicitly require the `challenge` caller to handle the `None` case (e.g., treating the BASE AST as empty) before invoking `git_show` to prevent a runtime `TypeError`.

## Nit
- Task 1 AC-1.1 lists `(kind, id, caller, callee, pin, owning_feature)` as the required fields rejected at write time. While correct for the caller's input, the schema also includes `registered_ts`. It would be clearer to specify that `registered_ts` is generated by `register()` itself rather than expected in the `entries` input, avoiding ambiguity about schema validation completeness.
