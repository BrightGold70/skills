# Design: phase5-gate-feature-scope

## Executive Summary
One module, `h_mad_target_identity.py`, gains discovery, checkout identity, applicability and arming-input functions; the two Python hooks, the judge, the Claude hook, the writer, the assembler and the landing probe each call them at the sites listed here, and no surface keeps a rule of its own.

## Detailed Design

### 1. Git calls
`git_environment()` returns a copy of the process environment without the four variables the spec names, and with `LC_ALL=C`. Every git call of the shared functions and the two root lookups passes it. Every call this feature adds runs with `--no-optional-locks`, reads bytes, and has a 2 s budget (that of `[ignored]` is its waits, summed: §2); a missing git, a nonzero exit not listed below, or an exhausted budget is "cannot answer".

| id of row 29 | Call, run with `-C` | Answer used |
|---|---|---|
| `[checkout]` | `rev-parse --show-toplevel` in the deepest existing directory | one trailing newline removed, then `canonical_directory` |
| `[ignored]` | `check-ignore --no-index -v -n -z --stdin`, one process for the whole scan | a path is ignored when its record's pattern field is non-empty and does not begin with `!` |
| `[index]` | `ls-files -z` | every parent directory of every path is content |
| `[head]` | `ls-tree -r -d -z --name-only HEAD` | every directory named is content |
| `[unborn]` | `log -1 --format=`, only after `[head]` failed | `does not have any commits yet` on stderr: no content in `HEAD`; anything else: cannot answer |

Observed at `b29173f1`, git 2.54.0, in scratch repositories. Every reading in §1, §2, §4, §6, §7 and §12 is a prototype reading, made by hand or with scripts that are not in the repository, until S0 commits them as the parts of `discovery_probe.py` (§12) and the commands can be re-run; one marked as not re-runnable from this repository stays one:

- `printf 'ign\0ign/a\0neg/keep\0s\0.git\0' | git check-ignore --no-index -v -n -z --stdin` gives one four-field record per path, with empty fields for the two last and `!/neg/keep` as the pattern of a re-included directory; a path under `.git` does not end the process. Records arrive after each write, so one process serves a whole scan (the readings below come from such exchanges).
- `--no-index` is required: content is judged from `[index]` and `[head]` together, one rule, and not partly by `check-ignore`.
- `git ls-files -z -o -i --exclude-standard --directory` is not used: it collapses a directory that holds only ignored files and is not itself ignored (it printed `only/` and `s/` beside the ignored `h/`), which FR-2 counts.
- A directory that does not exist has no type, so a rule that ends in `/` matches it only when the question does: with `/ign/` ignored, `ign` gives empty fields and `ign/` the pattern (at `5e36fac6`). §7 asks about such directories, so a directory that does not exist is sent with a trailing `/`, and answers are matched by their order. An existing one is answered the same way with or without it.
- With no commit, `ls-tree` and `rev-parse --verify` fail as they do with a damaged ref; only the `log` message distinguishes them (`does not have any commits yet`, `appears to be broken`).

Content names are compared exactly, then by NFC and case folding confirmed by `os.path.samefile`, so a directory spelled otherwise in the index on a case-insensitive filesystem keeps its content, and on a case-sensitive one it does not. An `OSError` from `samefile`, as for a directory that only `HEAD` has, means not the same.

### 2. Discovery (FR-2)
`TreeOracle(root)` holds the streaming process and the content set, which is read once, after the batch in which git first calls a directory ignored and before the next batch is sent; `excluded(relative)` answers from a memo. It classifies a path's ancestors from the top down, each once; a path below an excluded directory is excluded without being sent; a path below an ignored directory that is not excluded inherits "ignored". `excluded = ignored and not content`. If any call it needs cannot answer, the answer is not excluded. A content call that fails is not repeated, and then every directory that git calls ignored counts. Batches are at most 64 paths and 4 KiB, all answers read before the next write, so neither pipe can fill.

**The streaming process** is started with stderr to `DEVNULL` and unbuffered pipes (an `OSError` from closing one is ignored). An exchange is one batch, written, and its records, read. The 2 s bounds the time spent waiting for the process, summed over its life, and not its lifetime (spec Performance); listing directories is no wait for it, nor is a content call, which has 2 s of its own. Each wait is given what is left of the 2 s. An exchange fails when the process cannot be started, a write fails, or the output ends or the 2 s runs out before the last record of the batch has arrived, and when nothing of the 2 s is left as it begins; one whose last record has arrived has not failed. An exchange that fails ends git for that scan: its pipes are closed, the direct child is killed and reaped (`kill`, `wait`), nothing is restarted, no content call is begun, and the walk goes on, pruned only by the answers there are. Otherwise nothing ends the process but the closing of its input, which comes when the process that holds that input exits, if not earlier; git then leaves (spec Performance). Residual: a launch that is not git and ignores that closing.

**When git ends partway** ("Answers stand", "Count the whole batch"), what counts is decided per path. A path is *answered* when its record has arrived whole and, if that calls it ignored, the content set is there; one whose answer follows from such answers without a call (below an excluded directory; below an ignored one, with the content set there) is answered too. An answered path keeps its answer, and every other candidate counts. Git ends for the scan at the exchange that fails, and not when its process happens to be gone: when all records of a batch have arrived, its content calls are made and decide it. The first batch is the batch that is the first in which git calls a directory ignored; when its exchange fails, the content set is not there, so it counts whole. In a later batch a record that has arrived whole stands. These are the meanings of "answered" and "first batch" in the plan's sentence on a git error for a batch.

`walk_state_files(root, oracles=None) -> Walk(files, errors)`; `session_state_files(root, oracles=None)` is its `files`. `oracles` is a mapping from a canonical top to its one `TreeOracle`: an oracle that is in it is used, and one that is started is put in it. A `Scan` has one (§5) and gives it to its own walk, to every chain asked through it and to the second places of FR-6 (§7), so one scan has one oracle, with one memo and one budget, for each root. Without it a call has a mapping of its own.

1. The root file is tested by its own path, first, and always counts.
2. Directories are processed breadth first. A directory is listed with `os.scandir`; a listing error yields no children and one entry `(directory, error name)` in `errors`. Children that are symlinks, are named `tests` or `fixtures`, or hold `.git` (`lexists`) are dropped. Each remaining child is tested for `docs/.bkit-memory.json` by `lexists` on the joined path (so a symlinked `docs` is followed and a symlinked `P` is not) and for `docs/.git`, before any of them is listed. `.git` directories of the root are walked like any other; the spec does not exempt them.
3. The oracle is started before the first listing (so before the children of the root are tested). No directory is listed, and no candidate returned, until `excluded` has answered for it; the children of one listing are asked together.
4. An `lstat` of a candidate that fails other than by absence (`FileNotFoundError`, `NotADirectoryError`) is treated for `files` as the walk of `7a3cca48` treats it (FR-2; the residual of spec FR-10 apart), and adds one entry to `errors`. An excluded directory is not listed, and what testing it raised is dropped, so nothing in or below one is an error. A root that does not exist or is not a directory is a listing error like any other.

Only the landing probe reads `errors` (§12); every hook's answer is the one it has without them.

`phase5_scan(root)`, the writer, the assembler and the landing probe discover this way, with or without a live record (spec Performance, the operator's ruling). The whole scan starts at most four processes (`[ignored]`, `[index]`, `[head]`, `[unborn]`), whatever the numbers of files, sub-projects, trees or levels. At a root outside any git work tree the first process is the only one: its early end shows that. With git missing the start fails and there is none.

`chain_state_files(root, target, oracles=None)` walks the target's directory chain as `read_chain` does now (realpath of the parent; outside the root, the root file alone). The chain is cut at each directory strictly below the root that holds `.git`; each part is judged relative to its own top (the root, or that nested checkout), the top's own file always counting. Only where a file is present below a top is the oracle for that top asked, and it is started only when the mapping has none. So a target in a sub-project with a state file, under however many names, adds no process for the session root to a scan: its directories are answered from the memo. A nested checkout on the chain is another root, with at most four of its own. `read_chain` has no scan and a mapping of its own, so on codex and agy a production or listed target below such a file is another discovery of that root. `lstat` errors other than absence keep their present decision on the chain and in the walk (the residual of spec FR-10 apart).

### 3. Reading
`read_state(path)` returns `StateRead(path, status, data, error, exception)` with `status` one of `read`, `absent`, `unreadable`, `not-object`. `_state_at` and `_state_status` keep their names, arities and answers over it. `_any_phase5_status` re-raises what it raises today: a `not-object` top level, or an exception `_state_status` does not catch. Scans themselves do not raise, so `arming_target` can treat such a file as unreadable. `live_records(read)` is the one comparison with `step5`.

### 4. Checkout identity (FR-1, FR-3, FR-4)
`checkout_of(path) -> Checkout(top, answered)` asks git in the deepest existing directory of the path's `os.path.realpath`. It has three answers (spec Definitions, Checkout of a path):

1. *A checkout*: git exits 0 and prints a path that `canonical_directory` accepts. `top` is that canonical path.
2. *In no work tree*, `top=None, answered=True`: git exits 128, its whole message, under `LC_ALL=C`, is `fatal: not a git repository (or any of the parent directories): .git`, and no `.git` entry of any type exists in that directory or in a directory above it. An entry is looked for by `lstat`; an error other than absence counts as one.
3. *Cannot answer*, `top=None, answered=False`: everything else. The rule is the complement of the first two and not a list of messages.

For a path whose resolved form has a `.git` component, when git gives no checkout, the answer is the checkout of the nearest directory above that holds such a component and has one; only when there is none does answer 2 or 3 stand. All of this is applied before any caller sees the answer. Residual: the one the spec states, a git directory that is not named `.git`, has no `.git` entry above it and is too damaged for git to recognise.

Observed at `5e36fac6`, git 2.54.0: the message of answer 2 in a plain directory; `not a git repository: (null)` where a `.git` file names a missing directory; `this operation must be run in a work tree` in a bare repository and in the `.git` of a valid checkout; a directory in a checkout that holds an empty `.git` directory gives the outer checkout, which is its answer.

`session_checkout(root)`: unknown, without asking git, when `canonical_directory(root)` raises; else `checkout_of(root)`.

**A readable root whose top level cannot be canonicalised** has an unknown session checkout (spec Definitions, Session checkout; AC-4.16): every live record applies, in the hooks and judge verbs alike. The stage is consulted, because the exception of FR-9 is for a root that itself cannot be opened. Observed: with a top level of mode 0311 and a readable directory below it, `git rev-parse --show-toplevel` answers and `canonical_directory` raises `PermissionError` on the answer. codex (with an explicit root) and Claude can meet it and get a case each, on every surface they have, plus the judge verbs; agy's root is the top level itself, and its present refusal is unchanged. Control: the same fixture with the top level readable and the record naming another checkout, not gated.

`recorded_checkout(value) -> (top, reason)`, the one test used by applicability, the writer and the assembler:

| Reason | Condition, tested in this order |
|---|---|
| `field-absent` | key absent, or null |
| `field-invalid` | not a string; empty; not absolute; not encodable as a path (`ValueError` from `os.stat`) |
| `path-missing` | `os.stat` raises `FileNotFoundError` or `NotADirectoryError` |
| `checkout-unreadable` | `os.stat` raises any other `OSError` |
| `not-a-checkout` | `os.stat` says it is not a directory; it is then neither opened nor given to git, so a FIFO cannot block and a file of mode 000 is this reason |
| `checkout-unreadable` | `canonical_directory` raises `OSError`; git cannot answer (a bare or damaged repository included) |
| `not-a-checkout` | in no work tree; its checkout is another directory (a directory inside a `.git` whose holder is known included) |
| (usable) | canonical path returned; when it equals the known session checkout no git call is made |

Answers are memoised within one scan by directory, so git runs once for the session, once for each distinct target or command directory, and once for each distinct other checkout a live record names. With no live record none of these runs.

### 5. Applicability (FR-3)
`applicable(records, session, target=None, directory=None) -> tuple[Applied, ...]`, with `Applied(record, applies, reason)`. The first that holds gives the reason: the unusable-field reason; `session-unknown`; `checkout-match`; for a target, `target-unknown` then `target-match`; for a directory, `directory-unknown` then `directory-match`; else `other-checkout`.

Rule 5 (FR-3 and AC-3.5) has a value of its own. `command_directory(args, key, decode, absent)` gives it: `MALFORMED_WORKDIR` when the key is present in `args` and holds anything but a non-empty string, null and `""` included, or when `decode` raises; `decode()` for a non-empty string; `absent` when the key is not there. `decode` takes no argument, so the hook binds what its decoder reads, and the root is given as a string, because the root of both hooks is a `Path` and a directory is known only as a string. codex passes `workdir`, `lambda: _command_cwd(payload)` and, as `absent`, `str(root)` when the payload's `cwd` is missing, null or `""`, and that `cwd` as it is otherwise (a test of those three and not of truth, so `0` and `[]` are not the root); agy passes `Cwd`, a function of no argument that is its present decoding of that call's `Cwd`, and `str(root)`. It never raises. The directory given to `_safe_shell_command` stays what it is now on both hosts (`_command_cwd`, and agy's own variable), so a record without the new fields decides as before (AC-10.1). `directory` is unknown when it is not an absolute string that names an existing directory, or when `checkout_of` is not answered for it; so a payload `cwd` that is a number, a list, a relative path, a missing path or a file is unknown, and every live record applies, as AC-3.5 says of an absent `workdir`; a directory in no work tree is known and is contained in no checkout. `None` means rule 5 is not asked.

`stage_gates_shell(record)` is the one reading of a stored stage: false when `phase5_stage` is exactly `"planning"`, true for every other value and for an absent key.

`Scan(root, files, oracles)` holds `root`, the files, their reads, the live `records`, the oracles of §2 and the session checkout (computed on first use); `phase5_scan(root)` is `Scan(root, session_state_files(root, oracles), oracles)` with a new mapping. It gives `Status(value, applied)` with `value` one of `active`, `unknown`, `inactive`. A status is compared by its `value` and never tested for truth: it is a tuple, and a tuple that is not empty is true.

- `session()`: rules 1 to 3, stage not consulted.
- `write(target)`: rules 1 to 4 for that target, over the session's records and those of the target's chain (so a nested checkout's files are included for a target inside it); an unreadable file of either is `unknown`. The target's checkout is `checkout_of` the part of its spelling before its first link, so a link ahead does not move it; a resolved target has no link, and where the link leads is a name of its own (§7). A path on the chain whose presence `lstat` cannot decide keeps its present decision here and in FR-6 (the operator's "Drop it"; the residual of spec FR-10 apart; FR-2, AC-6.4).
- `shell(directory, gates)`: rules 1 to 3 and, unless `directory` is `None`, rule 5. Only a record for which `gates(record)` is true gates the shell; `active` before `unknown`. `gates` is `stage_gates_shell` from S9 and `every_stage`, which is always true, before it.

## Error Handling Strategy
- Git cannot answer: a candidate it has not answered counts (§2); a checkout is unknown; a directory that exists is unknown for rule 5. No git failure raises into a hook, and neither does decoding a command directory for rule 5, which is then unknown.
- FR-5 could not resolve a word (no directory, a file-system error): the word does not lead to the writer, and the text still decides. An exception in `arming_write`, the writer's import included, is a hook exception.
- A path whose presence `lstat` cannot decide: each branch keeps its present decision, FR-6 among them (§5), the residual of spec FR-10 apart. That residual is an exception to each sentence of this design that keeps a present decision or refusal, as it is to each of the spec's.
- Discovery met a directory it could not list or a presence `lstat` could not decide: hooks as now; the landing probe reads `UNKNOWN` (§12).
- The identity module without the FR-6 function: the Claude hook refuses `arming-input` in place of any allow; codex and agy refuse on the failed import.
- A hook or verb exception keeps its present refusal (codex `judge-error`, agy default deny, Claude trap, verbs exit 2).
- A state file that cannot be read keeps its AC-4.9 outcome; `active` from the session's records precedes `unknown` on a shell, `unreadable` precedes everything on a chain.
- Writer: `StateWriteError`, exit 2, `ERROR:` on stderr, no `STATE-WRITE:` line, store byte-identical. Callers read the token and re-read the store.
- Assembler: the spec's exit-2 exception, token on stdout.
- Phase transitions print their `[H-MAD]` markers: the 5d mark, `exit-pending`, and the assembler halts.
