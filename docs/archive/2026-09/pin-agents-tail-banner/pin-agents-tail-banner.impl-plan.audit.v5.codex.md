## Summary
The plan is unusually concrete, but it still contains two correctness gaps in the evidence model and one mandatory connection-testing gap. In particular, its launch-command acceptance criterion cannot be satisfied by the unchanged regex it specifies, and retained scrollback is treated as proof of what a pane is currently running even though the document itself admits panes can outlive the agent. The task/test wiring also does not meet the base invariant's bidirectional connection-mutation requirement.

## Must-fix
- AC-3.1 promises launch-command matching that the specified implementation cannot perform — `_agent_pv_re` currently matches `openai codex|model: *gpt-|gpt-…` for codex and `antigravity cli|gemini [0-9]` for agy; controlled checks of the documented launch lines (`codex '--dangerously-bypass-approvals-and-sandbox'` and `agy '--dangerously-skip-permissions'`) produce NO MATCH for both. T3 nevertheless says launch-command-only evidence resolves, T3 says launch and vendor forms are both in `_agent_pv_re`, and no task changes that helper, so a faithful implementation either remains red or makes AC-3.1 pass by adding a banner and thereby fails to test the claimed path. Reconcile the spec/design/plan by either extending and testing the regexes (including rival rejection) or removing the launch-only guarantee and rewriting AC-3.1.
- Retained tail text is historical evidence, not proof of what the pane “IS RUNNING” — the retention comment explicitly covers a pane where the agent exited and the operator then used the shell, but considers only the `>2000`-line case where the old signature disappears. With fewer than 2000 subsequent lines, the stale own-agent banner remains; if it is the unique match, exactly-one and rival rejection both accept it and dispatch can be sent into a shell, the plan's stated worst failure. Add a measured stale-pane replay and a negative AC, and require current-agent evidence before auto-resolution; if Orca exposes no such evidence, tail evidence must be downgraded to a diagnostic/manual-pin aid rather than a resolver.
- T6 does not verify the T2→T3 connection in both directions — the base Connection enforcement invariant requires a mutation that disconnects the call site while leaving `_orca_tail_sig` intact and another that forces the connection to fire when an earlier pass already resolved. The mutation set has neither: `entry-gated-on-n-eq-0` only disables matching on the ambiguous-title path, while AC-3.6 is never exercised against a force-fire mutant. Add both mutations, verify each anchor landed, and require the positive tail-resolution test and the no-read-after-Pass-0 test respectively to kill them.

## Should-fix
- T2 does not specify an executable way to test the private helper “alone” — `test_hmad_dispatch.py` currently invokes the wrapper only through its unconditional `main`, while `_orca_tail_sig` depends on both `_cmd_run` and `_exec_run`. Specify the leaf-extraction/assembly helper (or another exact harness), and name the required imports; the proposed AC-2.7 code already needs `re`, which the module does not currently import.
- T6's claim that `-k tail` selects exactly the mutation-target tests is false — the current module already has `test_wait_snapshots_the_full_buffer_not_a_tail` and `test_no_verdict_remedies_say_from_start_not_a_bigger_tail`, and T5 adds `test_skill_md_names_tail_evidence_pass`, which also matches. This does not defeat per-node-id attribution, but the verification description should use a selector such as `-k 'test_tail_'` or accurately state the broader collection.
