# Spec: hmad-test-boundaries

## Executive Summary

| Perspective | Summary |
|---|---|
| **Problem** | H-MAD's Phase 6 TDD gate (`h-mad/scripts/h_mad_tdd_judge.py` and `h-mad/hooks/h-mad-tdd-gate.sh`) verifies that tests precede production edits and that each spec acceptance criterion (`AC-X.Y`) is exercised RED before GREEN, and `h-mad/scripts/h_mad_mutation_harness.py` verifies that tests catch declared code-level mutations. Neither gate checks **what** tests assert against **which** boundary at Phase 4 (Design): a design can pass Phase 4 without declaring the public interface under test, the independent source of expected outputs, which dependencies are mocked, or what is excluded from unit testing. That gap admits tautological tests (asserting against outputs computed by the implementation under test) and boundary drift (testing internal helpers or mocking the unit under test). |
| **Solution** | Add a mandatory `## Test Boundaries` section with a 5-column Markdown table (`Public interface`, `Acceptance criteria`, `Expected result source`, `Mocked dependencies`, `Exclusions`) to the Phase 4 design template (`h-mad/references/inline-protocols.md`) and `h-mad/agents/design-author.md`; ship a standalone deterministic checker (`h-mad/scripts/h_mad_test_boundaries_check.py`) invoked by `h-mad/scripts/h_mad_audit_gate.py` on Phase 4 design audits without altering `REQUIRED_SECTIONS` in `h_mad_doc_shape_check.py`; update the Phase 4 design audit prompt (`h-mad/audit-prompt.template.md` and `h-mad/agents/doc-auditor.md`) to challenge oracle independence and boundary placement; and calibrate the checker against 3 archived designs augmented with `## Test Boundaries` tables plus 5 seeded broken fixtures and a mutation spec (`h-mad/tests/mutation-specs/test_boundaries_gate.json`) verified via `h-mad/scripts/h_mad_mutation_harness.py`. |
| **Function / UX Effect** | Every new Phase 4 design document must declare its test boundaries and cover every active `AC-X.Y` in the paired spec (either as a test row or as a `verified by: audit \| live-run \| operator \| doc-review` row naming its proving artifact) before `h_mad_audit_gate.py` can emit `GATE: PASS` or write a `.gated.json` stamp. Pre-existing designs and `docs/archive/**` designs without `## Test Boundaries` are deterministically exempt (`TEST-BOUNDARIES: EXEMPT`). |
| **Core Value** | Forces test boundary and oracle-independence decisions upstream into Phase 4 Design where both deterministic tooling (`h_mad_test_boundaries_check.py`) and independent LLM auditors (`doc-auditor`) can reject tautological or misplaced test plans before Phase 5 (`impl-plan`) and Phase 6 (`implement`) begin. |

## Goal

Shift test-boundary and expected-result-source verification into H-MAD Phase 4 (Design) by requiring a 5-column `## Test Boundaries` table in `docs/02-design/features/<feature>.design.md`, enforcing structural, coverage, placeholder, and oracle-tautology checks deterministically at the Phase 4 design audit gate via a standalone script (`h-mad/scripts/h_mad_test_boundaries_check.py`), instructing Phase 4 design auditors to challenge semantic oracle independence and mock-boundary placement, and proving zero false positives on 3 calibrated archived designs and 100% rejection on 5 seeded defect classes.

### FR-2: Standalone Test Boundaries Checker (`h-mad/scripts/h_mad_test_boundaries_check.py`) — CLI, Tokens, Table Shape, Placeholder Blocklist, and Tautological-Oracle Rules

1. **CLI invocation contract.**
   - `python3 h-mad/scripts/h_mad_test_boundaries_check.py <design_path> [--spec <spec_path>] [--root <project_root>] [--no-exempt]`
   - `<design_path>`: positional path to the `.design.md` file to check.
   - `--spec <spec_path>`: optional explicit path to the paired `.spec.md` file. When omitted, the script resolves `<spec_path>` as follows:
     1. If `<design_path>` matches `<root>/docs/02-design/features/<feature>.design.md` (or relative `docs/02-design/features/<feature>.design.md`), resolve `<root>/docs/01-plan/features/<feature>.spec.md`.
     2. Otherwise, look for a sibling `<feature>.spec.md` in the same directory as `<design_path>` (where `<feature>` is `<design_path.name>` with `.design.md` stripped).
   - `--root <project_root>`: optional repository root directory. When omitted, the effective project root is inferred as `<design_path>`'s ancestor project root (`abs_design.parents[3]`) when `<design_path>` resolves under `<project_root>/docs/02-design/features/<feature>.design.md` or `<project_root>/docs/archive/...`, and falls back to the current working directory (`Path.cwd().resolve()`) otherwise, so invoking the checker or `h_mad_audit_gate.py` from another working directory or an external skill installation directory without `--root` still resolves `<project_root>/docs/01-plan/features/<feature>.spec.md`.
   - `--no-exempt`: optional boolean flag. When passed, disables pre-existing and archive exemptions so the target `<design_path>` is evaluated strictly even if it is under `docs/archive/` or its feature stem is in `PRE_EXISTING_FEATURES`.
2. **Stdout tokens, exit codes, and caller actions ("Read the token, never `$?`").**
   - Every invocation of `h_mad_test_boundaries_check.py` emits a primary single-line machine token on stdout followed (on `FAIL`) by one `TEST-BOUNDARIES-ISSUE:` line per violation:

| Stdout token | Exit code | Meaning | Caller action |
|---|---|---|---|
| `TEST-BOUNDARIES: PASS path=<design_path> rows=<N> acs=<M>/<M>` | `0` | `<design_path>` has a valid `## Test Boundaries` table with `<N>` data rows (`N >= 1`), zero cell violations, and covers all `<M>` active spec ACs. | Proceed (`h_mad_audit_gate.py` allows design audit gate to pass if audit report findings also pass; `design-author` proceeds to report `DONE`). |
| `TEST-BOUNDARIES: EXEMPT path=<design_path> reason=<archived\|pre_existing_feature>` | `0` | `<design_path>` contains no `## Test Boundaries` heading, `--no-exempt` was not set, and `<design_path>` qualifies for exemption under FR-4. | Proceed without requiring `## Test Boundaries` (`h_mad_audit_gate.py` records `TEST-BOUNDARIES: EXEMPT` and does not fail the gate). |
| `TEST-BOUNDARIES: FAIL path=<design_path> issues=<K> reasons=<comma-separated-sorted-unique-reason-codes>` | `0` | `<design_path>` is not exempt and has `<K>` (`K >= 1`) deterministic violations in `## Test Boundaries` or spec AC coverage. Each violation is printed on a subsequent stdout line `TEST-BOUNDARIES-ISSUE: row=<R\|-> col=<column_name\|-> code=<reason_code> detail=<message>`. | Refuse the design (`h_mad_audit_gate.py` forces `verdict = "FAIL"` and refuses to write `.gated.json`; `design-author` fixes the table and re-runs). |
| `TEST-BOUNDARIES: UNREADABLE path=<target_path> err=<ErrorType>` | `2` | Emitted when `<design_path>` does not exist, is a directory, or cannot be decoded as UTF-8; when an **explicitly passed** `--spec <spec_path>` does not exist, is a directory, or cannot be decoded as UTF-8; or when a default-resolved `<spec_path>` (for a non-exempt design when `--spec` was not supplied) **exists on disk** as a directory or cannot be decoded as UTF-8. `<target_path>` is the offending `<design_path>` or `<spec_path>`. | Treat as a hard failure (`h_mad_audit_gate.py` forces `verdict = "FAIL"`; orchestrator halts and reports the unreadable path). |

   - **Closed set of `code=<reason_code>` values on `FAIL` (exit `0`):**
     - `missing_section`: `## Test Boundaries` heading is absent from a non-exempt design document.
     - `missing_table`: `## Test Boundaries` section contains no Markdown pipe table, or contains zero data rows beneath the separator row.
     - `invalid_columns`: emitted when (a) the Markdown table header row does not have the exact 5 columns `Public interface`, `Acceptance criteria`, `Expected result source`, `Mocked dependencies`, `Exclusions` in that order (matched case-insensitively after stripping outer whitespace), **or** a data row has `!= 5` cells (`row=header col=-` or `row=<1-based-row> col=-`); **or** (b) a data row has 5 cells, its `Acceptance criteria` cell (column 2) did not match `empty_cell` or `placeholder_cell`, the paired spec has `>= 1` active ACs, and the `Acceptance criteria` cell contains **zero** `AC-X.Y[a-z]` tokens (`row=<1-based-row> col=Acceptance criteria code=invalid_columns`).
     - `empty_cell`: a cell in any of the 5 columns is empty after stripping whitespace and inline formatting (`*`, `_`, `` ` ``).
     - `placeholder_cell`: a cell in any of the 5 columns matches the closed placeholder blocklist (except `none` in `Mocked dependencies`).
     - `tautological_oracle`: the `Expected result source` cell matches the closed tautological-oracle pattern set.
     - `invalid_non_test_row`: a row whose `Public interface` starts with `verified by:` uses an unrecognized verification kind or fails to name a concrete proving artifact in `Expected result source`.
     - `missing_spec`: emitted (`row=- col=- code=missing_spec`) under `TEST-BOUNDARIES: FAIL` (exit `0`) when `--spec` was **not** supplied on a non-exempt design and neither default candidate (`<root>/docs/01-plan/features/<feature>.spec.md` nor `<design_dir>/<feature>.spec.md`) exists on disk.
     - `uncovered_ac`: one or more active `AC-X.Y` identifiers in the paired `.spec.md` do not appear in the `Acceptance criteria` column of any row.
     - `unknown_ac`: an `AC-X.Y` identifier listed in the `Acceptance criteria` column of a row does not exist as an active or retired AC in the paired `.spec.md`.
   - Residual: Any error outside the 4 primary tokens (`PASS`, `EXEMPT`, `FAIL`, `UNREADABLE`) and the 10 `reason_code` values above is out of contract and must not be emitted.
3. **Section & table extraction rules.**
   - Scan `<design_path>` line by line tracking fenced code blocks (` ``` ` or `~~~`). Ignore any heading or pipe row inside a fenced code block.
   - Locate the level-2 heading matching `^##\s+Test Boundaries\s*$` outside fenced code blocks. Its body extends up to the next level-1 or level-2 heading (`^#{1,2}\s+`) outside fenced code blocks, or end of file.
   - Within the `## Test Boundaries` body (outside fenced code blocks), extract the first Markdown pipe table: a header row (`| ... |`), a separator row whose cells match `^:?-{2,}:?$`, and 1 or more contiguous data rows (`| ... |`). Split cells on unescaped `|` (`(?<!\\)\|`), unescape `\|` to `|` within cell text, and strip leading/trailing whitespace.
4. **Cell normalization & closed placeholder blocklist.**
   - Normalize a cell's text for blocklist matching by stripping outer whitespace, stripping surrounding backticks/asterisks/underscores (`` `*_ ``), collapsing internal whitespace runs to a single space, and applying `.casefold()`.
   - **Closed placeholder blocklist** (matched on the normalized cell string in all 5 columns, with one column-specific exception noted below):

### FR-3: Spec AC Coverage & Non-Test (`verified by:`) Row Rules

1. **Active vs. retired spec AC extraction from `.spec.md` (head-anchored definition rule).**
   - Given the paired `<spec_path>`, scan lines outside fenced code blocks (` ``` ` or `~~~`) and outside `## Version History`.
   - Anchor spec AC extraction to the AC identifier defined at the **head** of an AC bullet or heading line matching:
     `^\s*(?:-\s+(?:\[[ xX]\]\s+)?|#{1,6}\s+)(?:~~)?(?:\*\*|`)*(AC-(\d+)\.(\d+)([a-z]?))\b`
     Only the single leading `AC-X.Y[a-z]` group captured at the head of each matching bullet or heading line is extracted as a spec AC definition (sorted by `(int(X), int(Y), letter)`). Prose cross-references or examples of `AC-...` appearing later on the same bullet/heading line are ignored.
   - A head-defined `AC-X.Y[a-z]` is classified as **retired** (`retired_acs`, excluded from required active coverage) if and only if on its defining bullet/heading line in `<spec_path>`:
     - the head `AC-X.Y[a-z]` token is wrapped in Markdown strikethrough (`~~AC-X.Y[a-z]~~`, `~~**AC-X.Y[a-z]**~~`, ``~~`AC-X.Y[a-z]`~~``, or the line head opens with `~~` before the AC token and has a closing `~~` on the line), OR
     - immediately after the closing bold/backtick/token delimiters of the head `AC-X.Y[a-z]` token (and optional parenthesized/bracketed tags and punctuation/whitespace `[:.,\s-]+`, with `-` placed at the **end** of the character class so Python `re` never raises `re.PatternError`), the remainder of the line starts with case-insensitive `(?:retired|superseded|removed|dropped)\b` or `\[(?:retired|superseded|removed|dropped)\]` or `\((?:retired|superseded|removed|dropped)\b`.
   - Every other head-defined `AC-X.Y[a-z]` on bullet/heading lines in `<spec_path>` (outside fenced code blocks and `## Version History`) is **active** (`active_acs`). Verified head-anchored counts across the 5 reference specs: `17` active (`0` retired) in `docs/01-plan/features/hmad-test-boundaries.spec.md`; `24` active (`0` retired) in `docs/archive/2026-08/exec-path-hardening/exec-path-hardening.spec.md`; `40` active (`0` retired) in `docs/archive/2026-09/audit-report-docs-copy/audit-report-docs-copy.spec.md`; `44` active (`0` retired) in `docs/archive/2026-09/tdd-gate-fail-opens/tdd-gate-fail-opens.spec.md`; and `63` active (`1` retired: `AC-3.7`) in `docs/archive/2026-10/grok-audit-surface/grok-audit-surface.spec.md`.
   - Residual: Prose mentions of `AC-X.Y[a-z]` mid-line, inside `## Version History`, or inside fenced code blocks in `<spec_path>` are ignored. A retired `AC-X.Y[a-z]` is optional in `## Test Boundaries` (permitted if listed, never required if omitted).
2. **Coverage verification between `## Test Boundaries` and `<spec_path>` (multi-token cell extraction).**
   - Unlike `<spec_path>` (which extracts only the single head-anchored `AC-X.Y[a-z]` definition per bullet/heading line under FR-3.1), from every data row's `Acceptance criteria` cell (column 2 of `## Test Boundaries` in `<design_path>`), extract **all** `\bAC-(\d+)\.(\d+)([a-z]?)\b` tokens present in the cell (since a single boundary row may cover multiple ACs such as `AC-1.1, AC-1.2`).
   - If a 5-cell data row's `Acceptance criteria` cell did not match `empty_cell` or `placeholder_cell`, the paired spec has `>= 1` active ACs, and the cell contains **zero** `AC-X.Y[a-z]` tokens, emit `TEST-BOUNDARIES-ISSUE: row=<1-based-row> col=Acceptance criteria code=invalid_columns detail=...`.
   - If any active `AC-X.Y[a-z]` from `<spec_path>` does not appear in at least one data row's `Acceptance criteria` cell, emit `TEST-BOUNDARIES-ISSUE: row=- col=Acceptance criteria code=uncovered_ac detail=missing active ACs: AC-...`.
   - If any `AC-X.Y[a-z]` appearing in a data row's `Acceptance criteria` cell is neither an active AC nor a retired AC in `<spec_path>`, emit `TEST-BOUNDARIES-ISSUE: row=<R> col=Acceptance criteria code=unknown_ac detail=unknown AC not in spec: AC-...`.
3. **Non-test rows (`verified by: audit | live-run | operator | doc-review`).**
   - When an acceptance criterion cannot be verified by an automated unit/integration test (for example, pure documentation/prompt prose or live operator walkthroughs), the row's `Public interface` cell (column 1) must begin (case-insensitively after stripping outer whitespace and backticks) with `verified by:` followed by one of the 4 closed verification kinds:

## Non-Functional Requirements

- **Determinism & zero external dependencies:** `h-mad/scripts/h_mad_test_boundaries_check.py` uses only the Python 3 standard library (`argparse`, `pathlib`, `re`, `sys`, `typing`), makes zero network or LLM calls, and completes in `< 200ms` (`< 0.200` seconds) per design document (measured via `time.monotonic()` in `h-mad/tests/test_h_mad_test_boundaries_check.py` across each of the 3 archived calibration pairs under `AC-6.1`).

- **Backward compatibility (Invariants Axis B):** Existing features in `PRE_EXISTING_FEATURES` and `docs/archive/**` without `## Test Boundaries` emit `TEST-BOUNDARIES: EXEMPT` and never fail `h_mad_audit_gate.py`; existing synthetic unit tests in `h-mad/tests/` that run `h_mad_audit_gate.py` on dummy `.design.md` files without active spec ACs continue to pass without modification.
