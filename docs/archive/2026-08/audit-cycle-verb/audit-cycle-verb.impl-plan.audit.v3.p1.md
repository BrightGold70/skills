## Summary
The implementation plan successfully decomposes the verb into nine well-isolated tasks and incorporates the constraints derived from the design's phase-3 audit cycles. However, there are critical logical contradictions in the `gate()` count-discarding behavior, algorithmic flaws in the shell pseudo-code that silently overwrite per-pass state, and fake mutations in the connection spec that violate the Connection Enforcement invariant by reusing a single downstream guard to claim multiple upstream calls are "forced".

## Must-fix
- **`gate()` invariant contradiction on `INVALID` token** — The plan states that `verdict == "INVALID"` discards counts (`must=0, should=0`), but `gate()` unconditionally asserts `len(findings) == must`. If a report is missing `## Should-fix` but contains a populated `## Must-fix` section, the subprocess returns `INVALID` (`must=0`), but the in-process read will find the must-fix bullets (e.g., `len(findings) == 2`). The assertion `2 == 0` will raise an `OperationalError` and crash the cycle instead of yielding `UNVERIFIED reason=no_gate_sections:p<i>`. `gate()` must skip the `len(findings) == must` assertion (and extraction entirely) when the token is `INVALID`.
- **Invalid Connection Mutations for unconditional calls** — Task 8 invents fake "force" mutations for unconditional connections to reach a count of 12, violating the Connection Enforcement invariant. `verb-assemble-force` removes the `HALT` guard (which happens *after* assembly, so it doesn't force assembly), and `verb-helper-force` removes the exact same `ASSEMBLE:` token guard to claim it forces the helper. The invariant explicitly states "One direction certifies a connection that exists but is unconditional." Task 8 must drop the fake "force" mutations for unconditional calls (`verb -> assemble` and `verb -> helper`) rather than reusing unrelated guards to inflate the mutation count.
- **Task 5 loop variable shadowing silently drops HALT tokens** — In Task 5 Step 4's assembly loop, `tok_i` is assigned as a scalar (`tok_i="$(sed ...)"`). Step 5 then evaluates "any tok_i starting HALT". Since `tok_i` is a scalar, it will only hold the token from the *last* iteration of the loop. If pass 1 HALTs but pass 2 PASSes, the HALT is overwritten and lost, causing the script to illegally dispatch. The implementation must store tokens in an array (e.g., `tok[$i]`) or accumulate a halt flag inside the loop.
- **Missing context arguments in Task 5 no-pass routing** — Task 5 Step 5 pseudo-code invokes the helper no-pass mode with only `--halt-reason` (`helper no-pass mode via "$here/h_mad_audit_cycle.py" --halt-reason "assemble_halt:p${i}", exit 0`). The Design explicitly requires that "Every context arg is forwarded unconditionally, including in no-pass mode" (e.g., `--feature`, `--phase`, `--passes`). Task 5 must explicitly pass these context arguments, otherwise the helper cannot render the `[H-MAD]` marker or the correct `passes=K` count.

## Should-fix
- **Positional argument omission in Task 2 prose** — Task 2's description writes `h_mad_report_wait.py --timeout <grace>`, omitting the positional `<report_path>` argument. While the AC is clear, the prose should match the correct signature (`h_mad_report_wait.py <report_path> --timeout <grace>`) defined in the Design.

## Nit
- **Argument variable mismatch in Task 7** — Task 5 Step 1 parses the grace period as `--report-grace (default 5)`, but Task 7 Step 10 passes it as `--grace "$grace"`. The pseudo-code should consistently name the shell variable `$report_grace` (or the parsing should explicitly map it to `$grace`) to avoid confusion during implementation.
