# Implementation Plan: regression-provenance-ledger

> Source: docs/02-design/features/regression-provenance-ledger.design.md (post-audit, v1.9)
> Branch target: feature/215-regression-provenance-ledger

## Executive Summary

Seven tasks build a stdlib-only wire registry bottom-up — schema and `load` first (with the
conftest guard that must exist before any test writes a registry), then the pure verifier core,
then the git-backed BASE comparison, then the CLI that assembles them into a `WIREREG:` verdict —
after which a single `wiring` task connects the existing 5b gate's `main()` to `register()`, and
two final tasks add the warning-only AST shape challenge and the `SKILL.md` protocol text.

## Task 1: wire_registry_schema_and_load

**Production file**: `h-mad/scripts/h_mad_wire_registry.py`
**Test file**: `h-mad/tests/test_h_mad_wire_registry.py`
**Task shape**: `new-behaviour`

**Description**: Create the new stdlib-only module holding the `.h-mad/wires.jsonl` record schema
and its `load()` parser, plus `register()` with its runtime read-back. `load()` raises on a
malformed line naming the line number, because a silently skipped line is an unguarded wire
reporting as guarded. `register()` writes then re-reads and compares the stored record against what
it intended to write, raising on mismatch — this is production behaviour, not a test step, so the
run that drops a write is the run that fails. This task also adds the sibling conftest guard for
`.h-mad/wires.jsonl`, which must land before any test writes a registry (J18 class: the writer is a
path resolver, and per-test `tmp_path` redirection cannot detect a mutation that disables the
redirection branch).

**Code structure**:
```python
# Record fields: kind, id, caller, callee, pin, owning_feature, registered_ts, status,
# removal_provenance, removed_by_feature, superseding_feature, successor_pin
VALID_KINDS: frozenset[str]          # {"wire"} — enum is wire-only this feature
VALID_PROVENANCE: frozenset[str]     # {"superseded", "pinned-a-defect", "renamed"}
DEFAULT_REGISTRY = ".h-mad/wires.jsonl"

class RegistryError(Exception):
    """Malformed registry content — a cannot-judge, never a verdict."""

def validate_record(record: dict) -> dict:
    """Return the record, or raise RegistryError naming the offending field."""

def load(path: Path) -> list[dict]:
    """Parse JSONL. Raises RegistryError naming the 1-based line number on a bad line."""

def register(entries: list[dict], path: Path) -> list[dict]:
    """Write a BATCH (updating in place on duplicate `id`), then re-read and compare.
    Raises on mismatch. Batch, per the design's `register(entries, path)`: a singular
    signature would make the 5b caller read-modify-write the whole JSONL once per task."""
```

**Acceptance Criteria**:
- [ ] AC-1.1: a caller-supplied record missing any required field (`kind`, `id`, `caller`, `callee`, `pin`, `owning_feature`) is rejected at write time with `RegistryError`. `registered_ts` is **generated by `register()`**, not expected in the input — a caller-supplied timestamp would let a record claim it was registered at a time it was not, and the field exists to say when the writer actually ran
- [ ] AC-1.2: `kind: "counter"` is rejected — the enum accepts only `"wire"`
- [ ] AC-1.3: writing a duplicate `id` twice leaves exactly one record, updated in place
- [ ] AC-1.4: a malformed JSON line makes `load()` raise `RegistryError` whose message contains the 1-based line number
- [ ] AC-4.2a: a tombstone (`status: "removed"`) with no `removal_provenance` is rejected
- [ ] AC-4.2b: a `superseded` tombstone with no `superseding_feature` is rejected
- [ ] AC-4.2c: a tombstone of any provenance with no `removed_by_feature` is rejected
- [ ] AC-4.2d: a `renamed` tombstone with no `successor_pin` is rejected — the schema requires it, and without it the rename declares a successor that cannot be verified, which is the FR-4 evasion `unverified_renames` exists to catch
- [ ] AC-6.2: the read-back is runtime, not test-only — stubbing the write to drop silently makes `register()` itself raise, with no test assertion involved
- [ ] J18: `conftest.py` gains a session-scoped autouse guard that snapshots `.h-mad/wires.jsonl`, restores it if the suite moved it, and fails loudly naming the cause; a test that deliberately re-introduces the leak proves the guard fires
- [ ] J18-mutation: the conftest guard is itself mutated to its permissive value via `h_mad_mutation_harness.py` with `root` passed explicitly, returning `MUTATION: ALL_CAUGHT` — the deliberate-leak test shows the guard fires on a leak, but only mutating the guard shows it is not decoration, and only the harness proves the anchor landed rather than matching zero times and reporting the guard as enforced

**Dependencies on other tasks**: None

## Task 2: partition_and_run_pins

**Production file**: `h-mad/scripts/h_mad_wire_registry.py`
**Test file**: `h-mad/tests/test_h_mad_wire_registry.py`
**Task shape**: `new-behaviour`

**Description**: The pure verifier core. `partition()` takes records plus the collected node-id set
and returns three sets — `resolving`, `missing`, `unverified_renames`. `missing` is derived from
`status: "active"` records only, so a tombstone is excluded before any set arithmetic. A `renamed`
tombstone's `successor_pin` enters `resolving` tagged with its tombstone's `id` **only if** that
successor is in `collected`; otherwise it goes to `unverified_renames` and never reaches the runner.
That intersection is an invariant of `partition()`, not a caller's responsibility: passing an
unresolvable node id to pytest aborts the whole selection (`rc=4`, `no tests ran`), so every wire
would go unverified while no test failed. `run_pins()` returns two empty lists — so `verified` and
`broken` both count 0 — and spawns
**nothing** when `resolving` is empty, because a pytest call with no node-id arguments collects the
entire tree (1331 tests here) and would report a maximal false PASS. Failing pins are recovered from
pytest's short-summary `FAILED <node-id>` lines, matched by string equality against each record's
`pin`.

**Code structure**:
```python
def partition(
    records: list[dict], collected: set[str]
) -> tuple[list[dict], list[dict], list[dict]]:
    """-> (resolving, missing, unverified_renames). Pure; no subprocess, no git.
    Element types are explicit because `run_pins` takes `resolving: list[dict]`."""

def collect(rootdir: Path) -> set[str]:
    """`pytest --collect-only -q` -> node id set. Subprocess 1, always."""

def run_pins(resolving: list[dict], rootdir: Path) -> tuple[list[dict], list[dict]]:
    """-> (verified, broken). Spawns NOTHING when `resolving` is empty. Subprocess 2, conditional."""
```

**Acceptance Criteria**:
- [ ] AC-2.1: with 2 pins of which 1 fails, the counts are `verified=1 broken=1 missing=0`
- [ ] AC-2.2: a broken wire's `owning_feature` appears in the output content, not merely in a count
- [ ] AC-2.3: a pin absent from `collected` is reported as `missing`, a distinct count from `broken`
- [ ] AC-2.4: a tombstoned record whose pin is gone is NOT in `missing` — it is a declared removal
- [ ] AC-2.1b: when every pin is missing, `verified=0 broken=0` and the second subprocess is **never spawned** (asserted against `run_pins` directly, not inferred from a suite that happens not to hit it)
- [ ] AC-4.3a: a `renamed` successor present in `collected` is injected into `resolving`, is actually executed, and a failure is reported under its tombstone's `id` rather than as an anonymous broken pin
- [ ] AC-4.3b: a `renamed` successor NOT in `collected` goes to `unverified_renames`, never reaches the runner, and produces no `rc=4` abort
- [ ] A pin appearing in neither the passed nor the failed set after a run that did execute is reported as an internal inconsistency, not counted as verified
- [ ] `partition()` performs no subprocess and no git call — unit-testable outside a repository

**Dependencies on other tasks**: Task 1 (must complete first)

## Task 3: base_comparison_and_tombstones

**Production file**: `h-mad/scripts/h_mad_wire_registry.py`
**Test file**: `h-mad/tests/test_h_mad_wire_registry.py`
**Task shape**: `new-behaviour`

**Description**: FR-4. `git_show(sha, path, repo)` is the single git primitive and **validates the SHA
itself** via `git rev-parse --verify --quiet <sha>^{commit}` (rc 0 valid, rc 1 invalid) before
reading. The validation must live in the primitive, not in `load_base()`, because the AST challenge
in Task 6 calls `git_show` directly — a validator one level up would leave the challenge reading
"invalid commit" as "file did not exist at BASE", a false clean by the exact mechanism the
validation prevents. `git show` alone cannot discriminate: an absent path at a valid commit and an
invalid commit both exit 128. After validation a 128 is unambiguously "path absent at BASE", so
`git_show` returns `None` and `load_base()` turns that into an empty list — every id is new, which
is not an error. `compare(base_records, head_records)` is pure, takes two plain lists, does not know
git exists, and finds ids present at BASE and absent at HEAD. A tombstoned id is still *present*, so
it is not a removal.

**Code structure**:
```python
def git_show(sha: str, path: str, repo: Path) -> str | None:
    """Validate the SHA, then read the path at it. None = path absent at that commit.
    Raises on an invalid SHA — the CLI turns that into exit 2."""

def load_base(sha: str, path: str, repo: Path) -> list[dict]:
    """Thin JSONL parser on top of git_show. Absent file -> []."""

def compare(base_records: list[dict], head_records: list[dict]) -> list[dict]:
    """-> undeclared removals: ids at BASE, absent at HEAD. Pure; no I/O."""
```

**Acceptance Criteria**:
- [ ] AC-4.1: an id present at BASE, absent at HEAD, with no tombstone yields `FAIL` and names both the id and its `owning_feature`
- [ ] AC-4.4: the declaration is findable from the removed id — the record at that id is what is returned
- [ ] An invalid `--base` SHA is exit 2, **not** an empty base set (which would be a false clean)
- [ ] A registry absent at a valid BASE yields an empty base set, every id new, and no error
- [ ] `compare()` called with two record lists performs no git call and is unit-testable outside a repository
- [ ] A tombstoned id present at both BASE and HEAD is not reported as a removal
- [ ] `compare()`'s result is surfaced as the `undeclared_removals=U` count Task 4 prints, so the `FAIL` it drives is legible in the token rather than only in the detail lines

**Dependencies on other tasks**: Task 1 (must complete first)

## Task 4: cli_verdict_grammar_and_trackedness

**Production file**: `h-mad/scripts/h_mad_wire_registry.py`
**Test file**: `h-mad/tests/test_h_mad_wire_registry.py`
**Task shape**: `new-behaviour`

**Description**: FR-2 and FR-3 — the `verify` subcommand that assembles Tasks 2 and 3 into the
`WIREREG:` token. **Existence is checked first and short-circuits**: an absent registry is
`PASS registered=0` with no git command run at all. That ordering is mandatory because
`git ls-files --error-unmatch` exits non-zero for an *absent* path as well as an untracked one, so
checking trackedness first would report `UNTRACKED` for every repo that has simply never seeded a
registry. Only for a file that exists: `git check-ignore -q` (exit 0 = ignored) plus
`git ls-files --error-unmatch` (non-zero = untracked); either yields `UNTRACKED`. The remedy string
is computed from *which* condition fired — an ignored path is told to add `!.h-mad/wires.jsonl`, an
untracked one to `git add` it — because `.h-mad/` is ignored in this repo and not in HemaSuite, so
the identical gate must say different things. `UNTRACKED` does **not** short-circuit the run: it is
determined early and reported at the end, so `registered=N` and every other count is real on that
verdict too. Verdicts exit 0; only a missing `--base`, an invalid `--base` and an unreadable
registry exit 2, so a stricter gate never registers as a `PostToolUseFailure`.

The token carries `undeclared_removals=U` alongside the other counts. The design's v1.6 amendment
states that a count driving a `FAIL` must appear in the grammar, and AC-4.1 makes an undeclared
removal a `FAIL`; without the count, that verdict prints `broken=0 missing=0
unverified_renames=0` next to `FAIL` and is unreadable. Each `FAIL` driver likewise gets its own
named halt reason, because a verdict exits 0 — so the marker is the only thing that makes a 5f
stop diagnosable from logs alone (`invariants.base.md:61`).

**Code structure**:
```python
def trackedness(path: Path, repo: Path) -> tuple[bool, str | None]:
    """-> (tracked, remedy). Caller MUST check existence first."""

def verify(registry: Path, base: str, rootdir: Path, repo: Path) -> dict:
    """Assemble the verdict dict consumed by the CLI printer.
    Takes `repo` explicitly because it must pass it down to both `trackedness(path, repo)`
    and `load_base(sha, path, repo)`; deriving it from `rootdir` inside would make the
    git root implicit at exactly the two call sites whose verdicts depend on it."""

def main(argv: list[str] | None = None) -> int:
    """Router over three subcommands, which print DIFFERENT grammars:

    verify    -> `WIREREG: PASS|FAIL|UNTRACKED registered=N verified=K broken=J
                 missing=M unverified_renames=R undeclared_removals=U`, plus a
                 `[H-MAD]` halt marker per FAIL driver. Exit 0 on a verdict, 2 on
                 cannot-judge (missing/invalid --base, unreadable registry).
    register  -> writes the batch; no verdict token.
    challenge -> `WIRECHALLENGE: …` (Task 6). Verdict-neutral by construction, so it
                 emits NO halt marker and ALWAYS exits 0 — a warning-only mechanism
                 must never be able to stop a run."""
```

**Acceptance Criteria**:
- [ ] AC-3.1: an absent registry yields `PASS registered=0` and the trackedness check never runs (no false `UNTRACKED`)
- [ ] AC-3.2: a gitignored registry yields `UNTRACKED`, never `PASS`
- [ ] AC-3.3: the remedy text differs between the ignored case and the untracked case
- [ ] AC-3.4: `registered=N` is present on **every** verdict, including `PASS`
- [ ] AC-2.5: exit 0 on `PASS`, `FAIL` and `UNTRACKED`; exit 2 on an unreadable registry
- [ ] A missing `--base` is exit 2
- [ ] `broken > 0`, `missing > 0`, `unverified_renames > 0`, or `undeclared_removals > 0` each independently produce `FAIL`
- [ ] `undeclared_removals=U` is present in the token on **every** verdict — per the design's v1.6 amendment, a count that drives a `FAIL` must be in the grammar, or a `FAIL` with every other count at 0 is unreadable
- [ ] An untracked registry containing a broken pin reports `UNTRACKED` while the detail lines still carry the broken wires
- [ ] Every `FAIL` driver maps to a named halt reason, each emitting a `[H-MAD]` marker: `step5f:wire_regression:<id>` on `broken`, `step5f:wire_pin_missing:<id>` on an undeclared `missing`, `step5f:registry_untracked` on `UNTRACKED`, `step5f:undeclared_removal:<id>` on an undeclared removal (AC-4.1), and `step5f:unverified_rename:<id>` on an unverifiable rename (AC-4.3b)
- [ ] No `FAIL` driver is reachable without a halt reason — asserted by enumerating the drivers against the halt-reason table, so a later driver added without a marker fails the test rather than halting anonymously

**Dependencies on other tasks**: Task 2, Task 3 (must complete first)

## Task 5: register_on_wirepin_pass

**Production file**: `h-mad/scripts/h_mad_wire_pin_gate.py`
**Test file**: `h-mad/tests/test_h_mad_wire_pin_gate.py`
**Task shape**: `wiring`
**WIRE**: `h-mad/scripts/h_mad_wire_pin_gate.py:main` → `h_mad_wire_registry.register`
**WIRE-PIN**: `h-mad/tests/test_h_mad_wire_pin_gate.py::TestRegistrationWire::test_passing_wiring_task_is_registered`

**Description**: FR-6, and the one new wire in this feature. `check()` stays a pure predicate and is
signature-unchanged; `main()` — the I/O shell — is what calls `registry.register()`, on
`WIREPIN: PASS` only, for each `wiring` task carrying a real `WIRE`/`WIRE-PIN`. Registration is I/O,
so placing it in `main()` is what keeps the pure predicate side-effect-free *and* makes the call
itself the pinnable thing. Both mutation directions are required per `invariants.base.md:107`. The
removal direction is why the module-level revert is structurally insufficient here: deleting the
`register()` call leaves `h_mad_wire_registry` intact and all of its own unit tests passing, so only
a wire-scoped revert can observe the difference.

`owning_feature` comes from a new **`--feature` CLI flag** on the 5b gate, not from parsing the
plan's filename. The filename is a convention, not a contract — `h_mad_wire_pin_gate.py` is already
invoked on arbitrary paths (including `/tmp` fixtures throughout its own test suite), so deriving
the feature from it would silently register wires under a stem like `test_plan` or `impl-plan`.
`owning_feature` is the field an operator reads when a wire breaks months later, so a wrong value is
worse than a missing one. When `--feature` is absent the gate registers **nothing** and says so:
the verdict is unaffected (registration is not a gate condition), but a silent skip would make the
registry quietly incomplete, which is the failure this feature exists to remove.

**Code structure**:
```python
# in h_mad_wire_pin_gate.main(), after the verdict is computed and printed:
def _register_wiring_tasks(tasks: list[dict], registry: Path, feature: str) -> int:
    """Build one entry per `wiring` task with a real WIRE/WIRE-PIN and pass them to
    `registry.register(entries, path)` as a SINGLE batch. Returns the count registered.
    Called ONLY on verdict == "PASS"; a non-wiring task registers nothing."""
```

**Acceptance Criteria**:
- [ ] AC-6.1: a passing 5b `wiring` task makes the registry entry appear with no operator action
- [ ] Removal direction: delete the `register()` call with the callee intact ⇒ the WIRE-PIN test fails, while `h_mad_wire_registry`'s own unit tests still pass
- [ ] Unconditional direction: make registration fire for every task regardless of shape ⇒ a fall-through test asserting a `new-behaviour` task registers **nothing** fails
- [ ] `check()`'s signature and the `WIREPIN:` grammar are unchanged — additive only
- [ ] A `WIREPIN: FAIL` run registers nothing
- [ ] Registry parsing is imported from `h_mad_wire_registry`, never re-implemented in the gate; `WIRE`/`WIRE-PIN` parsing stays in the existing `_parse_tasks`
- [ ] A plan with N wiring tasks produces exactly ONE `register()` call carrying N entries, not N calls — asserted by counting calls, so a per-task read-modify-write of the whole JSONL cannot creep back in
- [ ] `owning_feature` is taken from the `--feature` flag; a run without `--feature` registers nothing and reports that it skipped registration, while leaving the `WIREPIN:` verdict unchanged
- [ ] The feature name is never derived from the plan's filename — pinned by running the gate on a `/tmp` fixture path and asserting no wire is registered under the fixture's stem

**Dependencies on other tasks**: Task 1, Task 4 (must complete first)

## Task 6: ast_shape_challenge

**Production file**: `h-mad/scripts/h_mad_wire_registry.py`
**Test file**: `h-mad/tests/test_h_mad_wire_registry.py`
**Task shape**: `new-behaviour`

**Description**: FR-5, warning-only and verdict-neutral by construction, running at **5f** — 5b has
no production diff (HEAD equals BASE) so an AST comparison there could never fire while reporting
`challenges=0` as though it had looked. The changed-file set is
`git diff --name-status --diff-filter=d <base> HEAD -- '*.py'`, run with `cwd=repo` so the `'*.py'`
pathspec resolves from the repo root rather than the caller's working directory, and **filtered to
production paths — test paths are never challenged**. That production filter is not tidiness: a test
file matches no `Production file` claim in any task, so without it every changed test would be
reported as `unattributed` on every run, and the one signal `unattributed` carries (an unclaimed
*production* change) would be buried under noise from files the challenge is defined not to look at.
A file attributed to a `wiring` task is likewise exempt: that task has already declared its
connection and pinned it, so challenging it would re-raise the thing the plan states outright.

**`--diff-filter=d`, not the design's `--diff-filter=AM`** — measured, and it corrects the design.
`d` (lowercase: *exclude* deleted) is exclusion-based, so it keeps the design's actual requirement
(a deleted file must never be parsed, since reading its HEAD version raises `FileNotFoundError` and
crashes the verifier instead of reporting) while not silently dropping every other status. `AM` is
an allowlist and drops renames outright. Probed on a tree carrying all four statuses at once:

```
A pkg/brandnew.py   D pkg/doomed.py   M pkg/keep.py   R073 pkg/tomove.py -> pkg/moved.py

--diff-filter=AM -> brandnew.py, keep.py                      # moved.py silently absent
--diff-filter=d  -> brandnew.py, keep.py, moved.py            # rename kept, deletion still excluded
```

`pkg/moved.py` had *gained a new function* in the same commit, so under `AM` a rename is a free pass:
every cross-boundary call it introduces is invisible to the challenge. The design's own probe only
exercised a deletion (`plain 62 / AM 61 / deletions 1`), which is why the gap survived to here. Every
path `d` returns was confirmed to exist at HEAD, so the `FileNotFoundError` constraint still holds.

**Use `--name-status`, not `--name-only`, and read a renamed file's BASE version from its OLD
path.** Including renames is only half the fix: `--name-only` prints just the *new* path, so
`git_show(base, new_path, repo)` returns `None`, the file reads as brand-new, and **every**
pre-existing cross-boundary call in it is reported as an addition — trading the false negative
above for a false-positive flood on exactly the files that just became visible. `--name-status`
carries both paths, tab-separated, and the BASE read must use the old one. Probed:

```
$ git diff --name-status --diff-filter=d BASE HEAD -- '*.py'
R062<TAB>pkg/tomove.py<TAB>pkg/moved.py

$ git show BASE:pkg/moved.py    fatal: path 'pkg/moved.py' exists on disk, but not in 'BASE'
$ git show BASE:pkg/tomove.py   import json…                       # the real BASE version
```

So each changed file resolves to a `(base_path, head_path)` pair: equal for `A`/`M` (and
`base_path` simply absent at BASE for a true addition), and old→new for `R`. Attribution matches on
`head_path`, since that is what an impl-plan's `Production file` names. Attribution reuses the 5b gate's
existing `_parse_tasks()` rather than re-parsing the document, mapping each changed `.py` to the
task claiming it; both sides are normalised to repo-relative POSIX paths with a suffix-match
fallback, and an unresolvable claim is reported as `unattributed` *and named*, so a systematically
mis-written plan surfaces as a pattern rather than as silent false positives. Boundary resolution
builds a module-name → repo-path index by walking the repo; unresolvable targets (stdlib,
third-party, not in the index) are **skipped, not guessed**, and an ambiguous stem is reported
rather than resolved to the first match. Acknowledgment reuses `h_mad_audit_gate`'s
`## Acknowledged-not-fixed` parser by import — factored out there if not currently exported, never
copied.

**Code structure**:
```python
def changed_files(base: str, repo: Path) -> list[tuple[str | None, str]]:
    """`git diff --name-status --diff-filter=d`, cwd=repo -> [(base_path, head_path)].
    base_path is the OLD path for an `R`, the same path for an `M`, and None for an `A`.

    The caller MUST branch on `base_path is None` and use an empty BASE AST, rather than
    passing it to `git_show(sha, path: str, repo)` — whose `path` is typed `str` and which
    would raise TypeError. `None` here means "no BASE version exists", which is a real and
    common case (every added file), not an error."""

def build_module_index(repo: Path) -> dict[str, list[Path]]:
    """module name (stem, and dotted path where __init__.py chains exist) -> paths."""

def ast_targets(source: str) -> set[str]:
    """Imported module names + the root of each call target. Structure, not text."""

def challenge(base: str, impl_plan: Path, boundaries: Path, ack: Path, repo: Path) -> dict:
    """Return the outcome dict the CLI printer renders — same shape of contract as
    `verify()`; `challenge()` itself prints nothing.

    main() renders it as `WIRECHALLENGE: challenges=N acknowledged=K unattributed=U
    dangling=D stale=S ambiguous=A`, or as
    `WIRECHALLENGE: NOT_COMPARED reason=<no_production_diff|no_boundaries>` when the
    comparison could not be performed at all. Always exit 0 — verdict-neutral either way.

    NOT_COMPARED is a distinct token, not prose: `challenges=0` from a run that looked
    and `challenges=0` from a run that could not look are the same string, and the second
    is exactly the silent no-op this feature exists to remove."""
```

**Acceptance Criteria**:
- [ ] AC-5.1a: an undeclared cross-module call in a `new-behaviour`-shaped task raises a warning naming both the task and the crossing
- [ ] AC-5.1b: a changed file claimed by a `wiring` task raises no challenge
- [ ] AC-5.1c: a changed file claimed by NO task is counted as `unattributed` and named, not dropped
- [ ] AC-5.1e: a *dangling claim* — a task's `Production file` that matches no changed file even after suffix-match normalisation — is counted in its **own** `dangling=D`, never folded into `unattributed=U`. The two are opposite directions (a file nobody claimed vs a claim matching no file) with opposite remedies, and summing them into one number makes both unactionable
- [ ] A renamed-and-modified production file is challenged, not skipped — pinned against a fixture carrying `A`, `M`, `D` and `R` statuses at once, since `--diff-filter=AM` passes every other case while dropping exactly this one
- [ ] A renamed file's BASE version is read from its **old** path, so only genuinely new cross-boundary calls fire — pinned by renaming a file that keeps a pre-existing cross-boundary call and adds one: exactly one challenge is raised, not two. Reading BASE from the new path returns `None` and would flag both
- [ ] AC-5.1d: reindenting or line-wrapping a call site with no semantic change does NOT fire the challenge (AST, not regex)
- [ ] AC-5.2: the warning leaves both the `WIREPIN:` and `WIREREG:` verdicts unchanged, and `challenge` always exits 0
- [ ] AC-5.3a: raised and acknowledged counts are both reported as content
- [ ] AC-5.3b: an acknowledgment naming a challenge that was never raised is counted `stale`
- [ ] AC-5.3c: invoked at a point with no production diff, the challenge prints `WIRECHALLENGE: NOT_COMPARED reason=no_production_diff` — a distinct token, never a bare `challenges=0`, because a run that looked and a run that could not look must not render identically
- [ ] AC-5.4a: boundaries come from `.h-mad/boundaries.json`, never hardcoded
- [ ] AC-5.4b: an absent boundary map means no boundaries, so the challenge never fires — and it says so as `WIRECHALLENGE: NOT_COMPARED reason=no_boundaries` rather than `challenges=0`. Declaring no topology is the correct default for such a repo (per the design), but it must not render identically to a repo that declared boundaries and had none crossed
- [ ] `challenge` without `--base` is exit 2
