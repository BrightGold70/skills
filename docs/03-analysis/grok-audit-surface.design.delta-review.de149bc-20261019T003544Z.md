## Must-fix
- The D11 step-3 positive rule sends a readable, drifted grok log to `UNREADABLE` when the spec needs a smoke FAIL. In `measure_effort` (`h-mad/scripts/h_mad_audit_cycle.py:597-600`), a non-blank log with no agy event, no codex banner and no `_GROK_TYPES` type gets shape `unparseable`, because `scan_grok` returns `None` when `seen` is false (`h-mad/scripts/h_mad_review_evidence.py:366-368`). Its Effort item is `p1 tools=0 ok=0 failed=0 thinking=0 …` (I rendered it with T5). Such a log still passes step 2, since every line is a JSON object with a string `type`. Step 3 then refuses `input_unparseable`, and UNREADABLE outranks FAIL (`test_smoke_unreadable_outranks_fail`). So the AC-1.2 result the smoke exists to produce (`vocab_missing:end,tool_call,tool_call_update`, all three of which must fire when no grok type was seen) never prints. The same holds for a grok log carrying agy-style events (shape `parsed`). The spec reserves UNREADABLE for inputs that "could not be read" and publishes nothing "until the smoke derives again to `PASS` or `FAIL`". A deterministic drift never derives again, so the AC-1.8 smoke-failure branch can never ship. The four new opposed fixtures lock this in: each puts a coherent `f0_text()` log beside a non-grok item, a pairing the wrapper never produces, and asserts UNREADABLE. Possible repairs: (a) step 3 refuses only when the item is absent, or when it is a "wrong file" rendering (`codex-text`, `missing`, `empty`). For `parsed` and `unparseable` items, the FAIL reasons stand, and a fixture built from a real drifted log (JSON typed lines outside `_GROK_TYPES`) asserts `SMOKE: FAIL reason=vocab_missing:end,vocab_missing:tool_call,vocab_missing:tool_call_update`. The residual is a `parsed` item on a log where all three vocabulary types are present. (b) Raise an OPEN-DECISION to add an AC-1.7 reason for "Effort item is not `format=grok`". The spec's list is closed: "There is no other reason value". Either way, the D11 sentence "AC-1.1 is therefore met only by the positive grok item" must name how a non-grok item that is not a wrong file fails the smoke.

- `build-root --reset <abs root>` deletes before any check of its target. D5 builds the expected tree, then removes "every entry of the live root whose root-relative path is absent from the expected tree … whatever its kind", and only after that runs step 6 (content scan, then reach check) on the live root. Nothing checks beforehand that the target is a root this probe built. The runbook passes `--reset "$ROOT"`, with `ROOT` set by hand from the previous block (`ROOT=<path from ROOT: READY>`). In a fresh shell (a resume between S1 cycles), or after a mistyped path, the target becomes `""`, which a `Path` reads as `.`, the repository root. It could also be the work tree or `$HOME`. The reset would then delete every entry not in one document's export, including `.git`, and the reach check would refuse `root_git` only afterwards. Required: a precondition that runs before any removal. Possible forms: (a) the target is absolute, is an existing directory, its basename starts `gas-root-d<k>-s1-` for the same `--doc`, and it sits directly under `tempfile.gettempdir()`; (b) the probe requires `--root-record <file>` and refuses unless the target equals that file's `ROOT: READY path=`; (c) the D7 reach check runs on the target first and refuses `root_git:<path>` before anything is mutated. The precondition needs its own refusal fixture (target = a `git init`ed dir, target = the empty string) and a P-row. The runbook should also use `${ROOT:?}`. I did not check which refusal reason AC-5.4 would accept for (a). `root_git:<path>` fits (c), and `internal:<E>` is always available.
