## Architecture Considerations

**Design obligations.** The spec leaves these to Phase 4. They are listed so the design cannot skip
them. The plan does not settle them.

- **DO-1 — the `TDD-STATE:` line shape (FR-3).** The line must carry everything FR-3 steps 1 and 2
  need, so the hook never reads state or `PATH` itself. Every added field gets a closed value set.
  An unknown value matches no alternative of `STATE_ACTIVE_RE` and refuses `judge-error`.
  The design must also say what happens to every **existing literal of the line** in the tree,
  and its shape must satisfy the placement invariants P-1..P-5 (see DO-1a).
- **DO-1a — the line's existing literals.** The line is a contract with copies outside the judge
  and the hook. Command and reading at `17d73037`:
  `git ls-files -z h-mad | xargs -0 grep -l 'TDD-STATE: active'` → **6 files**:
  `h-mad/hooks/h-mad-tdd-gate.sh`, `h-mad/scripts/h_mad_tdd_judge.py`,
  `h-mad/tests/mutation-specs/claude_gate_judge_wiring.json`, `h-mad/tests/test_h_mad_tdd_gate_fallback_agent.py`,
  `h-mad/tests/test_h_mad_tdd_gate_judge.py` and `h-mad/tests/test_h_mad_tdd_judge.py`. The same
  reading holds at `d90decc6`. `test_h_mad_tdd_gate_judge.py` `_tree_b` stubs the judge's `state`
  verb with an old-shape line as its default. `test_h_mad_tdd_gate_fallback_agent.py` builds stub
  lines from `PREFIX`, **and** it asserts on the judge's real output (P-1, P-2).
  `test_h_mad_tdd_judge.py` pins the line through `ACTIVE_RE`, which is anchored with `$`, and
  through four more assertions (P-3..P-5). v1.1 said the second file held only stubs and that

  **Placement invariants — design constraints on the new line.** Each is an assertion on
  `judge.format_state_line(...)` itself. Located by test name at `d90decc6`
  (`grep -n 'def test_format_state_line_emits\|def test_fold_outcome_round_trips\|def test_fallback_tag\|def test_state_line_escape_and_blocker\|def test_state_line_empty_values\|def test_state_line_path_with_space' h-mad/tests/test_h_mad_tdd_gate_fallback_agent.py h-mad/tests/test_h_mad_tdd_judge.py`):
  - **P-1** (`test_h_mad_tdd_gate_fallback_agent.py` `test_format_state_line_emits_the_fallback_fold`,
    under AC-3.2's byte-identical rule). The line contains ` records=1 fallback=grok:1 record=`,
    so `records=`, `fallback=` and the first ` record=` stay adjacent. The test runs in-process
    with the **ambient** `PATH`, and `agy` is on `PATH` on this machine. So the `fallback=` value
    stays the fold over the records alone. The both-peers-out gating of FR-3 step 3 is applied
    by the hook, from other fields, and is never folded into this value. A
    `grok_wire_reverts.json` mutation row names this test as its `test`.
  - **P-2** (same file, `test_fold_outcome_round_trips_through_the_gate_ere`, byte-identical).
    The hook keeps exactly one line matching `^STATE_ACTIVE_RE='(.*)'$`. Python `re.fullmatch` of
    that literal accepts the judge's line, and `group(4)` equals the fold. The hook matches with
    bash `[[ =~ ]]`, which is POSIX ERE, and ERE has no non-capturing group: at `d90decc6`,
    `bash -c 're="^a(?:b|c)$"; [[ ac =~ $re ]]; echo $?'` prints `2`. So no parenthesised
    group may come before the `fallback=` group, and the literal must mean the same thing to
    Python `re` and to ERE.

  - **P-5** (`test_h_mad_tdd_judge.py` `test_state_line_empty_values_encode_as_percent` and
    `test_state_line_path_with_space_decodes`). After the first ` record=`, comma fields 0, 1 and 2

    by `%%,*`, the file as the third field, and the tag by `##*,`

  **What the invariants leave open.** This was probed at `d90decc6` with a scratch script, since
  deleted, that built one candidate line per placement and checked P-1..P-5 against it:
  - A **per-record field between the state file and the trailing fallback tag** satisfies all
    five, with a capture group of its own.
  - A **header field before `codex-escape=`** satisfies all five only without a capture group
    (a bracket expression, for example). With one, it fails P-2.
  - A **header field between `fallback=<fold>` and the first ` record=`** fails P-1.
  - A **field after the last record** fails P-3.

  per-record, between the state file and the trailing fallback tag. **Do not place a header field

  `git ls-files -z h-mad | xargs -0 grep -l -e 'codex-escape=' -e ' record=' -e 'STATE_ACTIVE_RE' -e 'format_state_line'`.

  located individually, and the assembler copy from its joined `str` constant. The design owes
  those locators. What they must achieve: a mutation of any one copy makes the test fail, which
  no text holding two or more copies can give. The test carries the stage-6 control: one mutation
  row per copy, each changing only that copy and run alone, each failing the check, scored
  `MUTATION: ALL_CAUGHT`. Each row's `find` carries context that makes it unique in its file,
  because the harness refuses a non-unique anchor. The design owes the test's placement, its
  locators and the canonical block's exact text, which must match spec FR-9. Residual: the test
  shows that every copy carries the canonical block. It does not show that a copy carries no
  other, contradicting sentence beside it, or that a seventh surface exists. A seventh surface
  held in a `str` constant or in non-`.py` text is found by re-running the spec's FR-9 sweep (the
  union of the line grep and the joined-literal reading). A surface built at run time is found
  only by reading the code that builds the dispatch text.

**Rule over the class.** A rewrite either keeps each pinned literal, or changes that test's
literal in the same commit to text the rewrite keeps, with the test's assertions otherwise
unchanged. The Task's RED names every pin it moves. A pin is never deleted. A new locator uses a
precedent that fits the target's structure: `titled_section` for an ATX heading, and the
`str.index` slice above for a list item.

- The static wiring check proves the wiring entry exists, not that agy honours it (FR-5 residual).

## Problem

Codex is the only Phase-5 implementer h-mad accepts. The seams that hard-code it are listed here:

- **State.** `h-mad/scripts/h_mad_state_schema.json` declares `codex_status` and `fallback_agent`
  (`grok|claude|null`) and sets `"additionalProperties": false`. Any new key must therefore be
  declared there, or `h_mad_state_write.py` rejects it. (Read with `cat` on the schema.)
- **Claude-side authorship gate.** `h-mad/hooks/h-mad-tdd-gate.sh` refuses Claude's production write
  as `codex-authorship` when `HMAD_CODEX_UNAVAILABLE` is empty, the state line says
  `codex-escape=no`, and `command -v codex` succeeds. Otherwise it folds `fallback_agent` into
  `fallback-grok` / `fallback-invalid`. (`grep -n 'codex-authorship\|fallback-grok' hooks/h-mad-tdd-gate.sh`.)
- **Single state source.** `h-mad/scripts/h_mad_tdd_judge.py` `read_chain` collects every `step5`
  record on the target's `docs/.bkit-memory.json` chain into `Record(key, codex_status, state_file,
  fallback)`. `format_state_line` prints `TDD-STATE: active codex-escape=… blocker=… records=…
  fallback=… record=…`, and the hook parses that line with `STATE_ACTIVE_RE`. The judge's
  `ESCAPE_STATUSES` is `{"unavailable", "exhausted"}`.
- **Staging.** `h-mad/scripts/h_mad_assemble_tdd.py` accepts `--agent` with `choices=("codex",
  "grok")`. The default timeout is 1500 for grok and 900 otherwise. `command_block` derives a
  non-codex first line from the codex line. The test
  `test_prompt_file_is_agent_independent` pins that the prompt bytes do not depend on `--agent`.
- **Prompt.** `h-mad/references/codex-implementer-prompt.md` opens "You are Codex implementing…"
  and its `Hook:` line names only Codex's and Claude's gates. Because that test pins one prompt
  for every agent, grok is told it is Codex today.
- **Write gate.** `h-mad/hooks/h-mad-codex-tdd-gate.py` speaks Codex's hook contract. Its
  `permissionDecision` deny goes out under `hookSpecificOutput`. agy's contract is
  `{"decision": "deny", "reason": …}` on stdout (`h-mad/references/agy-runtime.md` §"Hooks",
  §"The TDD gate"). No agy gate exists, and that section prescribes the halt
  `step5:agy_tdd_hook_unverified` until one is verified against a real refusal.

## Terms

- **Peer**: `codex` or `agy`. **Fallback**: `fallback_agent`, which is `grok`, `claude`, or
  absent/`null` (equivalent to `claude`).
- **Chosen implementer**: the record's `implementer` field. Absent or `null` reads as `codex`.
- **Resolved implementer**: who actually authors Phase 5 for a record. FR-2 defines it.
- **Active step5**: at least one record on the governing state chain has `phase == "step5"`. This
  is the same predicate both existing gates use.

## Requirements

### FR-1 — State fields

Add to `h_mad_state_schema.json`. Every field is OPTIONAL and additive, so `required` does not
change and records written before this feature stay valid:

| field | values | absent means |
|---|---|---|
| `implementer` | `"codex"` \| `"agy"` \| `null` | `codex` |
| `agy_status` | `"available"` \| `"unavailable"` \| `"exhausted"` \| `null` | `available` |
| `implementer_switch` | object `{from, to, reason, ts}` \| `null` | no switch has happened |
| `review_independence` | array of objects `{leg, module, reviewer, implementer, independent}` | nothing recorded |
| `implementation_authors` | array of objects `{module, agent}` (D-15) | no implementation dispatch recorded |

- `implementer_switch.from` and `.to` take `codex|agy|grok|claude`. `.reason` takes one of the
  closed set of switch reasons in FR-2. `.ts` is an ISO-8601 timestamp in the RFC 3339
  `date-time` profile (`YYYY-MM-DDTHH:MM:SS[.fraction]` then `Z` or `±HH:MM`), narrowed to
  seconds `00`–`59` (D-14, below). The form the
  writer already emits, `%Y-%m-%dT%H:%M:%SZ` (`h_mad_state_write.py` `_utc_now`), is one instance.
- **An invalid `.ts` is refused on both validator paths.** The store is validated by
  `jsonschema.Draft7Validator` when it imports and by the bundled `_MiniDraft7` in
  `h_mad_state_validate.py` when it does not. Neither enforces `format` today: at `e7730f78`,
  `{"type":"string","format":"date-time"}` accepts `not-a-date` on both (`Draft7Validator(s).is_valid`
  → `True`, `_MiniDraft7(s).is_valid` → `True`). `_MiniDraft7`'s docstring says it ignores
  `format` on purpose, because the production path supplies no format checker. Declaring
  `"format": "date-time"` on `.ts` therefore enforces nothing, and the requirement is the refusal
  itself: a `.ts` that is not an RFC 3339 `date-time` is refused whichever path runs. That covers
  a non-date string, a date with no time (`2026-10-16`), and a calendar-invalid date
  (`2026-02-30T00:00:00Z`).
  - **A leap second is refused too (D-14).** RFC 3339 admits a seconds field of `60`. This spec
    narrows `.ts` to seconds `00`–`59`: a `.ts` whose seconds field is `60`, with or without a
    fraction and whatever its offset, is refused on both paths like any other invalid value.
    Reason: every `.ts` h-mad writes comes from Python `datetime` through the writer
    (`h_mad_state_write.py` `_utc_now` is `datetime.now(timezone.utc).strftime(...)`), and
    `datetime` cannot hold second 60 (`datetime(2016,12,31,23,59,60)` and
    `datetime.fromisoformat('2016-12-31T23:59:60+00:00')` both raise `ValueError: second must be
    in 0..59`; the message's tail varies by Python version and is not part of this claim). So the narrowing refuses no value the writer can produce. Residual: a
    hand-supplied `.ts` (for example through `--set`) that names a real leap second is refused,
    and that is intended.
  - **Mechanism: a design obligation.** The design picks one and cites the probe output: extend
    `_MiniDraft7` and its differential corpus; or pass a format checker on the library path and
    match it in the bundled one; or check on the writer side before validation. One hazard binds
    every option that uses the library's format checker. `jsonschema` checks `date-time` only when
    the optional `rfc3339-validator` package imports, and otherwise passes the value silently.
    It imports in `/opt/anaconda3/bin/python3`, where `FORMAT_CHECKER` refuses `not-a-date`.
    Stock `/opt/homebrew/bin/python3` has no `jsonschema` at all, so it takes the bundled path.
    A mechanism that leans on that package must show the refusal with the package absent.
  - **Residual.** Three existing fields already declare `"format": "date-time"`: `started_ts`,
    `owner_heartbeat_ts` and `halt_ts` (`grep -n -B3 '"format"' h-mad/scripts/h_mad_state_schema.json`,
    3 matching lines). They stay annotation-only unless the chosen mechanism is schema-wide. If
    it is, it starts refusing invalid values in those fields too. The design must then run
    `classify_store` over the live state files and report every record that changes class
    before the mechanism ships.
- `review_independence[].leg` takes `5e-review|5e-verify|6a-prime`, and `module` is a string or
  `null`. `reviewer` and `implementer` take `codex|agy|grok|claude`. `independent` is a boolean.
- **`implementation_authors` — the durable author record (D-15, operator decision OD-E2 (a)).**
  One entry per accepted implementation dispatch, so FR-7 §"Attribution" can recover a module's
  complete author set after the orchestrator has lost its dispatch context.
  - **Entry schema.** An object with exactly two keys, both required, no others
    (`additionalProperties: false`): `module`, a non-empty string (`minLength: 1`; it is the
    `--module` value the assembler requires), and `agent`, one of `codex|agy|grok|claude`. An
    entry with an agent outside that set, a missing or empty `module`, a missing `agent`, or an
    extra key is refused on both validator paths. Every keyword this uses (`type`, `items`,
    `required`, `additionalProperties`, `enum`, `minLength`) is in `_MiniDraft7`'s supported set
    (its docstring's `Deliberately supports ONLY` paragraph, at `3ad735f7`). The field itself is optional, so a
    record written before this feature, which has no such field, validates unchanged.
  - **Duplicates are allowed and meaningful.** The array is a log, not a set: agy's 5e GREEN and a
    later agy fix dispatch are two entries. The author set of a module is the distinct `agent`
    values of the entries whose `module` equals it; array order is dispatch-acceptance order, so
    the module's last entry names its latest accepted implementation dispatch.
  - **When the orchestrator appends.** On accepting a module's 5e GREEN dispatch, and on accepting
    each later fix dispatch for that module: exactly the dispatches FR-7 §"Which dispatches are
    implementation dispatches" counts. Never on a 5d RED dispatch, and never on a dispatch that
    halted, timed out or was rejected. `agent` is the agent that authored the accepted code:
    `codex` or `agy` for a peer dispatch, `grok` for a `fallback_agent` grok dispatch, and
    `claude` when FR-2 resolves `claude` and Claude writes the code itself (that write is the
    accepted dispatch). The append happens before any review leg of that code runs, so every
    review entry is preceded by the authors it reviews.
  - **Mechanism.** The same Record mechanism as `review_independence` (FR-7 §"Record"): an add
    that never removes or alters an existing entry, validated against this schema before anything
    is written, with a refused add leaving the store unchanged and printing the writer's existing
    refusal. Whatever mechanism the design names for `review_independence` serves both keys.
  - **Failure the caller sees.** A refused append (invalid entry) is the writer's `ERROR:` refusal
    and the store is unchanged; the orchestrator corrects the entry and appends again before any
    review leg of that code. A skipped or lost append leaves the module's author set incomplete,
    which FR-7 handles by its unrecoverable rule, never by guessing.
- `h-mad/references/state-schema.md` gains one row per field, with the same value sets.
- **The existing `fallback_agent` description changes on both surfaces that state it.** Its
  `description` in `h_mad_state_schema.json` ("Who covers Phase-5 authoring when Codex is out. The
  field is read only when codex is out: …") and its `state-schema.md` row ("Optional Phase-5
  author when Codex is out.") are both false after FR-3, which reads the field only when **both**
  peers are out for the record. Both are rewritten to the FR-2 condition, so that each names agy
  beside Codex. (`grep -n 'fallback_agent' h-mad/scripts/h_mad_state_schema.json
  h-mad/references/state-schema.md`.)
  - **Pinned literals.** `test_h_mad_state_fallback_agent.py`
    `test_fallback_agent_description_states_the_four_facts` asserts four substrings of the schema
    description: `read only when codex is out`, `are equivalent`, `HMAD_CODEX_UNAVAILABLE does not
    override` and `prose-enforced`. The rewrite either keeps all four (for example "read only when
    codex is out and agy is out too"), or changes the test in the same commit to the new fact.
    The test must never be deleted to make the rewrite pass.
  - **Residual.** The `fallback-grok` refusal text in `h-mad-tdd-gate.sh` says "while codex is
    out". FR-3 keeps it byte-identical. It stays true, because codex is out whenever the refusal
    fires, but it does not mention agy. That is accepted as the price of byte-identity.
- **The existing `codex_status` description changes on both surfaces that state it, for the same
  reason.** Its `description` in `h_mad_state_schema.json` says a production write in step5 "is
  blocked when Codex is available" and that `exhausted`/`unavailable` records that Codex cannot
  author, "permitting Claude to write the fallback". Its `state-schema.md` row says "An unavailable
  or exhausted status permits a Phase-5 authoring fallback". Under FR-2 both are false when agy is
  available: the declaration moves authorship to agy, and FR-3 refuses Claude. Both are rewritten
  so that authorship is stated as FR-2's resolution (Claude only when `resolved` = `claude`). The
  audit-routing half (consumer 2, the teammate leg) is unchanged, per FR-10. (`grep -n
  'codex_status' h-mad/scripts/h_mad_state_schema.json h-mad/references/state-schema.md`.)
  - **Pinned.** No test pins the `codex_status` description text: at `200ffd52`, `git ls-files
    h-mad/tests | xargs grep -l 'permitting Claude to write the fallback\|permits a Phase-5
    authoring fallback\|One switch, both effects\|blocked when Codex is available'` lists 0 files.
    The zero is load-bearing only for this rewrite; a test added later that quotes the text is
    found by re-running the grep. One test pins the property ORDER:
    `test_fallback_agent_description_states_the_four_facts` asserts `fallback_agent`'s index is
    `codex_status`'s index + 1. The FR-1 fields are therefore never inserted between those two.

**Failure modes.** The schema validates only the values that `h_mad_state_write.py` writes. A
hand-edited record can still hold anything, so the judge treats values as follows:
- An `implementer` value outside `{codex, agy, null}` is `invalid` and refuses fail-closed (FR-3).
- An `agy_status` value outside the escape set reads as `available`. This is today's rule for
  `codex_status`, kept for parity. It fails toward refusing Claude, never toward admitting it.
- `implementer_switch` and `review_independence` are read by `h_mad_phase7_preconditions.py`
  only (FR-7). There a malformed entry is reported as the warning `review_independence_malformed`
  and is never read as `independent=true`.
- `implementation_authors` is read by the orchestrator's FR-7 attribution step only; no script
  reads it. The writer refuses a malformed entry, so one can only come from a hand edit. A field
  that is not an array, or that holds any entry not matching the entry schema, establishes no
  module's author set (a malformed entry's `module` cannot be trusted to say which module it
  belongs to): every module's set is unrecoverable (FR-7), and each leg writes no entry rather
  than one with a guessed `independent`.

### FR-2 — One resolution function, in the judge

`h_mad_tdd_judge.py` gains a single function that resolves a record. `h-mad-tdd-gate.sh` and the
FR-2 CLI verb both read it, and neither re-derives any part of it. For each record R:

- `codex_avail(R)` = `HMAD_CODEX_UNAVAILABLE` empty ∧ `codex` on `PATH` ∧ `R.codex_status ∉ ESCAPE_STATUSES`
- `agy_avail(R)`   = `HMAD_AGY_UNAVAILABLE` empty ∧ `agy` on `PATH` ∧ `R.agy_status ∉ ESCAPE_STATUSES`
- `chosen(R)` is `R.implementer` (absent/`null` → `codex`), and `other(R)` is the other peer.
- `resolved(R)` = `chosen` if `chosen` is available; otherwise `other` if `other` is available;
  otherwise `R.fallback_agent`, where absent, `null` and `claude` all mean `claude`.

The env-var and PATH evaluation moves from the hook into this function. The judge runs as a child
of the hook and inherits its environment, so the inputs are the same ones the hook reads today.

**Switch reasons (closed set).** A switch happens when the resolved author is not the chosen
peer. The reason is the first unavailability cause of the chosen peer, checked in this order:
`env` (`HMAD_<PEER>_UNAVAILABLE` non-empty), `status` (`<peer>_status` in the escape set),
`cli-absent` (not on `PATH`). The set is closed because these three are the only inputs to
`*_avail`. A new availability input must add a reason here.

**CLI verb.** `python3 h_mad_tdd_judge.py implementer --root <root> --feature <feature> [--record]`
prints exactly one line. Read the token, never `$?`. Its values:

| token | meaning | caller does |
|---|---|---|
| `TDD-IMPLEMENTER: <codex\|agy> chosen=<peer> switch=none` | chosen peer is available | stage `--agent <codex\|agy>` |
| `TDD-IMPLEMENTER: <codex\|agy> chosen=<peer> switch=<peer>-><peer> reason=<env\|status\|cli-absent>` | automatic peer switch | stage the resolved peer; print the line on the dispatch |
| `TDD-IMPLEMENTER: <grok\|claude> chosen=<peer> switch=peers-out reason=<chosen peer's reason>` | both peers out | today's fallback path, unchanged |
| `TDD-IMPLEMENTER: invalid field=<implementer\|fallback_agent> value=<pct-encoded>` | record holds an invalid value | halt `step5:implementer_invalid`; fix the record; never dispatch |
| `TDD-IMPLEMENTER: no-record feature=<pct-encoded>` | no such feature in the state file | halt `step5:implementer_unresolved`; the feature name or root is wrong |
| `TDD-IMPLEMENTER: unreadable file=<pct-encoded> error=<name>` | state file cannot be read | halt `step5:implementer_unresolved`, same as the gate's unreadable state |

**Halts (v1.10, adopted from impl-plan v1.1 Task 16).** The verb's caller has exactly three halts,
one per failure class of the token above: `step5:implementer_invalid` (an `invalid` token: the
record is wrong and a human fixes it), `step5:implementer_unresolved` (a `no-record` or
`unreadable` token: the verb could not reach a record), and `step5:implementer_switch_unrecorded`
(any token with ` record=failed`, below). The three tokens that name a peer (`switch=none`, a peer switch,
`peers-out`) halt nothing. Residual: `failure-recovery.md` gains no row for any of the three
halts in this feature (impl-plan v1.1 adds none); a recovery row for them is owed to a later
feature, not settled here.

With `--record`, any `switch` other than `none` writes `implementer_switch` to the record through
`h_mad_state_write.py`'s write path, so the claim and session rules apply. The write is skipped
when the stored value already has the same `from`, `to` and `reason`, which keeps re-staging
idempotent. A failed write prints the token with ` record=failed` appended. The caller halts
`step5:implementer_switch_unrecorded`, because a switch that is not in state is exactly the
silent switch the operator decision forbids.

`h_mad_assemble_tdd.py` remains state-independent (`test_state_fallback_agent_is_not_read` stays
green). The orchestrator runs the verb and passes the result as `--agent`.

### FR-3 — Claude-side authorship gate

`h-mad-tdd-gate.sh` folds every `step5` record on the chain, as it does today. Precedence is
first match wins:

1. Any record with an invalid `implementer` refuses as kind **`implementer-invalid`**, naming
   the record's key and file and the `--set implementer=codex|agy|null` remedy.
2. The first record, in chain order, whose `resolved` is a peer refuses as
   **`codex-authorship`** when that peer is `codex` and **`agy-authorship`** when it is `agy`.
   Each message names the dispatch (`hmad-dispatch exec <peer> <promptfile>`), the
   `--set <peer>_status=exhausted` declaration, and the `HMAD_<PEER>_UNAVAILABLE=1` one-off escape.
3. Otherwise, today's `fallback_agent` fold applies unchanged (`fallback-invalid` outranks
   `fallback-grok`; absent/`null`/`claude` everywhere lets Claude proceed to the judge).

**Compatibility, stated exactly.**
- The `codex-authorship` message text is byte-identical to today's.
- The `fallback-grok` and `fallback-invalid` message texts are byte-identical to today's.
- Their trigger conditions change in one deliberate way: they now fire only when **both** peers
  are unavailable for the record (operator decision, 2026-10-16).
- Consequence: on a machine with `agy` on `PATH`, `codex_status=exhausted` used to admit Claude
  or route to grok. It now refuses with `agy-authorship`.
- Existing fixtures that build their own `PATH` without `agy` keep their outcomes. Example:
  `h-mad/tests/test_h_mad_tdd_gate_fallback_agent.py` puts `bin_dir:/usr/bin:/bin` on `PATH`, and its
  `codex`-absent assertion runs on that path.

The refusal kinds the gate can emit after this feature are `implementer-invalid`,
`codex-authorship`, `agy-authorship`, `fallback-invalid` and `fallback-grok`, plus the judge's
DENY kinds (the `KINDS` set in `h_mad_tdd_judge.py`, minus `red-measured`). `judge-error` is one
of those DENY kinds. All of them go out in the existing `permissionDecision: deny` JSON form with
exit 0.

The `TDD-STATE:` line is a contract between the judge and the hook. It must carry everything
step 1 and step 2 need, so the hook never reads state or `PATH` itself. Its exact shape is the
design's choice. Every added field gets a closed value set, and an unknown value matches no
alternative of `STATE_ACTIVE_RE`, so it refuses as `judge-error`.

**A field that is missing is not an admitting value.** A line that lacks a field steps 1 or 2
need refuses `judge-error`, like an unknown value. That covers a line in today's shape. It is the
rule the tree already holds for the `fallback=` field:
`test_h_mad_tdd_gate_fallback_agent.py` `test_state_stub_fallback_field_is_judge_error[missing-field]`
asserts `judge-error` for a line that omits it. Reading a missing peer field as "no peer
resolved" would let a judge that stops emitting it admit Claude silently. So the design may not
keep old-shape lines passing by making the new fields optional.

**Consequence for the existing stub-line fixtures (the AC-3.2 exception).** Two gate test files
stub the judge's `state` verb with a `TDD-STATE: active` literal in today's shape:
- `test_h_mad_tdd_gate_judge.py`: the `_tree_b` default `state_line`;
- `test_h_mad_tdd_gate_fallback_agent.py`: the `PREFIX` and `RECORD` constants that its
  `_stub_outcome` lines are built from.

(`git ls-files h-mad/tests | grep 'test_h_mad_tdd_gate_.*\.py$' | xargs grep -l 'TDD-STATE: active'`
finds those two files at `17d73037`.) Under the rule above, those literals would refuse
`judge-error`. So they are re-shaped to the new line. The permitted edit is exactly this: the
text of a string literal that stubs a `TDD-STATE: active` line, plus the minimum code that
composes one, such as a constant that the line is concatenated from. Each re-shaped stub must
carry values for the new fields that reach the outcome the test already asserts. The following
stay byte-identical: every assertion, every expected kind and reason substring, every test name
and every parametrisation id. A test whose asserted outcome cannot be reached by some new-shape
line is a contradiction for the design to report. It is never a licence to change the assertion.

Two other copies of the line are outside AC-3.2, and they follow the line:
- `test_h_mad_tdd_judge.py` `ACTIVE_RE` is a `$`-anchored copy of the grammar. It is updated to
  the new grammar in the same commit, and its existing assertions keep their meaning.
- The mutation rows that quote the line in their `find` or `replace` are re-anchored in the same
  commit, and they gate on `MUTATION: ALL_CAUGHT`.

**Assertions over the real line constrain where new fields go.** Some existing tests run the
real `judge.format_state_line` in-process and assert its output. They are not stubs, so neither
the AC-3.2 exception nor the `ACTIVE_RE` update covers them, and they stay byte-identical:
- in `test_h_mad_tdd_gate_fallback_agent.py` (AC-3.2's byte-identical assertions):
  - `test_format_state_line_emits_the_fallback_fold` asserts the substring
    `" records=1 fallback=grok:1 record="`;
  - `test_fold_outcome_round_trips_through_the_gate_ere` requires `STATE_ACTIVE_RE` to fullmatch
    the real line and its `group(4)` to equal the fold;
- in `test_h_mad_tdd_judge.py`, outside `ACTIVE_RE`:
  - `test_fallback_tag` asserts `line.rsplit(",", 1)[1]` equals the fallback wire tag;
  - `test_state_line_escape_and_blocker` asserts the substring
    `codex-escape=… blocker=… records=N`;
  - `test_state_line_empty_values_encode_as_percent` and `test_state_line_path_with_space_decodes`
    index `line.split(" record=", 1)[1].split(",")` at 0, 1 and 2.

These permit a new-shape line, so FR-3 does not contradict them. They constrain it as follows,
and the design fixes the exact shape inside these limits:
- the header from `codex-escape=` to the first ` record=` stays contiguous. The two substring
  pins cover `codex-escape=… blocker=… records=N` and ` records=1 fallback=grok:1 record=`, so
  no field fits between any two of them. That rules out the slot after `fallback=<fold>` too. The
  only header slot left is between `active ` and `codex-escape=`, and an alternation there adds a
  capture group in front of `group(4)`;
- within a record, the first three comma fields (key, codex status, state file) and the fallback
  tag as the line's last comma token keep their positions. A per-record field between the third
  field and the tag is clear of every pin above;
- `format_state_line` still emits the fallback fold whatever `agy`'s availability is. Both
  `test_h_mad_tdd_gate_fallback_agent.py` tests run with the ambient `PATH`;
- `STATE_ACTIVE_RE` is POSIX ERE (bash `=~`), which has no non-capturing group. So any new
  capture group goes after the fallback capture, or `group(4)` moves.

A design that cannot meet these is a contradiction it must report. It is not a licence to edit
the assertions.

### FR-4 — agy write gate (`h-mad/hooks/h-mad-agy-tdd-gate.py`)

A new PreToolUse handler that speaks agy's contract and reuses the judge (`read_chain`, `judge`)
and the target-identity module that both existing gates use.

**Payload in, decision out.** It reads the camelCase JSON on stdin (`toolCall.name`,
`toolCall.args`, `workspacePaths`, `artifactDirectoryPath`). It prints exactly one JSON object
on stdout, either `{"decision": "allow"}` or `{"decision": "deny", "reason": "<text> kind=<kind>"}`,
and exits 0. An internal exception produces `deny` with `kind=judge-error` whenever the payload
names a tool in classes (b)–(d) below. Stdout that is not JSON blocks nothing in agy, so
**no path may exit without printing**.

**Every deny carries a kind (S1, v1.8).** Rule over the axis of deny paths: every path that
prints `deny` ends its `reason` with exactly one `kind=<kind>`, and `<kind>` is a member of one
closed list that the design enumerates (design §"FR-4"). This spec owns three sources of members
and names no others: `judge-error` (fail-closed: an exception, an unreadable or unresolvable
input, a missing path), `tool-not-admitted` (class (d)), and the kind the judge returns when
`judge` does not allow (the `kind` of its `Verdict`, passed through unchanged). Any further
member — for example a kind for an out-of-root target, the shell-allowance file, or a refused
shell command — is the design's to name; it must be in the design's list, not invented at a call
site. A deny with no `kind=` token, or with a kind outside the list, is a defect, and AC-4.2 pins
it. This is a deliberate difference from the Codex gate: at `cff71b49`, 6 of the 13 `_deny(`
call sites in `h-mad/hooks/h-mad-codex-tdd-gate.py` carry no `kind=` token (counted by parsing
each call's argument text, the `def _deny` line excluded). The agy gate does not inherit those
kindless denies.

**The activity reading (S4/E1, v1.8).** The gate decides "active step5" (§"Terms") in two
layers, as the Codex gate does. The first is a root-wide scan, the Codex gate's three-valued
`_any_phase5_status(root)`: `active` when any `docs/.bkit-memory.json` under the root has a record
with `phase == "step5"`; otherwise `unknown` when at least one cannot be read, is not JSON, or has
a non-object `orchestrator_state`; otherwise `inactive`. **Every deny this FR attaches to active
step5 also fires when the scan reads `unknown`**; only `inactive` stands it down. That covers the
`workspacePaths` cross-check, the class-(b) path-key and target denies, class (c) and class (d).
The second layer is the §"Terms" predicate itself: `inactive` does not prove the chain inactive
(the scan's `rglob` skips a directory it cannot search), so a class-(b) production `.py` target is
read through `read_chain` whatever the scan reads, and an `unreadable` chain denies
`kind=judge-error` and an `active` one sends the target to the judge. Residual: a state file that
neither the scan nor the target's chain reaches is invisible to the gate, as it is to the Codex
gate.

**Project root.** The gate is wired per project (FR-5, decision D-2), and agy runs a handler with
its working directory set to the directory that holds `hooks.json`. The root is therefore
`git -C <handler cwd>/.. rev-parse --show-toplevel`, canonicalised the same way the Codex gate
canonicalises its root. `workspacePaths` is a cross-check only. When `workspacePaths` is present
and none of its entries resolves inside the root, the gate denies with `kind=judge-error` when the
scan (above) reads `active` or `unknown`, and stands down when it reads `inactive`. This closes the payload-cwd open question: the root never
depends on a payload field.

**Tool classes.** The matcher is `*`, so every tool reaches the gate. With the scan reading `inactive`, every
tool is allowed except a class-(b) production `.py` target, whose chain is still read (above).
With it `active` or `unknown`:

| class | members | rule |
|---|---|---|
| (a) read-only | an explicit allowlist (`view_file`, `list_dir`, `grep_search`, `find_by_name`, `command_status`, …; the design fixes the list) | allow |
| (b) path-write | `write_to_file`, `replace_file_content`, `multi_replace_file_content`, `sed_file`, `notebook_edit` | resolve each target; judge it with the same rules as the Codex gate (production `.py` → test-first judge; test/doc/config paths and the `docs/` first-component rule → allow; out-of-root → deny, except a non-`.py` under `/tmp` and a non-`.py` under the payload's `artifactDirectoryPath`) |
| (c) shell | `run_command` | the Codex gate's shell policy (FR-6) |
| (d) everything else | every tool not in (a)–(c), including tools added in later agy versions | deny, `kind=tool-not-admitted` |

**Deliberate differences from the Codex gate (S4, v1.8: all adopted; item 6 added v1.10, D-16).** Class (b)'s "same rules
as the Codex gate" holds except for exactly these, which design §"FR-4" lists under the same
name. Each fails toward refusal or is forced by agy's payload:
1. A relative path resolves against the root, never a payload cwd. Forced: agy sends none.
2. The out-of-root allowance admits a non-`.py` under `artifactDirectoryPath` as well as `/tmp`.
   Forced: agy writes its artifacts there (the table above already says so).
3. The out-of-root `.py` test checks every same-directory name of the target, where the Codex
   gate checks only the spelled path's resolved name. Toward refusal: the agy refusal set
   contains the Codex one.
4. A root that cannot be canonicalised denies `kind=judge-error` whatever the scan would read;
   the Codex gate allows when its scan reads `inactive`. Toward refusal.
5. Every deny carries a kind (above); the Codex gate has kindless denies. Toward legibility; it
   changes no decision.
6. A class-(b) target that names an existing directory (`.`, `src/`, the root itself, or a
   symlink to a directory) denies `kind=judge-error` when the scan reads `active` or `unknown`,
   and is allowed when it reads `inactive` (D-16, OD-2). Toward refusal: without it such a target
   carries no file name to judge and is allowed under `active`. Residual: a path ending in `/`
   that names no existing directory is not a directory target under this rule; it is judged as a
   file name by the remaining class-(b) rules.
Residual: a rule the Codex gate gains later is not inherited, because each gate writes its own
composition. The target differential test (AC-4.1) is what catches that drift. A difference not
in this list is a defect in whichever gate it appears in.

Class (d) closes the class over agy's tool inventory, which is open-ended and changes between
versions. The inventory observed in
`docs/03-analysis/probes/multi-host-runtime/rehearsal/live-agy-2026-10-01.log` (the `init.tools`
array) already holds write-capable tools beyond the four that §"Hooks" lists: `sed_file`,
`notebook_edit`, `notebook_execution`, `send_command_input` and `call_mcp_tool`. A matcher written
as a list of names would have missed them.

**Target keys.** `write_to_file` carries its path as `TargetFile`, observed in agy's stream-json
`tool_info.parameters` (`docs/03-analysis/probes/multi-host-runtime/rehearsal/agy-G7-tool-write-then-link-read.log`).
The key in the hook payload's `toolCall.args`, and the keys of the other four path-write tools,

a non-empty string (`""`, `null`, a number) counts as no path key (E5); `""` is never
canonicalised to the root.

**Hook timeout.** agy's default handler timeout is 30 s

the floor moves when the budget does.

### FR-5 — Wiring, and the check that gates on it

- **Where.** In the project's `.agents/hooks.json`, under the hook name `h-mad-agy-tdd-gate`,
  event `PreToolUse`, matcher `*`. The command is
  `python3 ~/.gemini/config/skills/h-mad/hooks/h-mad-agy-tdd-gate.py`, where `~` is expanded by
  agy per hooks.md, and the timeout follows FR-4. This mirrors how HemaSuite wires the Codex gate
  in its tracked `.codex/hooks.json`, with a home-relative skill path and no checkout path.
- **Check.** A wiring check prints exactly one line. Read the token, never `$?`. The design names
  the script; extending `h_mad_hook_wiring.py` is preferred.

| token | meaning |
|---|---|
| `AGY-GATE: WIRED` | entry present, matcher `*` or `""`, command names the installed gate, timeout ≥ floor, gate `--self-check` passes |
| `AGY-GATE: UNWIRED reason=<no-hooks-file\|no-entry\|disabled\|matcher-narrow\|bad-command\|timeout-below-floor\|self-check-failed>` | one named defect; the first one found, in this order |
| `AGY-GATE: UNREADABLE file=<pct-encoded> error=<name>` | `hooks.json` is not readable JSON |

- **Enforcement.** `h_mad_assemble_tdd.py --agent agy` runs the check. On anything but `WIRED`,
  it writes no prompt and prints `ASSEMBLE-TDD: HALT agy_tdd_hook_unverified` followed by the
  check's line. The orchestrator then halts `step5:agy_tdd_hook_unverified`, the token
  `agy-runtime.md` §"The TDD gate" already prescribes.
- **Exit codes: a verdict exits 0, and only an operational error exits nonzero.** This follows
  `h-mad/invariants.base.md` §"Audit-gate signal discipline". A nonzero exit registers as a
  tool failure, so it may not carry a normal FAIL. The caller always reads the token, and the
  exit code only says whether a verdict was reached.

  | check line | check exits | assembler prints | assembler exits | kind |
  |---|---|---|---|---|
  | `AGY-GATE: WIRED` | 0 | writes the prompt and prints `ASSEMBLE-TDD: PASS …` | 0 | verdict, pass |
  | `AGY-GATE: UNWIRED reason=<any of the seven>` | 0 | `ASSEMBLE-TDD: HALT agy_tdd_hook_unverified`, then the check line | 0 | verdict, fail |
  | `AGY-GATE: UNREADABLE file=… error=…` | 2 | `ASSEMBLE-TDD: HALT agy_tdd_hook_unverified`, then the check line | 2 | operational: `hooks.json` exists and cannot be read as JSON |
  | no line, or a line with no `AGY-GATE:` token (the check crashed or could not start) | nonzero, or 0 with no token | `ASSEMBLE-TDD: HALT agy_tdd_hook_unverified check=no-token` | 2 | operational |

  - Every `UNWIRED` reason is a verdict, `no-hooks-file` included. The check was able to read
    the project and found the file missing. D-10's residual expects that state in any worktree
    that lacks the file, so it is a normal FAIL. Precedent that goes the other way:
    `h_mad_hook_wiring.py` exits 2 on `WIRING: UNKNOWN reason=no_settings`. The agy check
    differs on purpose, because there a missing file is the defect being reported.
  - `self-check-failed` is a verdict. The gate ran and its self-check failed.
  - **The gate's own `--self-check` follows the same rule (v1.10, orchestrator decision).** It
    prints exactly one token line on stdout. A normal `FAIL` verdict (a self-test of the gate's
    classification or shell policy came out wrong) prints its `FAIL` token and exits 0; only an
    operational error (the gate cannot run: an import it needs fails, or `JUDGE_BUDGET_S` cannot
    be read) exits nonzero. The design and impl-plan name the tokens. The wiring check reads
    `self-check-failed` on anything but the PASS token with exit 0, so the exit code changes no
    wiring verdict. The same decision corrects the Codex gate's pre-existing `--self-check`
    `FAIL shell-policy` branch, which at `84ec2133` prints to stderr and returns 2: it prints its
    token on stdout and exits 0 (impl-plan Task 4). Residual: the Codex gate's
    `FAIL parser` branch (stderr, return 2 at `84ec2133`) is not reached by that decision and is
    unchanged and unclassified here.
  - In every row the orchestrator's halt is the same, `step5:agy_tdd_hook_unverified`. The exit
    code never changes what the caller does. It only keeps a normal refusal out of the tool-failure
    channel.
  - **Residual.** `h_mad_assemble_tdd.py`'s docstring says "exit 0 on PASS, 2 on any HALT", and
    its existing HALT reasons exit 2. Those reasons are out of scope and keep exit 2. Nobody has
    classified them as verdict or operational, and that is owed to a later feature, not settled
    here. After this feature the docstring's "2 on any HALT" is false, so it is rewritten to say
    that the `agy_tdd_hook_unverified` verdict row exits 0.
- **Residual.** The check is static. It proves the entry exists, not that agy honours it. The
  live proof is the tracer's real refusal (FR-8). If a later agy version changes the contract,
  the check still reads `WIRED` until a live refusal fails, and that is stated in SKILL.md as the
  re-run trigger: re-run the FR-8 refusal step and the FR-8 forced-timeout step after any agy
  upgrade.

### FR-7 — Non-independent review flag

- **Rule over the axis.** A code-review leg is flagged non-independent when its reviewer agent
  equals the implementer of the code it reviews. The legs are 5e spec review, 5e anti-gaming
  verification and 6a-prime. Phase 3/4/5b audits review documents, not code, and are not legs.
  The rule covers every implementer, Codex included: a Codex reviewer on Codex-written code (for
  example the 5e anti-gaming verifier dispatched to Codex) is flagged exactly as agy on agy is
  (operator decision D-9). The flag is a warning, never a block.
- **Attribution: the implementer is the author of the reviewed code.** An entry's `implementer` is
  the agent whose successful implementation dispatch produced the code the leg reviews, as
  recorded for that dispatch in FR-1's `implementation_authors` (D-15). It is never read from `implementer_switch.to` or from the `implementer` field,
  which record routing, not authorship. `implementer_switch` is historical: Codex out → agy
  dispatched → switch stored; Codex back → Codex dispatched with `switch=none`, and the stored
  `.to` still says `agy`. Attributing from it would mark a Codex reviewer of Codex-written code as
  independent. When the reviewed code came from more than one agent's dispatch, `independent` is
  `false` if the reviewer is any of them, and `implementer` names that agent.
  - **Which dispatches are implementation dispatches (E4, v1.8).** A module's authors are the
    agents of its accepted 5e GREEN dispatch and of every later fix dispatch for that module the
    orchestrator accepted. A 5d RED dispatch is never an implementation dispatch (it writes tests,
    not the reviewed code), and a dispatch that halted, timed out or was rejected authored nothing.
    The 5d/5e assignment is SKILL.md §"Phase 5 (Implementation) sub-steps"'s (`5d` RED, `5e` GREEN); if that numbering moves,
    the rule follows the GREEN and fix dispatches, not the step number.
  - **The reviewer is none of the authors (S5, v1.8: adopted from design v1.1).** `independent` is
    `true` and `implementer` names the author of the module's latest accepted implementation
    dispatch. Reason: the schema holds one agent, the choice changes no `independent` value, and
    "latest" is decidable from `implementation_authors`' array order (D-15).
  - **The author set is complete, never a projection (E2, v1.8; source fixed by D-15, v1.9).**
    The orchestrator reads a module's author set from FR-1's `implementation_authors`: the
    distinct `agent` values of the entries whose `module` equals it, and "latest accepted
    implementation dispatch" is that module's last entry in array order. It reads the field on
    every leg, with or without its dispatch context, so a resumed 6a-prime leg recovers the same
    set a 5e leg used. It never rebuilds the set from earlier `review_independence` entries: a
    module written by agy and then fixed by Codex, reviewed at 5e by grok and verified by Codex,
    stores `implementer=codex` in both 5e entries, and an agy 6a-prime reviewer would then read as
    independent.
  - **When the set is unrecoverable, the leg writes no entry for that module** rather than an
    `independent=true` one. The cases, closed:
    - **Field absent.** Expected only for a feature whose implementation dispatches were accepted
      before `implementation_authors` existed.
    - **Field present, no entry for the module.** For a feature recorded after the field existed,
      this is a skipped or lost append (FR-1), a defect of the record step, not an expected
      state; the outcome is the same.
    - **Field malformed** per FR-1 §"Failure modes".

    The record cannot tell the first two apart, for the reason D-11 gives: the only signal is the
    absence itself. Residual: `review_independence_unrecorded` fires only when no `leg=6a-prime`
    entry exists at all, so one module missing among several recorded ones has no warning of its
    own, like a missing 5e entry (§"Record").
- **Record.** After each leg, the orchestrator adds one `review_independence` entry (FR-1) to the
  record through `h_mad_state_write.py`'s write path, so the claim and session rules apply. No
  verdict word changes, and `h_mad_extract_verdict.py` output is untouched (it prints only
  `<KEY>: <VALUE>`). The same mechanism adds each `implementation_authors` entry (FR-1, D-15);
  every requirement below applies to both keys.
  - **The writer has no append today.** `--set KEY=VALUE` JSON-decodes VALUE and replaces the
    whole value (`grep -n '"--set"' -A 6 h-mad/scripts/h_mad_state_write.py`). Adding an entry
    with `--set` is therefore a hand read-modify-write of the whole array, and it drops every
    earlier entry the caller fails to carry.
  - **Requirement.** Adding an entry never removes or alters an existing one. It is validated
    against FR-1 before anything is written. A refused add leaves the store unchanged and prints
    the writer's existing refusal. The design names the mechanism, and this spec does not choose
    it. The preferred mechanism is a writer operation that appends one entry. A read-modify-write
    procedure is acceptable only if it states how it detects an entry lost between the read and
    the write.
  - **Failure the caller sees.** A failed add is a missing record. FR-7's `unrecorded` warning
    surfaces a missing `6a-prime` entry at Phase 7. A missing 5e entry has no warning of its own,
    and that is the stated residual.
- **Surface.** `h_mad_phase7_preconditions.py` emits, as warnings (never blockers):
  - `review_non_independent` for each entry with `independent=false`, naming leg, module and agent;
  - `review_independence_unrecorded` for every implementer (`codex|agy|grok|claude`, the
    `implementer` field and `implementer_switch` alike) when a 6a-prime leg ran — `archreview` is
    `READY_TO_MERGE`, `WITH_FIXES` or `NO` — and there is no `review_independence` entry with
    `leg=6a-prime` (operator decision D-11). "Not recorded" must not read as "independent": without
    the warning, a skipped record would hide a Codex-on-Codex self-review. The other `archreview`
    values already surface on their own and add no `unrecorded` warning: absent or unrecognised is
    the blocker `archreview_not_run`, `SKIPPED_NO_PANE` the blocker `archreview_skipped`, and
    `SKIPPED_OPERATOR_OVERRIDE` the warning `archreview_overridden` — in none of them did a
    6a-prime leg run, so there is nothing to record.
  - **Features that predate this field.** The check applies to every feature whose Phase-7 check
    runs after this ships, with no grandfather rule (D-11). An archived feature is unaffected: the
    only code callers of `h_mad_phase7_preconditions.py` are its own CLI and its tests, so nothing
    re-runs it over closed features. A feature in flight whose 6a-prime ran before the field
    existed reaches Phase 7 with the warning; the orchestrator either adds the missing entry by
    the **Record** mechanism above, from the 6a-prime dispatch log, or carries the warning into the
    report.
  - `review_independence_malformed` per FR-1.

  The CLI prints each one as a `WARNING <code>: …` line, the form it already uses for every
  warning. FR-10 makes the Phase-7 report carry them.

### FR-8 — Live tracer, and the timeout it measures

One real task is staged with `--agent agy` and dispatched headless through
`hmad-dispatch exec agy`. Every reading goes to a committed probe under
`docs/03-analysis/probes/agy-coder-fallback/`, stamped with the sha and with `agy --version`.
- **Version.** This spec fixes no agy version. At `200ffd52`, `agy --version` prints `1.4.0`
  (earlier readings in this feature saw `1.3.6`). Each FR-8 reading stamps the version it ran
  against, and a reading taken under a different version than the gate's other readings is
  re-taken, never carried.
- **When it runs (D-13, operator decision on the design's OQ-B).** FR-8 is a post-merge stage: it
  runs after Phase 7's integrate, against the gate installed from main, and the feature is recorded
  COMPLETE only after the stage passes. Until then the feature is not COMPLETE, and
  `step5:agy_tdd_hook_unverified` stands.

1. **Payload capture.** A temporary capture hook records one real `toolCall` per class-(b) tool
   and per `run_command`. It establishes the arg keys FR-4 leaves open, and whether `workspacePaths`
   is present. The capture hook is removed after use (probe-then-delete), and the probe records
   that it was removed.
2. **Real refusal.** With the operator's real global `~/.gemini/config/hooks.json` loaded (it
   carries the `orca-status` `PreToolUse` `*` hook, which prints `{"decision":"ask"}`), agy is
   told to write a production `.py` with no failing test during active step5.
   - **Pass:** the file does not exist afterwards, and the stream-json log shows the gate's
     reason.
   - This step settles two unknowns: how agy combines a `deny` with a sibling `ask`, and whether
     agy requires workspace trust for `.agents/hooks.json`. It does not settle what agy does when
     a handler times out. An ordinary deny returns well inside the deadline, so no handler times
     out on this step. Step 2a settles that.
   - Until it passes, `step5:agy_tdd_hook_unverified` stands.

2a. **Forced handler timeout.** A temporary delay hook goes in the same project `.agents/hooks.json`
   slot, event `PreToolUse`, matcher `*`. Its `"timeout"` is set to a short value T. It sleeps
   for at least 2T, then prints `{"decision": "deny", "reason": "probe-timeout"}`. The task goes
   through the same transport, `hmad-dispatch exec agy`, and tells agy to write one named non-test
   file under the root. The probe records three readings, each one observed and none inferred
   from the others: whether that file exists afterwards; the wall time from the tool call to
   agy's next event, from the stream-json log; and agy's runtime message for the call. The
   outcome is exactly one of these:

   | outcome | file afterwards | wall time | what it means | what follows |
   |---|---|---|---|---|
   | `timeout-blocks` | absent | ≈ T | agy treats a late handler as a block | the write guarantee holds when the gate overruns its timeout |
   | `timeout-allows` | present | ≈ T | agy proceeds on a late handler (fail-open) | the write guarantee rests on the gate finishing within its timeout. FR-4's floor becomes load-bearing for safety, not only for liveness. This is recorded as a residual in `agy-runtime.md` §"The TDD gate" and raised to the operator as an open question before the gate is called verified. |
   | `timeout-not-enforced` | absent | ≥ 2T | agy waited and honoured the late `deny` | the configured timeout is not a deadline. Record it; FR-4's floor no longer bounds a write's latency. |
   | `session-error` | either | any | agy aborted the call or the session | record the message. The outcome is unclassified and the step is re-run, never read as a pass. |

   - The delay hook is removed after use (probe-then-delete), and the probe records that it was
     removed and that `.agents/hooks.json` is byte-identical to its pre-probe content.
   - The real gate is never slowed for this step. A delay inside `h-mad-agy-tdd-gate.py` would be
     a code path that ships.
   - Until the outcome is recorded, agy's handler-timeout behaviour is **unverified**. No
     document may describe it as settled.
3. **RED then GREEN** on the task.
   - Read `STATUS:` with `h_mad_extract_verdict.py`.
   - Run the independent scoped re-run, the revert test (`git stash push -u`) and the mutation
     pass exactly as for Codex.
   - Check where files landed: every write under the `--cd` root, and no `.py` outside it.
   - The verdict line is a claim. The tree delta and the re-run are the evidence.
4. **Timeout.** Until the tracer runs, `--agent agy` defaults to **1500 s**, the value grok
   uses, because grok is the other implementer whose turn length has not been measured. The tracer
   records the wall time of its RED and of its GREEN dispatch. The default then becomes
   `max(900, 3 × the slower of the two)`, rounded up to a multiple of 60. The derived value names
   its readings in the probe, so a re-measurement moves it. An explicit `--timeout` always wins,
   as it does for grok.

  even though it is one at this sha. The axis is "text in a `.py` file that is not a `str` constant".
  It has three members, and each one is handled:

    consecutive `#` lines is seen only when the comment text is joined. So the sweep also reads
    each `.py` file's comment tokens (`tokenize`, with the `#` stripped), joined and
    whitespace-collapsed.

    with a count (`unparsed=N`), its line-grep and comment readings still apply, and a nonzero
    count means the file is read by hand before the sweep counts as clean.
  - **Bytes literals** (`b"…"`) are not `str` constants. The line grep covers them on one line.
    A bytes literal split across lines is the residual of this axis.

  hook was removed and that `.agents/hooks.json` matches its pre-probe bytes. A `session-error`
  outcome does not satisfy this AC. If the outcome is `timeout-allows`, `agy-runtime.md` §"The TDD
  gate" carries the fail-open residual, and the operator question is raised before the gate is
  called verified.
- **AC-9.1:** The prompt contains no implementer-specific opening. `test_prompt_file_is_agent_independent`
  covers `codex`, `grok` and `agy`. The new-caller rule appears in RED item 1, in the WIRE-PIN
  paragraph, in the GREEN variant, in the SKILL.md 5d halt text, in the `failure-recovery.md`
  `step5d:red_wrong_reason:<module>` row and in the wiring-task header that `h_mad_assemble_tdd.py`
  emits. `test_h_mad_wiring_task_shape_docs.py`, `test_h_mad_agent_definitions.py` and
  `test_h_mad_assemble_tdd.py` stay green. FR-9's sweep, re-run on the shipped tree, hits no file
  that states the rule without the carve-out. The sweep is the union FR-9 defines: the line grep
  over every tracked file and the joined reading, which takes in `.py` comment text. The re-run
  reports `unparsed=N`. A nonzero `N` does not satisfy this AC until each unparsed file has been
  read by hand.
- **AC-9.2:** The FR-9 differential corpus runs all four cases (`new-caller`, `missing-callee`,
  `both-missing`, `unrelated-import`) as fixture repositories with real pytest REDs. For each case
  it records the RED's exception line, whether the callee resolves at the RED base (by import) and
  both verdicts. The set of cases whose verdict changed is exactly `{new-caller}`.
- **AC-9.3:** The FR-9 incident replay covers HemaSuite `notebooklm-integration-interface` T4
  WIRE-PIN 1 (`test_notebooklm_resolver.py` at `531a6296b`), T5 WIRE-PIN 1
  (`test_notebooklm_initialize.py` at `7aa0d9dec`) and T6 WIRE-PIN 2
  (`test_notebooklm_status_report.py` at `c2d671f6b`). For each case the committed probe holds:
  - the direct-call form's RED reproduced at the task commit's parent: `AttributeError`/
    `ImportError` on the caller, with the callee resolving by import. For T4 this is the committed
    pin; for T5 and T6 it is the pin with the scaffold replaced, per FR-9;
  - on that RED, the new rule's verdict **valid** and the old rule's verdict halt;
  - for T5 and T6 only, the committed scaffolded pin's RED (`AssertionError`) and the old rule's
    verdict on it, which is valid;
  - a wire-cut re-run at the task commit in which the committed pin fails;
  - a citation of the original evidence (M4.1, M5.1, WIRE 2 revert).

  It is stamped with both repositories' shas. A case that cannot be reproduced is recorded with
  its failing command and counted. It does not satisfy the AC.
- **AC-9.4:** The six copies of the new-caller rule (FR-9 surfaces 1–5 and the GREEN variant) are
  bound to one authority. Either every surface is generated from or checked against one shared
  source, or one test asserts that the carve-out text is equal across all six copies. The plan
  names which mechanism. Whichever it is:
  - **The carve-out text is the whole quoted block in FR-9**, all three sentences: the validity
    condition, "The RED report must name both.", and the wire-cut obligation. A check that binds
    only the first sentence does not meet this AC.
  - **Each copy is read from its own source location.** The span read for one copy contains no
    other copy. Three readings do not meet this AC, because a healthy copy in the same span
    masks a sick one: a contains-check over the whole assembled prompt (the template's copies
    1, 2 and 6 are filled into it beside the header copy); a file-level contains-check over
    `codex-implementer-prompt.md`, which holds three copies; and a file-level check over any
    file that holds more than one copy. The design names each copy's locator. A locator states
    what it does not pin, and the test fails, rather than passing, when a locator matches
    nothing or more than one span.
  - **The control is a mutation of exactly one copy, and it makes the check fail.** It is run
    once per copy, so six times, and once per sentence of the block in at least one copy. Each
    mutation row's `find` is unique in its file, because `h_mad_mutation_harness.py`
    `anchor_status` refuses a `find` that does not occur exactly once. A `find` therefore carries
    copy-specific context, and the `.py` copy's `find` is written against the source bytes,
    including the adjacent-literal split. A row the harness refuses is not a control.
- **AC-X:** Every new guard carries a mutation row that bites (`MUTATION: ALL_CAUGHT` with a `test`
  per row). The full suite passes per task.

## Decisions on the brainstorm's open questions

- **D-1 `run_command`:** command-shape rule shared with Codex (FR-6). Rationale: the tree shows
  that is what Codex parity is.
- **D-2 Hook scope:** per project (`.agents/hooks.json`). Rationale:
  - The Codex gate is wired per project (HemaSuite `.codex/hooks.json`; this repository has no
    `.codex/`).
  - A tracked file reaches every worktree.
  - The handler cwd gives the root without trusting a payload field.
  - No global hook fires in every agy session on the machine.

  Residual: a project without the file has no agy gate. FR-5 turns that into a halt, not a silent
  pass.
- **D-3 Payload cwd:** the root comes from the handler cwd (FR-4), with `workspacePaths` as a
  cross-check.
- **D-4 Timeout:** provisional 1500 s, then FR-8's formula. The hook-handler timeout is a separate
  figure, derived from `JUDGE_BUDGET_S`.
- **D-5 Availability:** CLI on PATH + `agy_status` + `HMAD_AGY_UNAVAILABLE`, symmetric with Codex.
  No liveness probe: the gate runs on every write and must be offline and fast, and a probe spends
  quota. An exhausted agy shows up when the dispatch fails, and the orchestrator records it with
  `--set agy_status=exhausted`.
- **D-6 Project default:** feature record only. A second source doubles the surface the gate
  resolves, and per-feature is the operator decision. A later default can seed the same field at
  `--create`.
- **D-7 Flag location:** a state field (FR-7). It is not on the extracted verdict, because that
  line is `<KEY>: <VALUE>` and its consumers parse it.
- **D-8 Audit legs:** unchanged (FR-10).
- **D-9 Codex reviewing Codex (was OQ-1; operator decision, 2026-10-16):** yes. FR-7's flag fires
  for any `reviewer == implementer`, Codex included, for example the 5e anti-gaming verifier
  dispatched to Codex on a Codex-implemented feature. It is a warning only, never a block.
  Consequence: Codex-implemented features can now carry a `review_non_independent` Phase-7
  warning that has never appeared before.
- **D-10 `.agents/` exclusion (was OQ-2; operator decision, 2026-10-16):** narrow it. Applied in this
  clone by the orchestrator on the operator's answer: the `.git/info/exclude` entry `/.agents/` is now `/.agents/skills/`.
  Evidence at `d65374e9`: `git check-ignore -v .agents/hooks.json` prints nothing (exit 1, not
  ignored), and `git check-ignore -v .agents/skills` still reports the `/.agents/skills/` entry.
  D-2's tracked `.agents/hooks.json` therefore needs no `git add -f`.
  - **Residual / prerequisite.** `.git/info/exclude` is per-clone local configuration and is not
    versioned. Every other clone of this repository, and every other project that adopts the agy
    gate, needs the same narrowing (or a `git add -f`) before its `.agents/hooks.json` can be
    tracked. Linked worktrees share the main clone's `info/exclude` (git's common dir), so they
    inherit the narrowing from the clone they belong to. Where the file is not tracked, FR-5's
    check reads `UNWIRED reason=no-hooks-file` in any worktree that lacks it, so the gap is a halt,
    not a silent pass.
- **D-11 `review_independence_unrecorded` for every implementer (operator decision, 2026-10-16):**
  widened from agy-only to `codex|agy|grok|claude`, matching D-9 (FR-7). Warning only, never a
  block. Rationale: it fires only when the recording step was skipped, so a feature that follows
  the new flow stays quiet; without it, a missing record would hide a Codex-on-Codex self-review,
  which D-9 now flags when it IS recorded.

    before this shipped" from "skipped the recording step", and the only signal the record offers
    — absence of `review_independence` — is the skip itself, so any such rule would also silence
    the case the warning exists for. A warning on an in-flight feature costs one backfilled entry
    or one report line.

Audit rubric (TWO axes, both mandatory):

Axis A — Generic adversarial:
- Contradictions inside the doc
- Gaps (missing error paths, untestable AC, unstated assumptions)
- Weak claims (load-bearing decisions without justification)
- Scope creep (work outside the stated feature boundary)

Axis B — Invariant compliance (any breach = must-fix, you cannot downgrade).
Two layers, both binding:

### Base invariants (workflow-universal; non-overridable by any project file — but the operator `## Acknowledged-not-fixed` sidecar still applies to base findings):

# H-MAD Base Invariants — Axis B (workflow-universal)

> Shipped with the `/h-mad` skill. The orchestrator inlines this file verbatim into the
> `INLINE_BASE_INVARIANTS` slot (name written bare — a bracketed mention inside an inlined
> file survives substitution and reaches the reviewer as an unfilled-looking placeholder)
> of every plan / design / impl-plan audit, **before** the

## Audit-gate signal discipline
- Any gate/check whose verdict the orchestrator consumes MUST communicate PASS/FAIL via an
  explicit **stdout token** and **exit 0** on a normal verdict (PASS or FAIL). Using a non-zero
  process exit to mean "FAIL" is a violation — a non-zero exit registers as a Claude Code tool
  failure (`PostToolUseFailure`) and leaks into coexisting plugins' error handling. A non-zero
  exit is permitted ONLY for genuine operational errors (missing/unreadable input).

## Single-source contract
- A rule applied by more than one surface (e.g. an audit blocking-item count read by both the
  orchestrator gate step and a precondition checker) MUST have exactly one authoritative
  implementation that all surfaces call, OR a test asserting byte-equivalence across surfaces.
  Independent re-implementations that can silently diverge are a violation.
- A contract stated in a template (e.g. an empty-section sentinel) MUST match what the consuming
  gate logic treats as that case. Template guidance and gate behavior disagreeing is a violation.

## Standalone / no plugin dependency
- The skill MUST NOT acquire a **runtime dependency** on any other plugin (OMC, bkit,
  context-mode, etc.) or external skill (spec-kit, b-mad, pdca). Coexistence accommodations
  (sharing a state filename, conforming doc structure to an external validator's required
  sections) are allowed; *requiring another plugin installed at runtime* is a violation.

## No new external dependency
- Scripts MUST use only Python stdlib plus tooling already depended upon by the skill (the
  agent dispatch substrate (cmux or orca, via `hmad-dispatch`); `jq` where the existing hook
  already uses it; `pytest`).
  Introducing a new third-party package or new CLI is a violation.
- **Dispatched agent CLIs are not script dependencies.** `codex`, `agy` and `grok` are optional
  runtime *agents*: reached only through a `hmad-dispatch` verb (`exec`, `send`, …), never imported,
  required, or invoked by a script or test for its own work — tests reach them through stubs, and an
  absent agent CLI is a dispatch-time condition the verb reports, never a failure of the skill.
  The list is closed: adding an agent to it is an operator decision recorded here, not something a
  document or a dispatch may assume. (`grok` added 2026-09-28, operator decision on
  `grok-codex-fallback` design audit v2.)

## Portable time bounds
- A time-bounded command MUST NOT be written as `timeout <s> <cmd>` or `gtimeout <s> <cmd>`.
  **Neither is a macOS system component**, so the form is unportable in both directions.
  A stock box ships neither and the call fails at 127; a box carrying `brew install coreutils`
  runs it fine and the bound silently rests on a CLI h-mad cannot assume is there.
  **What your box has is not an input to this rule.** h-mad already owns a time-bounder that
  reachable wherever `hmad-dispatch` is, so the form is forbidden unconditionally — not because
  of what happens downstream. (Reachable, not universal: where the wrapper itself cannot be
  called the rule below still applies — halt, do not drop the bound.) Do not reason from a local probe to an exemption. For anything committed
  or dispatched the form is additionally a new external CLI dependency (§"No new external
  dependency"); a downstream 127 is how that eventually surfaces, never the reason.
  Do not settle the question by probing: a local `command -v timeout` that succeeds is not
  licence, it proves only that this box has coreutils, and it means the 127 that would have
  exposed the improvisation never fires. Use `hmad-dispatch run --timeout <s> -- <cmd...>`,
  which exits 124 at the deadline.
- Where a 127 does fire, its aftermath is worse than the 127 itself. Measured: the reflex after `timeout: command not found`
  is to re-run the same command **unbounded** and call it "checking directly". That does not fail
  at the deadline, it hangs the phase, and in every log h-mad reads a hang and slow work are the
  same bytes. A plan, a design, or a prompt that leaves an agent no reachable time-bounder is a
  violation; the correct behaviour when none exists is to **halt**, not to drop the bound.

## Doc-template superset compliance
- Generated phase documents whose type is validated by an external doc-structure validator
  (e.g. bkit PDCA: `plan` → `docs/01-plan/...`, `design` → `docs/02-design/...`,
  `report` → `docs/04-report/...`) MUST be supersets that satisfy that validator's required
  sections AND retain the existing h-mad sections. Dropping an h-mad section or failing the
  validator is a violation.
- The contract binds the **saved document**, not only the template it came from. Where such a
  validator reclassifies a document by a substring of its *content* — bkit's `isPlanPlus` promotes
  a plan to a larger required-section list on seeing `Plan-Plus`, `Plan Plus`, `plan-plus`,
  `Brainstorming-Enhanced`, or `Intent Discovery` anywhere in the file — a generated document
  carrying that substring is a violation even though the template is clean. Guard it mechanically
  (`scripts/h_mad_doc_shape_check.py`); the literals are unremarkable prose, so an author cannot
  be expected to avoid them from memory.

## Operator-override preservation
- The `## Acknowledged-not-fixed` sidecar override mechanism MUST remain functional for all
  layers (base + project). Any gate change that causes overridden items to still count as
  blocking, or that ignores the sidecar, is a violation.

## Backward compatibility
- A change to the audit gate MUST preserve the PASS verdict for audit docs that passed before
  the change. Flipping a historically-passing audit to FAIL (absent a real new blocking item)
  is a violation.

## Marker discipline
- Orchestrator phase transitions and halts MUST emit `[H-MAD]` log markers so a run is
  diagnosable from logs alone. Silent state transitions are a violation.

## Mutation verification
- A step that mutates state (a git operation, a file write, a remote/CLI call) MUST verify the
  mutation by **re-reading the resulting state**; an **exit code is not evidence that a mutation
  occurred**. A plan, design, or implementation that treats a zero exit — or an echoed success
  string such as `Sent N bytes` or `{"ok":true}` — as proof of the intended effect is a violation.
- The failure this blocks is silent and looks exactly like success: two `zsh` no-ops (backtick
  execution inside `-m`, a leading-dash path) both exited 0 while doing nothing, and a dispatch
  reported `Sent 7293 bytes` into a dead pane. Where a command reports on its own behaviour, the
  check must read the *thing it was supposed to change*, from a separate call.
- **When several mutations target the SAME line, vary one field and keep the anchor shared.** A
  guard whose failure has separable parts — exit code, stream routing, message content — needs one
  mutation per part, each replacing the same anchor. That shape is what proves a content assertion
  load-bearing: the mutants that keep exit and stream and strip only the text are exactly the ones a
  returncode-only test survives. Two discriminators worth writing into the spec: a
  first-vs-last-occurrence mutant survives whenever the sought item is last in BOTH regions, so the
  discriminating fixture must put the decoys between the markers and leave the tail empty; and
  `survived` has four distinct causes — missing guard, equivalent mutant, weak test, and a mutant
  that never ran — which the verdict token collapses into one word. Diagnose which before acting.

## Test discrimination
- A test or guard MUST be **observed failing against the unfixed code** before it is trusted.
  For a regression test, revert the fix and re-run; for a guard, stub it to its permissive value
  and re-run the suite. **Zero failures is a finding, not a reassurance** — it means the check is
  unenforced, not that the code is safe. Keeping a check that has never been seen to fail is a
  violation.
- A check that cannot fail is decoration, and it is worse than no check because it reports
  coverage that does not exist. Two guards shipped green this way and were caught only by
  stubbing: one passed solely because an unrelated helper stripped the env var its subject read,
  and a documentation test passed with the documented guidance deleted, because both of its
  component words already appeared in nearby prose. Neither was visible to review or to a green run.
- The mutation must itself be verified (§"Mutation verification"): a `.replace()` that matches
  nothing exits 0 and reports the guard as enforced.
- **A criterion that cannot discriminate in EITHER direction is vacuous, and it survives both a
  green run and a mutation battery.** The stronger case of the bullet above: not "this check never
  fails" but "this check returns the same observation whether the behaviour is present or absent".
  Measured on AC-2.5b, which spied on `is_cli_available` *returning* `False` — the forced-`True`
  mutation emits an identical record and returns the same value, so neither the passing run nor the
  mutated run could tell the two states apart. AC-7.5c was the same shape. **Neither audit leg saw
  either one**; the revising author found AC-2.5b while fixing an unrelated must. A document audit
  reads prose and cannot ask "does this pin discriminate?", so the question has to be asked where the
  criterion is written: **name the observation that differs between the implemented and unimplemented
  states, and if you cannot name one, the criterion is decoration** — delete it or replace it with a
  positive assertion only the implemented behaviour produces. Spying on a return value that both
  states produce is the recurring form.
- **Mutating a path-resolution function can disable the suite's own isolation.** Tests usually
  isolate by pointing an env override at a temp path, and that override is honoured by a branch —
  the same kind of branch a mutation deletes. Stubbing the override branch in `_pin_file` redirected
  every pin write in the suite onto the developer's live session file and replaced two real agent
  handles, while the run reported 642 passed. Before mutating anything that decides *where* state is
  written, snapshot the real target and restore it, or run in a sandboxed working directory.
- **A stub must model the step the real system CONSUMES.** The rules above are about asserting the
  right thing; this one is about the fixture telling the truth. A stub that replays state the real
  system consumes once makes a test pass before the fix exists: an orca stub replayed an acked
  delivery forever, so a sibling-cache test re-matched from the queue, pinned nothing, and passed
  against unmodified code. Cardinality is part of the model — a fake that writes a path once where
  production writes it twice let a verb never dispatch with 57 tests green. Before trusting a stub,
  ask which of its effects are destructive in production and make the stub destroy them too.

## Verifying a review finding
- **A review finding has three separable parts — facts, concern, prescription — and they fail
  INDEPENDENTLY.** Before applying a prescription, diff it against the RED tests and the spec's
  acceptance criteria. A finding that matches the design doc but breaks tests means the DESIGN
  drifted, not the implementation. Measured: one pass's prescription broke a guard (1 failed, 53
  passed) while its concern was entirely real, and another review's prescription was backwards.
- Test a prescription by applying it as a mutation and reverting it. When two passes dissent, ask
  what the codebase ALREADY does — twice the house pattern beat both readings.

## Guard narrowing
- When a change **deliberately makes a guard accept something it used to reject**, the relaxation
  MUST be shown to be *exactly* the intended case: run a corpus of inputs through the old and new
  logic and diff the verdicts, then account for **every** input whose verdict softened. A green
  suite is not evidence here — it encodes the cases someone already thought of, which is the wrong
  population when the question is "what else did this let through?". This is the inverse of
  §"Mutation verification": that proves a guard still bites, this proves a loosening did not widen.
- The relaxation MUST rest on a **guarantee of the thing being parsed**, not on a heuristic that
  re-implements it. Narrowing a scanner by "ignoring quoted regions" means re-deriving the target
  language's quoting rules in a regex, which is how a bypass gets introduced; narrowing it by a rule
  the language itself guarantees is safe. Verify that guarantee **against the real interpreter**,
  not its documentation (§"Assumption verification").
- Both halves were load-bearing when this was written. Narrowing a heredoc scanner so it stopped
  denying inert prose, a 23-input differential corpus flagged one case as a regression; running the
  shape through real `bash` showed the body genuinely never expands, so the *test expectation* was
  wrong and the code was right. Without the corpus that case ships as either an unnoticed hole or a
  "fix" applied to correct behaviour — and nothing else would have distinguished them. The same run
  confirmed the intended relaxations numbered exactly two, and that the remaining 21 verdicts were
  untouched.
- A narrowing is scoped by **which checks consult the reduced input**, not by the reduction itself.
  Exempting the quoted region from *one* class of check while every other class kept scanning the
  full input is what kept the change from widening; a blanket exemption would have disabled
  detections that were still correct for reasons unrelated to the false positive.

## Connection enforcement
- A task whose deliverable is a **connection** — a call site, an import, a registration, a route, a
  flag or value propagated across a boundary — MUST ship a test that **fails when the connection
  alone is removed and the callee is left intact**. A test that exercises the callee directly is not
  evidence that the callee is reached. Shipping a connection with no such test is a violation.
- **A whole-module revert cannot establish this**, because it removes both sides: the RED split
  returns identically for a wired and an unwired build. The same blindness runs through every other
  layer — a RED phase goes red because the callee is *absent*, an anti-gaming audit finds a
  callee-scoped unit test perfectly discriminating, and a review of the diff sees a call site that is
  *present* and therefore reads as correct. **Presence is not enforcement.** Measured across two
  consecutive wiring tasks: each shipped its single load-bearing decision untested through every
  audit cycle and through the RED phase, and only a mutation scoped to the connection caught it.
- Mutate the connection in **both directions**: remove it → the wire test must fail; force it to fire
  unconditionally → the fall-through/negative test must fail. One direction certifies a connection
  that exists but is unconditional. Verify the mutation landed before trusting the run
  (§"Mutation verification") — a revert that never happened reports as a pass.

## Incident replay
- A fix motivated by a specific observed incident MUST be **replayed against the real artifacts
  already on disk** that motivated it, not only against cases authored alongside the fix.
  **Synthetic cases alone are a violation** whenever such artifacts exist and are reachable.
- Cases written next to a fix inherit the author's model of the bug, so they agree with it by
  construction. A detector validated on 14 handcrafted samples rejected the real historical label
  it was written to accept; the same replay then measured the true rate (7 of 13), which reclassified
  the defect from a one-off into the majority case. Replay is how a fix is told from a belief.

## Assumption verification
- Every **load-bearing assumption** in a plan or design — an API's accepted inputs, a command's
  output shape, a boundary, a default — MUST be **executed as a throwaway command before it is
  written into the design**, and the design **cites the observed output**. An assumption asserted
  without evidence, where evidence was one command away, is a violation.
- Design review cannot catch a wrong assumption: it reads as reasonable, and the implementation
  and its tests are then both built from the same wrong model, so they agree with each other and
  pass. Tracer-bulleting the assumptions of one feature confirmed a `--porcelain` boundary,
  confirmed a base-ref chain, and found a truncation hole — all before any code existed. Separately,
  a selector grammar assumed from a wrapper's own code was wrong in a way that had already let a
  destructive verb run unguarded.
- The evidence belongs in the document, not only in the author's terminal. A cited output is
  checkable by a reviewer; "I verified this" is not.
- **Attributing a failure to a cause requires the controlled PAIR, not just the repro.** Run the
  case with the blamed step and the case without it, and require the observable to differ. A repro
  that reproduces confirms the symptom, never the cause. Measured four times: pane readiness was
  blamed for an `injected:false` that a missing `--inject` flag fully explained, and that causality
  shipped in a doc and a PR body; a title-only reading concluded "no agents running" and the
  operator corrected it; and two carried repros were each falsified by a control that removed the
  step they blamed. Re-run the MEASUREMENT as well as the claim — a brief's conclusion can be right
  while its method is wrong.

- **A contract to RECOGNISE something needs a real instance of it, captured from the running
  system, before any gate scores it clean** — a banner, a log line, a response shape.
  `pin-agents-tail-banner` passed 2663 tests, 49 mutations and 53 audit cycles while its matcher
  hit 0 of 5 real agent banners: all 12 corpus positives were written by hand. The fixture corpus must include at
  least one captured sample with its capture command cited; an idealised fixture is not a sample.

## Behavioural premises carry their command
- A premise about **behaviour** — "X currently does Y", "this guard fires when Z", "the suite
  collects N", "the parser rejects W" — MUST carry the exact command that produced it, inline and
  runnable, beside the observed output. An output recorded without its command is not
  re-derivable, and a premise that cannot be cheaply re-run gets re-READ instead, cycle after
  cycle, by every reviewer in turn. Measured: one false behavioural premise survived **10** audit
  cycles that way.
- Narrower than §"Assumption verification" and it fails at a different moment: there the evidence
  was never gathered; here it was gathered once, written down as a conclusion, and thereby made
  uncheckable. Both readers are then reasoning about prose.
- **The command belongs in the document even when the answer is one number**, because the number
  alone does not say what was counted. Measured: two readers measuring "the same" census got **3**
  and **23**, having run different commands, and neither could tell which was wrong until the
  command was written down beside it. `git grep -l '```' -- '*.py'` is the census; "21 files" is
  a claim about one.
- A premise whose command has become expensive to re-run is not exempt. Say so, and say what the
  cheap proxy is — an unrunnable premise is a premise no later cycle can falsify.

## Counts a dispatch reports
- **Re-derive every COUNT a dispatched agent reports; never carry it into a document, a commit
  message or a verdict on the agent's word.** A report that is right about its actions can still be
  wrong about its numbers, and the two failures look identical from outside — the prose is accurate,
  the figures are confident, and nothing in the report signals which is which.
- Measured 2026-08-26: an `exec codex` report stated an anchor sweep as `mutations=238` when the
  tree held **244**, with every spec byte-identical to HEAD and every other figure in the same
  report checking out. Nothing had changed; the number was invented. The cheap control existed the
  whole time — `--check-anchors` prints the count in about a second.
- This is narrower than §"Assumption verification" and it applies at a different moment: there the
  risk is an assumption written without evidence, here it is evidence that was produced, looks
  right, and is false. Prefer a count you can re-derive with one command over any count a
  dispatch hands you, and when a count is load-bearing for a verdict, re-derive it before recording
  the verdict rather than after.

## Wrapper–runtime reconciliation
- A wrapper verb over an **external runtime's CLI** MUST be exercised **live against that runtime**
  — a full create → list → remove cycle, or the verb's own equivalent round trip — before it ships,
  and its **output-key extraction fixed against the observed envelope**. Shipping a verb whose
  response shape is known only from stub fixtures is a violation, however green the suite is.
- Stub fixtures encode the author's model of the envelope, so the wrapper and its tests agree with
  each other and both are wrong together — the Incident-replay gap, applied to response parsing.
  Four occurrences: a create-response `.id` read from the envelope (a per-request correlation uuid
  that always exists, so it yielded a plausible but useless handle) in two different verbs; then
  probing a live response for a delivery-id field surfaced `run_required` — the whole structured
  path had been **dead at its first mutation**, and no stub test could see it because the stub had
  no concept of a Run binding. Later the same day the real ack key proved to be `deliveryId` while
  the extraction chain led with `delivery_id`, and the only test covering that loop pinned the
  spelling the runtime never sends.
- The live probe is what finds these, not the review: each was invisible to design review, to the
  suite, and to a careful reading of the vendor guide. Where a live run is impossible (destructive
  verb, no credentials), say so in the doc and name what stayed unverified — an unmeasured shape is
  an open risk, not a pass.

## Regression provenance
- When a change makes an existing test fail, the plan or design MUST establish whether that test
  **asserts current behaviour that the change is fixing** before proposing to edit it. **Changing an
  existing test to pass is a violation unless** the doc states that the test pinned a defect (or
  stale contract) as correct, and cites what it asserted.
- The reflex "make the failing test pass" preserves the bug when the test *was* the bug. Three tests
  in one session asserted the defect as an acceptance criterion — a forwarded selector a live
  runtime rejects, a create-response handle the pane never has, a cwd-relative path — and each would
  have survived a naive "adjust the test" edit. A red pre-existing test is evidence about the test as
  often as about the change.

## Both halves of a doc change
- Removing a documented instruction, flag, or capability MUST be paired with **the executable
  replacement landed** (or an explicit statement that the capability is intentionally dropped, with
  the reason). A test asserting only that the old text is *gone* passes for a deletion that silently
  lost the capability.
- An unexecutable instruction was deleted in one session; a test checking only its absence would
  have gone green while the run lost the ability it named. The gate is: assert the new path works in
  the same change that removes the old one.

## Reimplementation parity
- Replacing a third-party dependency (validator, parser, formatter) with an in-tree implementation
  MUST ship a **differential test asserting identical results against the original** across a corpus
  that covers every construct in use, AND against the **real artifacts on disk**. Shipping the
  reimplementation with tests that exercise only itself is a violation.
- A hand-rolled reimplementation is worth exactly what its differential test catches. A bundled
  JSON-Schema validator agreed with the library on a construct-complete corpus and on the live state
  records; the traps it had to match (annotation-only `format`, `bool` is not `integer`) were
  invisible without the library beside it. Parity on a synthetic corpus alone repeats the
  Incident-replay gap: the corpus shares the author's model of the reimplementation.

Axis C — Spec reconciliation.

The spec is the source of truth for what this feature must do. A plan or design
is derived from it and may legitimately argue for a narrower reading — but it
may not do so silently, because every downstream phase then measures the
implementation against a spec the design already walked away from.

Read the spec above and reconcile it against the target document **by
identifier**, not by impression:

**Design audits — every acceptance criterion.** For each `AC-N.M` in the spec,
classify the design as exactly one of:

| Classification | Meaning |
|---|---|
| `implemented-as-written` | the design covers the AC in its spec form |
| `restated` | the design covers it in a different, usually narrower form |
| `absent` | the design does not address it at all |

**Plan audits — every functional requirement.** Same three classifications at
`FR-N` granularity. A plan is a strategy document and is not expected to restate
each AC; it *is* expected to address every FR or explicitly defer it.

Reporting rules:

- For every `restated` item, **quote both forms** — the spec's wording and the
  design's — so the divergence is auditable rather than asserted. Then say which
  is narrower and in what respect.
- `restated` and `absent` are **must-fix**. This is not a judgement that the
  design is wrong: a narrowing may be well-argued and may be the right call. It
  is a judgement that the divergence must be explicit and must land in the spec
  before the gate clears, so the operator decides deliberately rather than
  discovering it at verification.
- An AC whose narrowing the spec **already reflects** is
  `implemented-as-written`, not `restated`. That is the loop closing correctly.
- Do not infer coverage from a section heading or a passing reference in a risk
  or rationale table. An AC is covered when the document says what will satisfy
  it.

Report Axis C as a table in your `## Summary`, then raise each `restated` or
`absent` item as its own `## Must-fix` bullet.

Effort contract (binding on you either way; MEASURED only on some dispatches):

- **Sweep the whole document. Do not stop at the first blocking finding.** Measured
  over 83 design / 74 plan / 34 impl-plan cycles on one feature: the median pass
  returned **one** must-fix against a prompt asking for all of them, which turns every
  defect into its own round trip and is most of why those numbers are that large.
- **Read the tree before asserting what is in it.** The documents are inlined above,
  which is exactly why a pass can look thorough having opened nothing. Their claims are
  *about* the tree — a `path:symbol`, a signature, a test name, a count against its own
  list — and those are the claims that turn out to be wrong.
- **When you re-derive a published figure, four things must match or your reading answers a
  different question. Each has been got wrong here by an auditor, not only by the orchestrator:**
  - *Commit.* Presence at a sha is not provenance. "X was introduced in revision N" needs the
    needle PRESENT at N's landing commit **and ABSENT at N-1's** — two readings return N and
    N+1 alike. `git rev-list <base>..<sha> -- <path>` first: if that commit does not touch the
    file, it is not the figure's provenance.
  - *Corpus.* **Run the command the document DEFINES, not one that reproduces the document's
    number.** A head-scoped series verified whole-blob agreed for four shas and then did not;
    the gating auditor re-ran it, reported it reproduced, and the scope was wrong the whole
    time. Agreement with a published value is evidence about arithmetic, never about scope.
  - *Grammar.* `grep -c` answers "how many lines contain this string", never "how many
    instances of this concept exist". Print the matching lines and classify them before you
    publish a count — a Python kwarg and a diagnostic field spell identically. Over markdown,
    collapse newlines and admit the inline-code delimiters (`` ` ``): a needle that cannot
    match across a backtick reported 2 sites where there are 4.
  - *Shell.* Take each control in its own invocation; a `cd` in a chained command is not
    scoped to that command.
- **If a document publishes a screen with `# expect 0`, RUN IT** rather than reporting that it
  is present. Three sheet entries certified "no scoped census moved" over a commit at which the
  document's own trip-wire read 8.
- **An ABSENCE claim is a figure.** "No corpus instance …", "the corpus has none", "nothing in
  this repository" — hold each to the same command and sha as a count; both that shipped here
  were false. A zero bounded only by some *unrelated* constraint is a defect: the document says
  why it is zero and whether that reason is load-bearing.
- **A stated PROPERTY of a screen is a claim about code — execute it.** "No working-file edit can
  move this" was false of the shipped line. Do the thing it says cannot move it, and re-run. A
  control over an ALTERNATION tests the alternation, never its branches: a healthy sibling covers
  a sick one (one boundary repair was half-applied three rounds running and passed every time).
- **Your report is held to this too.** Every count carries its UNIT (`grep -n` lines are not
  occurrences); a population you prescribe is derived once and cited twice; and your PRESCRIPTION
  is a claim about the tree — one prescribed naming an enclosing function for a line that has
  none. Check it or mark it unchecked, and give every alternative repair rather than the best-
  reading one.
- **A pass at or below two successful tool calls cannot certify a clean.** Writing the
  report and its marker costs those two by itself, so at that floor nothing was read.
  When your transcript is captured — an `audit-cycle` dispatch — the combiner enforces
  this and scores the cycle `UNVERIFIED` rather than clean. When it is not captured,

Class rule (Must-fix and Should-fix): **every bullet carries a `class:` continuation line**, `build` or
`measurement`, under the bullet and never as a `- ` bullet of its own (a leading `- ` is a second
finding). The test is one question: **would the code or tests a 5d/5e implementer writes differ if this finding were fixed?** Yes → `class: build` (an interface, a contract, a
predicate, a fixture, a test's assertion or RED/GREEN count, a false premise about the platform). No →
`class: measurement` (a published number, stamp, ledger row, sha series, pointer or self-count that is
stale or mis-derived; the tree is unchanged by fixing it). An untagged bullet is scored as `build`, so
omitting the line never softens a finding — it only costs the orchestrator the triage. Put the `class:` line directly under its bullet (before or after `quote:`); do not indent a sub-bullet between a finding and its `class:` line, which leaves the finding untagged.

Quoting rule (Must-fix and Should-fix): **if a finding asserts what a document says, prove it.**
Add an indented `quote:` line under that bullet naming the file and carrying the span copied

The `quote:` line is a continuation of its bullet, never a new `- ` bullet — a leading `- ` would
be scored as a second finding. Use one `quote:` line per document the finding names.

This exists because backticks alone are ambiguous. Reviewers correctly backtick three other kinds
of span — code they are **proposing** as the fix, test inputs they **constructed**, and commands
they **ran** — and those legitimately do not occur in the document. Measured over 37 must-fixes:
43% of *real* findings carry a backticked span absent from the document, so absence alone proves
nothing and no automatic check can be built on it. `quote:` is the marker that separates a claim
about the document from everything else you are entitled to write in backticks.

A finding that asserts document content with no `quote:` line is not rejected automatically, but it
is the first thing the orchestrator re-derives from source — and a `quote:` span that does not occur
in the file it names is a finding withdrawn, not a finding to argue.
